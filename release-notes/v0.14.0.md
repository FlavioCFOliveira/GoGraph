## Semantic-versioning rationale

**MINOR**, under [Semantic Versioning 2.0.0](https://semver.org/) as this project applies it
pre-1.0 ([docs/semver.md](../docs/semver.md)).

- **Backwards-compatible functionality was added** — new exported types, functions and
  struct fields in `cypher/exec`, `cypher/explain`, `cypher` and `graph/lpg`; two new plan
  columns; seven new metric series. That is the MINOR trigger.
- **No change is marked breaking.** No commit in the window carries a `BREAKING CHANGE`
  footer or a `!` subject, verified over the full commit bodies.
- **Two backwards-compatible bug fixes** (#2771, #2773) would on their own have been a PATCH.
- **But the observable output changed**, and that is stated plainly rather than hidden behind
  the MINOR label. Adding fields to an exported struct breaks an **unkeyed** composite
  literal, and changing the rendered plan text breaks a consumer that parses it. Neither is a
  Go API removal, and pre-1.0 the minor digit absorbs both, but a caller in either position
  has work to do. See

## Highlights

### A db-hits figure nobody counted stopped printing as zero

The `DbHits` column could not distinguish *"counted, and it is zero"* from *"never counted at
all"*. Both printed `0`, and a reader had no way to tell which they were looking at.

It is now tri-state: a counted figure, a counted zero, and **`?`** for a figure nobody
counted. A total that sums across an unknown renders **`x + ?`** rather than a plain number
that quietly understates the truth. When **no** operator in a plan reports the figure at all,
the column is dropped entirely rather than filled with placeholder glyphs.

```
+------------------------------+----------+------+----------+---------+-----------+
| Operator                     | Est.Rows | Rows |   DbHits | Removed | Time (ms) |
+------------------------------+----------+------+----------+---------+-----------+
| Project                      |        - |   10 |        ? |         |     0.357 |
| └─ Filter                    |        - |   10 |        ? |    1990 |     0.354 |
|    └─ NodeByLabelScan [Wide] |     2000 | 2000 |     2000 |         |     0.042 |
+------------------------------+----------+------+----------+---------+-----------+
| Total                        |          | 2020 | 2000 + ? |         |     0.357 |
+------------------------------+----------+------+----------+---------+-----------+
```

The codebase already applied exactly this rule elsewhere: `bolt/server/plan_meta.go` omits the
page-cache fields rather than sending `0`, because GoGraph has no page cache and a `0` would be
a measurement claim. #2760 applied that one rule to `DbHits`.

**`UNKNOWN` is the default, and that ordering was forced by evidence.** The motivating audit
had assumed `Project` is a pure row transformer that reads nothing. It is not: the pattern
evaluator walks adjacency through the `evalRow` bridge, and `Project` was observed reporting
1 db-hit where the equivalent `Expand` reported 101. So an operator is trusted to report a
known figure only when it says so — 20 provably storage-free operators opt in through a
`noStorageAccess` marker, policed by a census test that derives the operator set from the
package AST rather than from a hand-maintained list.

### Four operator families that read storage and reported nothing now count it

Each is proved by an observed arm in which the db-hits figure **differs from the operator's
own row count** — which is the discriminator that makes the claim falsifiable, because a
figure that differs from the row count cannot have been derived from it.

| Operator | Before | After | Proving arm |
|---|---|---|---|
| `Expand` | `dbhits=1` on a type-filtered hop | `dbhits=100` | `-[:KNOWS]->` over a source with 99 `:LIKES` + 1 `:KNOWS`: `rows=1, dbhits=100` |
| `ParallelScanProject` | `0` | `2000` | `MATCH (n:B) WHERE n.v = 0 RETURN n.k + 1`, threshold 10: `rows=500, dbhits=2000` |
| `ParallelAggregateScan` | `0` | `2000` | `MATCH (n) RETURN n.v AS g, count(*) AS c ORDER BY g`: `rows=4, dbhits=2000` |
| `ParallelCountScan` | `0` | `2000` | `MATCH (n) RETURN count(*)`, threshold 10: `rows=1, dbhits=2000` |
| `ShortestPath` | `0` | `117` | `shortestPath((a)-[*]-(b))` on a 60-node chain: `rows=1, dbhits=117` |
| `AllShortestPaths` | `0` | `117` | `allShortestPaths((a)-[*]-(b))` on a 60-node chain: `rows=1, dbhits=117` |

**`Expand` changed definition, not merely scale.** It reported the edges it *emitted*; it now
reports the adjacency slots it *walked*. The old behaviour meant the same 100-slot CSR walk
reported `100` or `1` according to a predicate the storage layer never saw — a 100×
under-report at the filter's selectivity. Neo4j charges the hit regardless of the predicate
outcome, so the previous figure was an incompatible definition rather than a different unit.
The counter costs **O(1) per input row**, not per slot: the cursors already advance once per
slot, so bracketing their position at `loadAdjacency` yields an exact count from one integer
subtraction. Exactness was proved by a temporary per-slot probe that panicked on
disagreement — 0 disagreements over the full suites, and 36 once the window close was deleted.

**The three morsel-parallel leaves were the sharpest case.** Identical work, identical rows,
and the reported storage access moved to `0` because of `ParallelScanThreshold` — a setting the
reader never chose and cannot see in the output. Each leaf now reports a figure equal to what
the **serial control arm** reports for the same graph, which is the whole point: the number no
longer depends on a planning decision invisible to the reader. The charge is one atomic add
**per morsel** — one per 1 024 node references — and that granularity is not a convenience:
#2649 measured per-row shared atomics on this same operator at 18.9 % of flat CPU, with
scaling stopping past four workers. A node reference is counted once even though two phases
touch it, so a parallel plan reports N and not 2N against its serial twin.

### Rows removed by a filter

A new **`Removed`** column reports how many candidate rows a predicate threw away — the
reader-side half of the question `DbHits` answers from the storage side. `Filter`,
`ColumnarFilter` and `Expand` report it, through a `rowsRemovedCounter` marker with a
compile-time census.

The rule is worth stating exactly, because it is not the obvious one:

- an operator with **no rejection mechanism** omits the cell entirely — `NodeByLabelScan`,
  `Project`, every leaf;
- an operator that **has** one and rejected nothing prints **`removed=0`**, measured on
  `MATCH (r:Root)-->(b)` where `Expand` reports `removed=0` for an untyped walk.

PostgreSQL suppresses that zero in text mode. GoGraph prints it deliberately, because a filter
that rejected nothing is precisely the finding a reader of a slow plan is looking for. The
divergence is recorded rather than accidental.

### The planner estimate now sits beside the measurement it predicted

`Est.Rows` renders immediately left of `Rows`, over one plan, in one table — so an estimate
and the measurement that tested it can be compared without running two calls and aligning two
differently-shaped trees by hand. `Engine.Explain`'s tree gained the matching
`(est. rows=N exact)` annotation.

Provenance is marked, following the conventions `ExplainTable` already established: `N exact`
for a maintained exact count, `~N` for a histogram- or sample-derived figure, and `-` where
nothing is derivable. Four plan shapes have no logical node at all — the range-seek leaf, the
min-label re-anchored scan, the parallel leaves, and the columnar fusion chains — and they
render `-` rather than borrowing a neighbour's number.

**An honest limit, measured rather than glossed:** 80 of 110 observed operator instances render
`-`. That is not a mapping failure. `ExplainTable` renders `-` for `Selection`, `Projection`,
`ProduceResults` and `CartesianProduct` on the **logical** plan too, so the estimator itself
only attributes cardinality to access-path leaves. #2765 exposed that coverage limit; it did
not cause it.

### The planner consumes its own statistics for the first time

The property statistics have been maintained since #2097. Until this release, **nothing but
the `EXPLAIN` renderer read them** — `statsEqualityEstimate` and `statsRangeEstimate` had no
consumer outside the display path. #2766 wired them to a plan decision: the
disjoint-component join reorder now estimates a filtered component's emitted rows from the
histograms.

This is the first plan decision in GoGraph driven by a measurement rather than by a structural
rule, and the closing audit confirmed it **independently of #2766's own gates**, with a plan
that changed shape:

```
Query: MATCH (b:B), (a:A {tag:'rare'}) RETURN a.i, b.i
Graph: 400 :A, one of which carries tag:'rare'; 400 :B
The ONLY difference between the arms is whether RefreshStatistics has run.

ARM A — no statistics            ARM B — statistics refreshed
  ColumnarProject                  ColumnarProject
    Apply                            Apply
      NodeByLabelScan [B]              Filter
        (rows=400)                       NodeByLabelScan [A]
      Filter                               (rows=400, est=1/exact)
        NodeByLabelScan [A]            NodeByLabelScan [B]
          (rows=160000)                  (rows=400)
```

The **shape** differs, not merely the annotation: arm A drives `:B` and re-scans `:A` once per
outer row, while arm B drives the filtered `:A` and scans `:B` once. Counted db-hits fall from
**160 400 to 800**, a **db-hits count ratio** of −99.50 %, on a query whose result is identical
in both arms. Both labels have the same live cardinality, so a label-count-only planner cannot
make this choice — it is the property statistics that make the arms distinguishable.

**That −99.50 % is a count ratio, not a timing.** The audit host was not quiet (load average
1.42–2.52), and the audit therefore contains no latency or throughput figure at all.

Two design points, because both were forced rather than chosen:

- **The gate is a minimax over two cost rules.** `Apply` re-`Init`s the inner arm per outer
  **row**, while a `Selection` may be rewritten into a seek that collapses drain onto rows.
  The planner cannot see which realisation it will get, so a swap must win under **both**
  rules; each rule alone regresses under the other.
- **A staleness screen was added for the equality path**, which the design had not
  anticipated. An MCV hit is tagged `estExact` and carried no staleness check, so a stale
  count could have driven a swap. The screen closes that for the reorder — but not for
  `EXPLAIN`, which is still open as #2772.

The trustworthiness veto is untouched, and `estStats` is consumed over its **certified error
interval** under a 3× margin rather than at the point estimate.

### How wrong the estimates turn out to be is now observable

`cypher.stats.qerror` observes `max(est, act) / min(est, act)` per operator of a `PROFILE`d
plan; `cypher.stats.qerror.high` counts the samples past the 3× margin; and
`Engine.StatsMisestimatedPairs` reports **how many** `(label, property)` pairs are behind
them — it returns a count, not the pairs.

Three properties are deliberate:

- **The provenance boundary is `estimate.trustworthy()`**, because an *absent* estimate would
  invert the truth rather than add noise: its zero clamps to 1, so an operator emitting no rows
  would score a perfect q-error of 1 for an estimate nobody made.
- **`PROFILE`-only is structural**, not a runtime check — one call site inside
  `profileMaterialised`, policed by an AST gate.
- **A successful `RefreshStatistics` clears the pair set**, so it answers "is a refresh
  overdue?" rather than accumulating a lifetime tally. A non-zero reading *after* a refresh is
  the more interesting fact that the fresh statistics are still predicting badly.

`StatsMisestimatedPairs` counts only what a `PROFILE` has actually looked at. **A zero means
"nothing observed to be wrong", never "everything is right"** — and §7.3 of the closing audit
shows why that distinction matters (see
[*What this release does not do*](#what-this-release-does-not-do)).

### Two defects were found by the sprint's own gate, and both were fixed

Sprint 355's gate failed, twice, on defects that were **in the module** and not in the
instruments — the inverse of the previous release, where every red gate turned out to be an
instrument defect.

**#2771 — a declined MVCC label count was read as an empty label.** `ResolveLabelCount` is
exact-or-nothing and declines while MVCC history is live. `statsRangeEstimateInner` discarded
the `ok` flag, and the `n <= 0` guard below it then demoted the estimate to `estFallback`, so
the histogram path went silently inert and the veto kept the written order. The visible symptom
was the worst kind: **`EXPLAIN` rendered a reorder the engine did not take.**

The premise the task was opened on was **corrected by the evidence**: no concurrent writer is
involved. The records are the seed graph's own birth records, reclaimed by an asynchronous
vacuum that lags under whole-module parallel load — measured at **303 unreclaimed on an idle
graph with no writer**. On an idle host the vacuum always wins, which is exactly why the defect
was invisible outside `go test -race` over everything.

**#2773 — a labelled count cloned a roaring bitmap it never corrected.** The count path gated
on a **global** unreclaimed-record flag while the bitmap path gated **per-label**. When the
global gate was up and the per-label gate clear, `labelBitmapAsOfFiltered` cloned the bitmap
and returned it **uncorrected** — the clone existed for no purpose but to have
`GetCardinality()` called on it. That no correction ran was proved by the allocation figure
being **flat from 1 to 1 000 live records**, where a real correction grows with the count. An
idle graph reaches the state on its own, because `AddNode` writes a life record whose churn set
is the labels held at that instant — none — so an unreclaimed birth raises the global flag and
no per-label counter at all.

## Measured gains against v0.13.0

**This release is not measurably faster, and no claim is made that it is.** The
head-to-head against `v0.13.0` was run in one dimension only — **allocations** — because
the host carried a load average of 2.86–19.73 throughout, substantially caused by Spotlight
indexing the measurement's own worktrees. **A timing comparison remains UNMEASURED.** That
is not the same as "no difference".

Method: two clean worktrees, `-trimpath`, plain build (**no `-race`** — allocation counts
are not build-invariant), three arms interleaved with the order rotated each round, and the
noise floor measured first. Full record:
[`docs/benchmarks/v0130-vs-v0140-2026-09-06.md`](../docs/benchmarks/v0130-vs-v0140-2026-09-06.md).

**Noise floor.** Two independent builds of the same `v0.14.0` tree are byte-identical, so
`B` vs `B2` is the same binary against itself: **169 of 171** benchmarks agree within 0.5 %.
The two that do not are plan-cache shapes, where this host manufactures an **11.34 %**
allocation difference from nothing. Separately, the `store/wal` test binary is
**byte-identical between the two releases**, and all 7 of its benchmarks report identical
allocations — the method returns "no difference" where none is possible.

**Result — the added counting work costs nothing.** Sprint 355 added slot bracketing to
`Expand`, a per-morsel atomic to the three parallel leaves, per-run accumulation to the
shortest-path operators, reject counting to the filters, and an estimate on the physical
plan. Across **171 benchmarks, 159 are unchanged**; `Expand` is identical in all 14 arms and
the parallel leaves in all 17. **Nothing regressed.**

**Result — eight benchmarks changed, every one a reduction:**

| Benchmark | `v0.13.0` | `v0.14.0` | Δ `allocs/op` |
|---|---|---|---|
| join reorder, skewed shape, reorder on | 5 925 706 | **59 968** | **−98.99 %** |
| join reorder, live-history shape (quiet / live) | 564 429 / 564 428 | 25 031 / 25 055 | −95.6 % |
| `ReadAfterWrite_Session` / `_Sessionless` | 53 | 41 | −22.64 % |
| `ShortestPath_Layered` / `_LayeredTyped` | 126 | 108 | −14.29 % |

**The reorder gain is conditional and must not be quoted as a general speed-up.** It needs
`RefreshStatistics` to have run **and** a qualifying query shape — a disjoint two-component
match where a label count cannot identify the cheaper driver but a `(label, property)`
estimate can. Attribution is direct rather than inferred: the physical plan changes (at
`v0.13.0` the 100-row `:B` component drives and re-scans the 20 000-node `:A` label once per
row; at `v0.14.0` the filtered `:A` component, estimated at 3 rows, drives), the results are
byte-identical across both trees, and the reorder-disabled control is unchanged.

**Four benchmarks are unreliable and no claim is made for them** — the plan-cache shapes,
whose own round-to-round spread reaches 19 %.

## Performance — what was added, and what is not yet measured

**This release ships no release-level performance claim, and the reason is structural rather
than an omission.**

Sprint 355 **adds counting work** to paths that previously did none:

- slot bracketing in `Expand` — one integer subtraction per input row (#2761);
- one atomic add per morsel in each of the three parallel leaves — one per 1 024 node
  references (#2762);
- per-adjacency-run slot accumulation in `ShortestPath` and `AllShortestPaths`, charged at 9
  sites through one `scanRun` helper so the count and the loop bound cannot drift (#2763);
- rejected-row counting at 8 sites across the row and columnar filter paths (#2764);
- carrying the planner's estimate onto the physical plan (#2765).

Each was measured **at its own task, against its own baseline, with a noise floor measured
first**, and showed no statistically significant regression there:

| Task | What was measured | Result |
|---|---|---|
| #2761 | all 18 `BenchmarkExpand*` arms, `-benchmem -count=5` | allocs/op identical; **no timing claim made** — host at load average 1.5–3.0 |
| #2762 | parallel-scan benchmarks at `-cpu=1,4,10`, three arms rotated within every round | race-clean; concurrency deltas at 1/8/64 inside a noise floor that itself produced three "significant" verdicts between **identical builds** |
| #2763 | 7 shortest-path arms | zero allocations added; **no timing claim** — load average 2.4–2.9, and the noise floor produced a significant −1.57 % between identical builds |
| #2764 | 11 filter arms | allocations identical; **no timing claim** — load average 1.5–3.2 |
| #2765 | ordinary query path, plain build | allocation counts are the claim; **no timing claim** — load average 2.3–4.4 |

**None of those is a release-level measurement.** They are five separate per-task A/Bs on five
different shapes, each answering only "did *this* change regress *this* benchmark". The
**aggregate** cost of the added counting, across a realistic workload, at the release level, has
**not been measured**. Until the head-to-head above is filled in, this release makes **no claim
to be faster than `v0.13.0`**, and it would be equally wrong to assume it is slower.

Note how often the row above reads "no timing claim, host at load average N". That is the
sprint's own discipline and not a shortfall: allocation counts and db-hit counts are
load-invariant, wall-clock figures at these scales are not, and a figure taken on a loaded host
was reported as a count or not reported at all.

### The one per-task speed-up worth recording

Kept explicitly scoped to its own benchmark, and **not** offered as a release-level gain.

**#2766's join reorder, on `BenchmarkJoinReorderStatsSkewed`** — 20 000 `:A` of which 3 match,
× 100 `:B`:

| | figure |
|---|---|
| ns/op | 261.638 m → **2.658 m, −98.98 % (p = 0.000, n = 12)** — a 98.4× speed-up |
| B/op | 47.2 MiB → 553 KiB, −98.83 % |
| allocs/op | 5.93 M → 60 k, −98.99 % |

**Conditions, because the figure is meaningless without them.** Apple M4, 10 cores, go1.27.1
darwin/arm64, **non-race** build, `-benchtime=1s -count=1` over **12 interleaved rounds**,
compared with `benchstat`. The **noise floor was measured first**, same code against itself:
2.658 m ± 1 % versus 2.663 m ± 1 %, `~ (p = 0.887, n = 12)` — no significant same-versus-same
difference. **The host was not idle** — load average 1.87–2.72 on 10 cores, with a persistent
root `osascript` at ~15 % CPU. The noise floor was measured under those same conditions, which
is why a 98.98 % delta is not attributable to host noise; but **the absolute ns/op figures are
not quiet-host numbers and must not be quoted as such.**

**What this figure does not say.** It is one synthetic skewed shape, chosen to exhibit the
effect. It says nothing about a workload whose arms a label count can already separate, and
nothing about the release as a whole.

A modelling check run alongside it **refuted a hazard the consulting specialist had raised**:
a full filtered scan measured **23.94 % faster** than a bare scan of the same label
(1.419 m → 1.079 m, p = 0.000), because the predicate rejects rows before the aggregation pays
for them. Charging a filtered arm the full `N(label)` drain is therefore an *over*-charge
relative to a bare scan — the conservative direction, which is the direction a planner gate
should err in.

### #2773's allocation reduction

**32 → 20 allocations per operation** on a bare labelled `count()` over a plan-cache hit, on
the arm where unreclaimed MVCC records are live, with the quiet arm unchanged as the control.
The ceiling stays at 20 and gained a **lower** bound, so it cannot silently stop measuring.

**Build mode is stated because allocation counts are not build-invariant**: in isolation the
figure reads 19.0 in both plain and `-race` builds, but `-race` does change B/op (2 064 versus
2 056). The task also recorded a wall-clock figure for the same arm; **it is not reproduced
here, because no noise floor or host load was recorded alongside it.**

## Behaviour a caller can observe — the compatibility surface

Nothing here is marked breaking. Every item is observable, and the first four change bytes a
consumer may be parsing.

1. **`Engine.Explain` gained an `(est. rows=N exact)` annotation** on the physical plan tree.
   Where an operator has no derivable estimate, no annotation is added.
2. **`Engine.Profile`, `Engine.ProfileTable` and `Result.Profile()` gained `Est.Rows` and
   `Removed` columns**, and **an uncounted db-hits cell now renders `?` rather than `0`**, with
   an incomplete total rendering `x + ?`. Each column is dropped entirely when no operator in
   the plan carries that figure.
3. **`exec.PlanNode` gained exported fields** — `Est`, `DbHitsKnown`, `RowsRemovedByFilter`,
   `RowsRemovedByFilterKnown`. **`explain.OperatorStats`** gained the same four;
   **`explain.ProfileReport`** gained `TotalDbHitsUncertain`.
4. **Bolt `plan`/`profile` metadata gained `EstimatedRows`, `EstimatedRowsSource` and
   `RowsRemovedByFilter`, and now OMITS `dbHits` for an uncounted operator** rather than
   sending `0`.
5. **`Expand`'s db-hits figure changed definition** — adjacency slots walked, not edges
   emitted. A monitoring threshold set against the old figure will read up to the filter's
   selectivity higher; on the audit's arm that is 100×.
6. **The three parallel leaves and the two shortest-path operators report non-zero db-hits**
   where they previously reported `0`.
7. **The plan a query runs can now differ when statistics are present.** The reorder is
   **result-identical** — its order-safety gate is untouched and a differential suite holds the
   result multiset — but the plan **shape** is not.

### What you must do

- **If you parse plan text**, handle `?` in a db-hits cell and `x + ?` in a total, and do not
  assume a fixed column set: `Est.Rows` and `Removed` appear and disappear per plan.
- **If you are a Bolt client**, handle `dbHits` being **absent** from a profiled operator. That
  absence is the wire-level half of #2760 and it is deliberate.
- **If you construct `exec.PlanNode`, `explain.OperatorStats` or `explain.ProfileReport` with
  an unkeyed composite literal**, it will no longer compile. Switch to keyed fields. Keyed
  literals are unaffected.
- **If you assert on plan text in your own tests**, expect the new annotation and columns.
  Two `internal/sim` oracles in this repository were found comparing a data-dependent plan
  **string**; they now compare the shape, which is what they meant all along.
- **If you have thresholds or dashboards on db-hits**, re-baseline them. Six operator kinds
  now report a materially different number, and in `Expand`'s case a differently *defined*
  one.
- **Everyone else: no action.** There is no data migration, no format change, no configuration
  change, and no API removal.

## Premises refuted — the negative results

The sprint's most useful output, recorded because a refuted premise that goes unrecorded gets
re-derived next cycle.

- **`Project` is not a pure row transformer** (#2760). The motivating audit assumed it was.
  The pattern evaluator walks adjacency through the `evalRow` bridge, and `Project` was
  observed reporting 1 db-hit where the equivalent `Expand` reported 101. This is why UNKNOWN
  became the honest default instead of an opt-out.
- **`AllShortestPaths` is level-synchronous, not bidirectional** (#2763), and
  `totalEdgesTraversed` must **not** be folded into its db-hits figure — `exhArcs` already
  charges the whole run through `scanRun` and then counts only the surviving arcs, so summing
  them would double-count one walk under two definitions, by up to 2×. Both premises came from
  the task's own text and both were refuted by the code.
- **No concurrent writer is involved in #2771.** The task was opened on that premise. The live
  records are the seed graph's own birth records, left by a vacuum that lags under load —
  303 of them on an **idle graph with no writer**.
- **#2773 is not a measurement artefact**, which is how its own author framed it twice. The
  `+12` allocations were real work. And **#2753 named the wrong cause** for the same
  signature: it attributed the 32-vs-20 to sibling goroutines plus external load and fixed it
  by re-execing into an isolated child — but that isolation was already in the tree when the
  gate failed twice more, and a measurement alone in its own process cannot be contaminated by
  siblings.
- **`labelBounder` was refuted as the instrument** for #2771's staleness denominator, and a
  cheap lower bound was rejected too, both with reasons recorded.
- **The specialist's worked example for #2766 separates nothing**, and was refuted before
  implementation.
- **A predicate surcharge is the wrong direction** — see the 23.94 % modelling check above.
- **Reading estimates through the build's own snapshot resolver silently deleted them**
  (#2765), because `ResolveLabelCount` is exact-or-nothing and declines while MVCC history is
  live. That finding is what became #2771.
- **#2764's own brief mis-stated the rule it shipped.** It summarised rows-removed as
  "omitted, never `0`, when an operator rejects nothing". The shipped rule is different and
  better: no rejection *mechanism* omits the cell; a mechanism that rejected nothing prints
  `0`.

### Three verification findings worth more than the fixes

- **#2764's decisive verification was a single-site deletion**, which found that the columnar
  `FillChunk` forward increment was reached by **no test at all** while all four packages went
  green — and the forced per-site sweep then found a second, the columnar reverse arm. The row
  and columnar paths share their edge decisions but charge rejections separately, so every
  row-path gate left both columnar charges unproved, and **return-value mutation cannot detect
  that**. All eight sites are now killed by individual deletion.
- **#2767 needed three mutation passes.** The first counted three compile errors as kills. The
  second found two conditions that **cannot fail** — both were deleted rather than gated.
- **#2773 found its own new function's MVCC ordering claim ungated**: inverting the order
  passed all three packages. A dedicated seam now sits between the two reads and a test kills
  the inversion. **Two sibling ordering claims are reported UNGATED rather than assumed
  sound**, and a third is undriven entirely. A stated limit of the whole approach: every
  seam-based gate here is defeated by a mutation that relocates the **seam** rather than the
  reads, and nothing but the godoc defends the seam's position.

## Release packaging was broken, and is fixed

**#2758 — `.goreleaser.yaml` shipped the wrong files.** The archive file list contained
`docs/**/*`, a glob that matches only paths carrying **at least one directory component**. The
consequence, counted from `git ls-tree -r --name-only v0.13.0 -- docs/`:

| | `v0.13.0` tarball | after the fix |
|---|---:|---:|
| top-level `docs/*.md` | **0 of 112** | **113 of 113** |
| Markdown documents in total | 116 | **233 of 233** |
| raw `.txt` / `.log` / `.meta` / `.sh` | **138** | **0** |

Every one of those 138 raw files was under `docs/benchmarks/`. This sprint added 79 more, so
the ratio was getting worse, not better.

The file list now ships `docs/*.md` **and** `docs/**/*.md`. **Both patterns are load-bearing**,
because `**` never matches zero segments — `docs/**/*.md` alone reaches `docs/tck/status.md`
but not `docs/cypher.md`.

**It was verified the only way that counts: by building a snapshot artefact and extracting it.**
Reading the config is exactly what let the defect stand for a whole release and then put a false
claim about it into the changelog. The verification recipe is now recorded in
`.goreleaser.yaml` beside the file list:

```
goreleaser release --snapshot --clean --skip=publish,before,validate
tar tzf dist/gograph-*-darwin-arm64.tar.gz | grep -c '^docs/[^/]*\.md$'
```

All four OS/arch archives were checked and are identical in their document set. **The archive
grew**, from 4.4 MB to 5.3 MB: the fix adds 3.03 MB of top-level documentation and removes
2.14 MB of raw logs. That is a deliberate trade and not a size reduction.

**#2759 — the `v0.13.0` changelog entry contained a false claim, and it is corrected in place.**
The entry recording that `docs/release.md` and `CONTRIBUTING.md` asserted a non-existent branch
and tag protection regime went on to say the claim "shipped", because `.goreleaser.yaml`
"bundles `docs/**/*` into every release tarball, so the claim reached consumers as supply-chain
assurance". That sentence was **false**, and it was reasoned from the config rather than
verified against an artefact: `docs/release.md` was not in the `v0.13.0` tarball, and
`CONTRIBUTING.md` is not in the archive file list at all. The finding itself is unaffected — the
protection regime does not exist and both files did assert it — and only the claim's *reach* was
overstated. The correction is recorded as a dated note inside the `[0.13.0]` entry rather than
by editing the sentence away.

## What this release does not do

Every item below was **verified to still hold** at the closing tree `83ba8d8b`. Items are
flagged with a backlog task where one exists.

### Reachability and dead surface

- **`exec.OptionalExpand` is unreachable from any query** — measured: **0 of 11
  `OPTIONAL MATCH` shapes plan it**, every one lowering to `OptionalApply(… Expand …)`, and no
  `ir.OptionalExpand` appeared in any logical plan either. `exec.NewOptionalExpand` is still
  constructed in `cypher/api.go` (line 10391 at this release tree; the closing audit cites
  10358 at `83ba8d8b`), so the operator is **unwired, not dead**. **#2769** decides
  wire-or-retire.
- **`exec.RenderPlan` has no caller**, and renders a plan **missing the columns this release
  added**. `grep -rn 'RenderPlan('` excluding `RenderPlanNode` matches only its own definition.
  Its godoc says so honestly. **#2770**.

### Estimate quality

- **An MCV equality estimate is tagged `estExact` with no staleness check at all**, and this
  was demonstrated by measurement, not inferred: refresh with one `tag:'rare'` row, add 399
  more without refreshing, and `ExplainLogical` still prints `Selection (est. rows=1, exact)`
  while the operator emits 400. In the **same plan** the sibling `NodeByLabelScan` correctly
  updates to `est. rows=799` — one estimate live, one stale, **both tagged `exact`**. #2766
  added a staleness screen for the reorder's own use; `EXPLAIN` is still exposed. **#2772**.
- **The most-wrong estimate is the one q-error cannot see.** Columnar fusion chains carry no
  estimate, so they contribute no q-error observation — and a stale MCV estimate wrong by
  **400×** therefore produces **no q-error observation at all**, because the shape that exposes
  it fuses into a columnar chain. That shape, the single-pattern filtered match, is the
  commonest read form in the language. `ColumnarProject` renders `-` in 8 of 8 instances.
  No task.
- **`Expand`'s estimate ignores an intervening `Selection`**, biasing its q-error high. It
  carries `exact` in 4 of 6 observed instances with no allowance for a filter between it and
  its input. No task.
- **Estimate coverage: 80 of 110 operator instances render `-`.** A property of the estimator,
  not of #2765's mapping. No task.

### Reporting residue

- **The rendering still does not distinguish MEASURED from DERIVED.** A `NodeByLabelScan`
  reporting `2000` and a `ParallelScanProject` reporting `2000` render identically — the first
  is its own row count, the second a real walk. The column now separates *counted* from *not
  counted*; it does not separate *counted* from *inferred*. This is divergence D1's residue,
  and it is a smaller and better-defined gap than the one the superseded audit found. No task.
- **A `LIMIT 0` `PROFILE` captures the parallel tier with workers still in flight.** Measured:
  `… LIMIT 0` at threshold 10 renders `ParallelScanProject` with `rows=0, dbhits=0` **and
  `DbHitsKnown=true`** — a **known zero that is not a fact about the workload**. No task.
- **The count-store leaves render `?` where a known `0` may be the better answer.**
  `LabelCountScan` and `AllNodesCountScan` answer from a maintained counter and claim no
  marker, so they render `?`. Whether `?` or `0` is honest for an operator that reads one
  counter is a real question **this sprint did not settle**. The superseded audit had recorded
  them as printing `0` and argued that `0` was defensible; the classification moved in a
  direction it did not anticipate. No task.
- **`columnarExpand` is not independently proved MEASURED.** Its observed arm emits as many
  rows as it walked, so the discriminating comparison was not obtained for it. It is on the
  marker census — a source reading, not a measurement.

### `graph/lpg` ordering claims

- **Three ordering claims are real but ungated.** `LabelCountExact` has the identical seam
  blind spot #2773 fixed for `LabelCountAsOf` — the one-line remedy was **proven to work but
  deliberately not applied**, because it rewrites another task's gate message.
  `LabelCountBound` has no seam at all. `LabelsCountExact` fires the probe with **no test in
  the repository driving it there**. No task.
- **A same-label bitmap clone still costs 38 allocations**, when the churn is on the counted
  label and the correction genuinely runs. #2773 removed the case where the clone was
  *pointless*; it did not remove the case where it is real. No task.

### Gates not run

- **The soak and nightly layers were NOT run for this release.** Under the project's own
  acceptance gates the soak layer is a periodic reliability exercise and explicitly **not** a
  release gate — but it has now gone unrun for a **seventh** consecutive cycle, and nothing
  here claims otherwise.
- **This release carries no production certification of its own.** The most recent was taken at
  the `v0.11.0` commit.
- **No Bolt-driver round trip was performed.** D8 and D9 were audited in
  `bolt/server/plan_meta.go` **source**. `neo4j-go-driver` is not among the pinned clones, so
  the driver-decoder claim behind D8 is carried forward **unconfirmed**.
- **The metrics were not observed firing.** `internal/metrics` is import-restricted, so the
  external audit harness could not install a recording backend. The claim that
  `cypher.stats.qerror` fires on a never-refreshed engine rests on the call path plus the
  measured precondition that `NodeByLabelScan` carries `exact` on an engine that never
  refreshed — observed in 24 of 24 instances. **That is strong, but it is not the metric
  itself.**
- **The Neo4j evidence is from the Community clone**, so it describes the interpreted/slotted
  runtime. The Enterprise pipelined runtime was not examined.

### Still open from before

- **One openCypher divergence ships open, and the TCK is structurally blind to it.** rmp #2675:
  a subquery body's final projection is never translated, so the `COUNT {}` block form returns
  the wrong number — and **zero of 220 feature files contain `COUNT {`**, re-verified for this
  release, so no TCK scenario can catch it. The task remains in the backlog.
