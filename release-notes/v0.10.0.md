# Release Notes — GoGraph v0.10.0

**Date:** 2026-07-25
**Tag:** `v0.10.0`
**Module:** `github.com/FlavioCFOliveira/GoGraph`
**Status:** Pre-1.0 (unstable public API)

---

## Overview

GoGraph v0.10.0 is the thirteenth published release of GoGraph, a Go module
for graph **persistence**, **manipulation**, and — above all — **fast
search**, designed to scale from in-memory graphs to graphs that exceed RAM.

This is a pre-1.0 **MINOR** release, and it is entirely a **Cypher
query-planner and execution-engine** cycle, organised around one enabling
foundation and three optimisation families built on top of it:

- **Planner statistics and cardinality estimation (the foundation).** A new
  exact relationship **count-store** maintains `E(relType)`,
  `D(label, relType, dir)` and `T(labelA, relType, labelB)` in `O(delta)` on
  the commit fan-out, recomputed from the recovered graph at reopen.
  Alongside it, an off-write-path statistics layer (HyperLogLog NDV, exact
  top-k MCV, equi-depth histograms) drives **statistics-backed cardinality
  estimates in `EXPLAIN` / `PROFILE`**.
- **Count-store-gated reordering peepholes.** Result-identical, build-time
  plan rewrites — a min-cardinality multi-label anchor scan, a single-edge
  OUT-only anchor-swap, and a disjoint-scan-component reorder — each gated by
  the exact count-store and a shared order-safety predicate so they deviate
  from the written order only when provably result-identical and never slower.
- **Columnar / vectorised execution deepening.** The column-major `Chunk`
  runtime introduced in v0.9.0 is extended from projection to columnar
  aggregation, `Expand` as a chunk producer, and a columnar hash-join with
  late materialisation, keeping the chunk pipeline unboxed end-to-end through
  scan → expand → filter → aggregation.
- **Automatic intra-query parallelism broadening.** Parallel execution — no
  licence, no opt-in — is broadened from scan/count to `min` / `max` /
  `count` aggregation with a combine that is byte-identical to the serial
  fold, plus an `O(1)` count-pushdown.

## Semantic-versioning rationale

The bump is **MINOR** under [Semantic Versioning](https://semver.org/). Every
change in this release is additive: two net-new packages
(`graph/index/count`, `graph/index/stats`), net-new `cypher` and `cypher/exec`
planner and columnar operators, and net-new `EXPLAIN` / `PROFILE`
observability. The **45 commits** landed since `v0.9.0` were surveyed
(`git log --no-merges v0.9.0..HEAD`, a linear history with no merge commits)
and **no exported identifier was removed or renamed anywhere** — unlike
v0.9.0, which retired the dead `cypher/exec.ParallelScan` operator, this cycle
retires nothing. There is **no breaking change to the documented public-API
surface** (`graph/*`, `search/*`, `store/*`, `ds`, `bench/*` — see
[docs/semver.md](../docs/semver.md)); the only changes under that surface are
the two brand-new `graph/index/*` packages, which add exported identifiers
without touching any existing one.

As a `0.y.z` release the public API nonetheless remains unstable: it may
change without a major-version bump while the module matures toward `1.0.0`.
**Pin the exact version you depend on.**

## Compliance mandates — affirmed

Both compliance guarantees that define the project continue to hold without
regression at this version:

- **100 % openCypher TCK-compliant at the execution level** — every scenario
  in `cypher/tck/features/` passes, with no `failed`, `undefined`, or
  `pending` step. The execution gate stands at **3 897 / 3 897 scenarios**
  and **16 006 / 16 006 steps**, 0 failed, 0 undefined, re-verified by
  `TestTCKExecution` inside the `VERSION=v0.10.0 make release-preflight` gate
  at the release commit. The regression gate
  (`tckExecutionBaseline = 3897` in `cypher/tck/runner_test.go`) is
  unchanged. Every optimisation in this release is either result-identical by
  construction (the columnar operators, the count-pushdown), gated so it fires
  only when provably result-identical (the reordering peepholes),
  display-only (the cardinality estimates), or a byte-identical-to-serial
  parallel combine — and the whole TCK was additionally forced through the
  parallel path (`parallelScanThreshold = 1`) with 3 897 / 3 897 still
  passing.
- **100 % ACID-compliant** — Atomicity, Consistency, Isolation, and
  Durability hold across the in-memory engine and the WAL-backed `store.DB`,
  verified by the deterministic crash-injection battery
  (`internal/crashinject/`) and the WAL recovery tests (`store/wal/`,
  `store/recovery/`). The count-store and the statistics carry **no on-disk
  format, no WAL op, and no checkpoint component** — each is a pure function
  of the recovered graph, recomputed at reopen — so this release adds no new
  persistence format and changes no durability contract. The count-store is
  maintained under the same durable-then-visible `visMu` barrier the
  secondary-index fan-out already uses; the planner reads it (and every
  optimisation reads the graph) inside the query's pinned visibility barrier,
  observing the same committed state the row path does.

The Go toolchain remains **go1.26.5** (unchanged), and `govulncheck ./...`
reports no vulnerabilities.

## Highlights

- **Exact relationship count-store (`#2082`–`#2084`).** A derived,
  non-durable, engine-owned count-store maintains `E(relType)`,
  `D(label, relType, dir)` and `T(labelA, relType, labelB)` exactly, updated
  `O(delta)` on the commit fan-out and recomputed `O(V + E)` at reopen. The
  write path is neutral: `BenchmarkEngWriteAutocommit` allocs/op are identical
  before and after (34 → 34, all samples equal), with only a fixed `+2.36 %`
  B/op from the `O(1)` struct fields — the `#2051` alloc-explosion failure
  mode is provably absent.
- **Planner statistics and cardinality estimates (`#2097`–`#2102`).**
  HyperLogLog NDV (`m = 4096`), exact top-k MCV, and equi-depth histograms
  (`B = 256`, distribution-free `≤ 1/B` selectivity error), built by an
  explicit `RefreshStatistics` scan, now annotate every `EXPLAIN` / `PROFILE`
  operator with an estimated row count and its provenance
  (`exact` / `stats` / `heuristic`). The feature is display-only and, when
  unused, byte-identical on the write path to pre-statistics
  (`BenchmarkEngWriteAutocommit` allocs 34 → 34, B/op flat, `p = 0.182`).
- **Min-cardinality multi-label anchor scan (`#2077`).** `MATCH (n:A:B:C)`
  scans the smallest **exact** label instead of the first syntactic one.
  `BenchmarkMinLabelScanSelective` (a large `:Common` and a small `:Rare`
  label): **≈ 82× faster, ≈ 22× less memory, ≈ 122× fewer allocs**
  (223.6 µs vs 18.4 ms).
- **Single-edge anchor-swap (`#2090`).** For `(a:Hub)<-[:R]-(b:Leaf)`,
  re-rooting the written `DirIn` hub-anchored expand onto `:Leaf` as a
  `DirOut` expand: `BenchmarkAnchorSwapHub` **−92 % time (≈ 12.7×), −99.5 %
  allocs**.
- **Disjoint scan-component reorder (`#2091`).** Building the smaller exact
  node count first: `BenchmarkJoinReorderDisjoint` **−67 % time (≈ 3.1×),
  −83 % B/op**.
- **Columnar aggregation, columnar `Expand`, columnar hash-join (`#2104`–
  `#2106`).** `BenchmarkColumnarAgg` (1M-row group-by): allocs/op **−99.97 %
  (3.15M → 803)**, −43 % time. `BenchmarkExpandFilter` (~64k edges): allocs/op
  **≈ 7 200× fewer (181k → 25)**. `BenchmarkHashJoinDisconnectedEquiJoin`:
  allocs **−22.4 %**.
- **Parallel `min` / `max` / `count` aggregation and `O(1)` count-pushdown
  (`#2111`, `#2113`, `#2115`).** Single-query parallel `min` is **≈ 2.83×**
  at low concurrency and **regression-free at saturation** (conc = 64 parity)
  via a `budget == 1` inline-serial short-circuit; the bare-`count(*)`
  pushdown is **≈ 9 700× (−99.99 %)** — `O(1)` vs `O(N)`.

## What changed

### Planner statistics and cardinality estimation

The enabling work of this release is an **exact relationship count-store**
and a **best-effort statistics layer** that share one structural fact: every
selectivity is `S = C / N`, and GoGraph already maintains exact, always-fresh
population counts, so in every `S` the denominator `N` is exact and only the
numerator is ever approximate.

The **count-store** (`graph/index/count`, wired through `cypher`) maintains
`E(relType)`, `D(label, relType, dir)` and `T(labelA, relType, labelB)`
exactly — reusing the existing label index for `N(label)` — updated `O(delta)`
on the commit fan-out via a transaction-scoped `CountBuffer` flushed inside
the commit's `visMu` barrier after the WAL fsync succeeds, and recomputed
`O(V + E)` from the recovered graph at reopen. It therefore carries no on-disk
format, no WAL op, no checkpoint component, and no new fsync — it cannot
diverge from the graph because it is a pure function of it. The one case where
exact-and-`O(delta)` is unattainable, a label mutation on a high-degree node,
is handled by keeping the enumerable OUT side exact within a bounded
per-commit budget and marking the un-enumerable IN side **stale**; a stale
cell yields an estimate veto (never a wrong exact) and self-heals at reopen.
`N` and `E` are never affected and stay exact under every mutation. See
[docs/count-store-design.md](../docs/count-store-design.md).

The **statistics layer** (`graph/index/stats`) is built off the write path by
an explicit `RefreshStatistics` full scan, generation-stamped and
staleness-gated: **HyperLogLog NDV** (`m = 4096`, ≈ 1.6 % relative error, never
sampled — Charikar et al. PODS'00 prove any sampler is unbounded), **exact
top-k MCV**, and **equi-depth histograms** (`B = 256`, distribution-free
`≤ 1/B` selectivity error, with heavy MCV values isolated into singleton
buckets so the bound survives skew). The collector is **lazy** (nil until the
first `RefreshStatistics`), so a statistics-free engine constructs nothing and
its write path is byte-identical to pre-statistics; with statistics active,
maintenance is an `O(1)` atomic delta per tracked property. See
[docs/statistics-design.md](../docs/statistics-design.md).

Both feed **statistics-backed cardinality estimates in `EXPLAIN` /
`PROFILE`**: each operator is annotated with an estimated row count and its
provenance (`exact` from the count-store's `N` / `E` / `D`, `stats` from NDV /
histograms / MCV, or `heuristic`). This is **display-only** — a differential
test proves query results are identical with and without statistics
populated — and no plan-choice or execution behaviour depends on it. The
range-index seek stays exact-count-gated (it was proven that statistics do not
widen it), so the statistics' role is observability plus a documented
foundation for a future margin-gated mode.

### Count-store-gated reordering peepholes

Under the project's absolute no-regression mandate, a full join-order search
collapses to a small set of peepholes whose every cost input is a single exact
count-store entry. Each is a build-time plan rewrite, gated by two-sided
trustworthiness (both the candidate and the baseline cost inputs must be exact
and non-dirty, sampled from one snapshot) and by the shared `SuppressReorder`
order-safety predicate, so it deviates from the written order only when
provably result-identical and never slower:

- **Min-cardinality multi-label anchor scan (`#2077`).** `MATCH (n:A:B:C)`
  anchors on the label with the smallest exact bitmap cardinality, keeping the
  rest as a residual `Filter`. A label conjunction is a commutative `AND` and
  `min|Lᵢ| ≤ |L0|`, so the plan never does more work than the default.
- **Single-edge anchor-swap, OUT-only (`#2089`, `#2090`).** For
  `(a:A)-[:R]->(b:B)`, the anchor is chosen to minimise examined edges via the
  count-store degree `D(label, relType, dir)` under the cost `c_s·N + c_e·D`.
  It flips a written `DirIn` expand to `DirOut`; reverse-introducing swaps are
  vetoed, because a `DirIn` traversal costs work proportional to the source
  out-degree, invisible to the aggregate degree.
- **Disjoint scan-component reorder (`#2091`).** For a nested-loop join of
  disjoint single-scan components (no equi-join), the smaller exact node count
  is built as the outer side.
- **Order-safety predicate (`#2092`).** A shared `SuppressReorder` guard
  vetoes any reorder a bare `LIMIT` / `SKIP`, an arrival-order aggregation, or
  `collect()` would make observable.

`EXPLAIN` / `PROFILE` now render the chosen scan label and expand direction so
each reorder is visible, and every peephole is gated by an
`EngineOptions.Disable*` flag and proven byte-identical ON vs OFF by a
differential harness. See [docs/reordering-design.md](../docs/reordering-design.md).

### Columnar / vectorised execution deepening

The column-major `Chunk` runtime introduced in v0.9.0 — the late-materialised
columnar execution model that neither Neo4j (a row-batch morsel) nor Memgraph
(row-at-a-time) has — is extended from projection to the operators that
dominate analytic Cypher. The governing rule is unchanged: boxing is removed
only on the contiguous `ChunkProducer` suffix measured from the sink, so each
columnar operator is a drop-in with a row-mode fallback, is wired only for its
qualifying shape, and is differential-tested byte-identical columnar-ON vs
row-OFF.

- **Columnar aggregation (`#2104`).** `SUM` / `COUNT` / `MIN` / `MAX` and
  their `GROUP BY` forms run over typed chunk columns with an SoA scatter-add.
- **`Expand` as a `ChunkProducer` (`#2106`).** Traversal output is produced
  column-major, with a columnar filter applied over it.
- **Columnar hash-join with late materialisation (`#2105`).** A disconnected
  equi-join keeps its probe and build columns unboxed until the join emits.

Exact int/float semantics are preserved throughout (CIP2016-06-14: exact
`int64` `SUM`, `int 1 ≡ float 1.0` for grouping and join keys, `int 2^53 + 1
≠ float 2^53`). Traversal itself and entity / `Path` columns stay boxed
(pointer-rich, not scan-heavy). See
[docs/columnar-deepening-design.md](../docs/columnar-deepening-design.md).

### Automatic intra-query parallelism broadening

Automatic (no-licence, no opt-in) morsel-parallelism — engaged above
`parallelScanThreshold` and bounded by the `ParallelGovernor`, which keeps
total workers near `GOMAXPROCS` across concurrent queries — is broadened from
scan/count to aggregation:

- **Parallel `min` / `max` (`#2111`).** Each worker folds its morsels and the
  partials are merged with a **position-carrying combine that is
  byte-identical to the serial left-fold**, including the tie representative
  (int/float, ±0, `NaN`). Float `sum` / `avg`, int `sum`, `collect`,
  `percentile`, and `stdev` stay serial permanently — no deterministic,
  byte-identical combine exists for them under the multiset-plus-value-
  representation determinism obligation.
- **`O(1)` count-pushdown (`#2113`).** A bare group-by-less `count(*)` /
  `count(v)` over a full node scan reads the maintained live count in `O(1)`
  instead of scanning `O(N)`.
- **`budget == 1` inline-serial short-circuit (`#2115`).** When the governor
  hands a query a one-worker budget — the steady state under high
  concurrency — the aggregate runs that single worker synchronously on the
  calling goroutine (no goroutine, channel, context, or `pprof.Do`), keeping
  the saturated regime regression-free while preserving byte-identical output.

Intra-query parallelism is idle-core-bound: the win is at low concurrency, and
the governor correctly throttles it to neutral under load. Parallel `Expand`
(`#2112`) was benched and **deferred** — a single-query 4–5× that is
idle-core-bound, so no win under GoGraph's high-concurrency production
regime — with the measured evidence recorded. See
[docs/parallelism-broadening-design.md](../docs/parallelism-broadening-design.md).

The example harnesses under `examples/` — which the module neither imports nor
depends on — were extended to exercise and observe the new engine surface:
`25_software_house_api` drives the min-label anchor scan (`#2117`),
`31_metrics_observability` observes the count-store (`#2118`), and
`26_social_scale_bench` gains cardinality-estimate, columnar-operator and
intra-query-parallelism observations (`#2120`, `#2121`, `#2122`) plus a

`13_network_reliability` times GoGraph's own library max-flow (`#2074`), and
the `17_transactional_log` double-entry check is now a real reconciliation
invariant (`#2075`).

## Upgrade notes

- **No migration required.** Stores written by earlier releases open without
  conversion. The count-store and the statistics are derived, non-durable
  structures recomputed at reopen; they add no on-disk format and change no
  file layout.
- **No behaviour change for existing queries.** The reordering peepholes are
  result-identical and gated to fire only when provably so; the columnar
  operators and the count-pushdown are result-identical by construction; the
  parallel aggregation uses a byte-identical-to-serial combine. A query that
  the optimiser declines executes exactly as before.
- **`EXPLAIN` / `PROFILE` output is richer.** Operators now display an
  estimated row count with its provenance, the chosen scan label for a
  reordered multi-label or disjoint pattern, and the chosen expand direction
  for an anchor-swap. If you parse `EXPLAIN` / `PROFILE` text, expect these
  additional annotations.
- **Statistics are opt-in to populate.** The planner statistics layer is nil
  until you call `RefreshStatistics`; until then, cardinality estimates draw
  on the always-exact count-store (`N` / `E` / `D`) and heuristics. Populating
  statistics affects only estimate display, never results.
- **New optimisations can be disabled.** Each reordering peephole and the
  parallel/columnar paths are individually gated by an `EngineOptions` flag
  (for example `DisableMinLabelScan`, `DisableParallelScan`), primarily for
  differential testing; the features are enabled by default.
- **Pin the exact version.** As a `0.y.z` release the public API may still
  change without a major bump.

## Benchmark evidence summary

This release's performance work is entirely in the **Cypher query planner and
execution engine**; the headline guard-band set (the `search` /
`search/centrality` algorithms) is not on any changed path, and its
allocation columns are **identical to `v0.9.0`** (`Dijkstra_PostWarmup` and
`BFSDirectionOpt_PowerLaw` allocate zero bytes per call; `Dijkstra_Large`,
`Yen_K100`, and `Brandes_RandomGraph` match their prior allocation
footprints). The planner and execution-engine wins are substantial and each
was measured first-hand at the change that landed it (see the per-change
records in [docs/benchmarks/history/LEDGER.md](../docs/benchmarks/history/LEDGER.md),
rows 0020–0025):

- **Min-cardinality multi-label anchor scan** (`BenchmarkMinLabelScanSelective`):
  ≈ **82× faster**, ≈ 22× less memory, ≈ 122× fewer allocs.
- **Single-edge anchor-swap** (`BenchmarkAnchorSwapHub`): **−92 % time**
  (≈ 12.7×), −99.5 % allocs.
- **Disjoint scan-component reorder** (`BenchmarkJoinReorderDisjoint`):
  **−67 % time** (≈ 3.1×), −83 % B/op.
- **Columnar aggregation** (`BenchmarkColumnarAgg`, 1M-row group-by): allocs
  **−99.97 %** (3.15M → 803), −43 % time.
- **Columnar filter-over-`Expand`** (`BenchmarkExpandFilter`, ~64k edges):
  allocs **≈ 7 200× fewer** (181k → 25).
- **Columnar hash-join** (`BenchmarkHashJoinDisconnectedEquiJoin`): allocs
  **−22.4 %**, sec/op −5.7 %.
- **Parallel `min` aggregation** (`BenchmarkParallelAggregate_Concurrent`):
  ≈ **2.83×** single-query (conc = 1), **parity at conc = 64** (no
  regression under saturation).
- **`O(1)` count-pushdown** (`BenchmarkCountPushdown_O1`): ≈ **9 700×**
  (−99.99 %), independent of `N`.
- **Write-path neutrality** (`BenchmarkEngWriteAutocommit`): the count-store
  and statistics leave allocs/op unchanged (34 → 34); the statistics collector
  is byte-identical to pre-statistics when unused.

The authoritative measured figures — the freshly-measured headline guard-band
set, the planner/execution win table, and the parallel-aggregation
concurrency load test — are recorded in
[docs/benchmarks/v0.10.0.md](../docs/benchmarks/v0.10.0.md), measured on the
run environment documented there. Consult that document for the per-benchmark
