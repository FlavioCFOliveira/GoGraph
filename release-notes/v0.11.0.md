**Module path:** `github.com/FlavioCFOliveira/GoGraph`

## Overview

This is the largest release the project has cut: **505 commits** — 63 features,
83 fixes, 61 performance changes — of which **31 are breaking**. Sprints 311–315,
326, 327, 329 (six rounds), 334–336 and 338–343 merged in this window.

Where `v0.10.0` was **purely additive** — it removed no exported identifier and no
behaviour — `v0.11.0` is the opposite. It replaces the module's entire
concurrency-control mechanism, and the API changes that follow from that are not
optional. **Read [Upgrade notes](#upgrade-notes) before you bump the dependency.**

Two things define the release.

**Concurrency control became MVCC and nothing else.** At `v0.10.0` concurrency
control was *exclusion*: a single-writer semaphore in `store/txn`, an engine writer
mutex, and `Graph.View`, the read barrier. All three are gone. What replaced them is
a transaction clock with shared commit records, version chains on every store, a
contiguous commit frontier, optimistic write–write conflict detection with a
retriable error, a bounded background vacuum, and an MVCC clock derived from the WAL
at recovery. The consequence a user feels is on the write side: **durable write
throughput is now monotonic in writer count and scales 415× from 1 to 1024
writers**, where `v0.10.0` delivered the same throughput at 32 writers as at one.

**The planner gained six new access paths**, several asymptotic rather than
constant-factor: a prefix range seek for `STARTS WITH`, multi-label conjunction by
Roaring bitmap intersection, btree seek for string and numeric equality,
destination-ordered CSR neighbour runs probed in `O(log d)`, an index nested-loop
join, and a fused cyclic expand driven by multi-way leapfrog intersection.

**And one thing is worse.** A plan-choice defect regressed a selective multi-label
query **≈21.6×** in the default configuration. It is confirmed open at this tag,
filed as rmp #2431, and documented in [Known issues](#known-issues) rather than
omitted.

## Semantic-versioning rationale

`v0.11.0` is a pre-1.0 **MINOR** release. Under this project's
[SemVer policy](../docs/semver.md), pre-1.0 the minor digit absorbs breaking
changes to the exported Go API, so the 31 breaking changes in this release do not
force a major bump while the module is on the `0.x` line.

**Why this is not `v1.0.0`.** Three of the four documented `1.0.0` gates are now
met — execution-level TCK is at **100 %** against a **≥ 95 %** requirement, every
`T-` divergence is resolved, and the full local gate is green at the release
commit. **Gate 4 is not met**: it requires the soak report in `soak-artefacts/` to
reflect a run against the release commit, and those artefacts are from
**2026-05-30 at commit `b5453b9`** — more than 500 commits behind this tag. The
whole-tree soak layer has now gone unrun for four consecutive cycles. That gate,
together with the unmeasured items in [the certification envelope](#what-is-not-established),
is what stands between this release and `1.0.0`.

## Highlights

### Writes stopped being serial

Measured at this tag on the published ladder (`store/txn/write_scaling_bench_test.go`,
median of 6):

| Writers | Store API | Scaling | Cypher engine | Scaling | commits/fsync |
|--------:|----------:|--------:|--------------:|--------:|--------------:|
| 1 | 268.4 ops/s | 1.00× | 271.0 ops/s | 1.00× | 1.00 |
| 8 | 1,098.5 | 4.09× | 1,060.0 | 3.91× | 4.08 |
| 64 | 8,321.5 | 31.00× | 8,253.5 | 30.46× | 31.50 |
| 256 | 32,234.0 | 120.07× | 30,804.0 | 113.67× | 121.20 |
| **1024** | **111,483.0** | **415.28×** | **115,300.5** | **425.46×** | **422.05** |

**The mechanism is proven arithmetically:** the scaling factor equals
`commits/fsync` at every level, so the gain is group-commit fsync amortisation and
nothing else. The single-writer rate is this device's single-writer fsync rate and
is **unchanged** from `v0.10.0` — nothing was traded for the scaling.

This sweep is also the discharge of a standing debt: the last **three** production
certifications each recorded the store-level write-scaling sweep as unrun.

### The largest read gain is on a shape the benchmarks could not see

A parameterised index seek **did not seek**. Both revisions plan
`NodeByIndexSeek` and return identical rows, yet `v0.10.0` spent 41 ns per node at
5 000 nodes and 44 ns at 20 000 — its cost was `O(label population)`. It was a scan
wearing a seek's name.

| Shape | Fixture | v0.10.0 | v0.11.0 | Δ |
|---|---:|---:|---:|---:|
| point lookup on indexed `id` | 5 000 nodes | 204,673 ns | 3,171 ns | **64.5×** |
| point lookup on indexed `id` | 20 000 nodes | 888,475 ns | 3,325 ns | **267×** |
| 2-hop from indexed anchor | 20 000 nodes | 1,938,232 ns | 5,893 ns | **329×** |

**Why no benchmark caught it:** every benchmark in `bench/cypher_ldbc` passes
literal keys in the query text, and literals already seeked at `v0.10.0`. So the
flagship read suite measured **−28 %** for this cycle while the same engine improved
**50–65×** on the parameterised form that every Bolt client, prepared statement and
plan-cache hit actually sends. Both numbers are true; only one is what a deployed
application experiences.

A separate fix in the same family: **a string parameter now seeks the index exactly
as the identical literal does** (rmp #2414) — previously a parameter planned a full
label scan where the literal seeked.

### New planner access paths

| Access path | Gain | Note |
|---|---|---|
| Prefix range seek for `STARTS WITH` | **385×** | Byte successor, not code-point increment |
| Multi-label conjunction by Roaring bitmap AND | **2909×** | Residual label `Filter` dropped |
| btree seek for string equality | **849×** at 20 000 nodes | Cells that already worked unchanged |
| Index nested-loop join | **55×–258×** | Behind a measured cost gate |
| Hash join admitted for writing statements | **62.4×** | Build side proven pinned |
| Bidirectional `shortestPath`, typed/`DirIn`/`DirBoth` | **10.8×–32.8×** | |
| Destination-ordered CSR, probed `O(log d)` | **−7.37 %** power law | Quote the power law, not the geomean |
| `Expand(Into)` bound-destination seek | **−77.69 %** at degree 64 | Gain grows with degree |
| Symmetric anchor swap | **−99.69 %** at hub degree 40 000 | |
| Degree-answerable `COUNT` / `size()` | `COUNT { … } > 0` **88×** | O(1) degree primitive |
| Fused cyclic expand (`ExpandIntersect`) | geomean **−54.24 %** | **OPT-IN — off by default** |

**Two of these need reading carefully.** The destination-ordered CSR's quotable
figure is the **power-law −7.37 %**, not the −31.77 % geomean or the −81.76 % at
controlled degree 4096 — those are dominated by synthetic high-degree fixtures, and
RMAT overstates the power-law result by **3.9×**. And its gain is paid for on the
write path: a 2.5–34× more expensive CSR build and a +16.52 % checkpoint.

**The fused cyclic expand is OPT-IN and OFF by default.** Set
`EngineOptions.EnableCyclicIntersect` to get it. The polarity is deliberately
positive: the operator is new rather than a peephole, and the openCypher TCK
contains no directed cycle over three or more distinct node variables, so **the TCK
cannot gate it at all**. Sprint 315 also belongs in this release as a *negative*
result — the general worst-case-optimal join was rejected on measurement and only
this narrow fusion kept.

### Correctness capability that no ratio expresses

- **Snapshot isolation with conflict detection.** At `v0.10.0`, concurrent
  read-modify-write **lost 46 % of its committed updates**: four writers issuing 100
  `SET a.bal = a.bal + 1` statements each, every refusal retried, reported 400
  successes and left the property at **216**. `v0.11.0` detects write–write conflicts
  across seven stores and returns a retriable error.
- **Read-your-own-writes**, through `cypher.Session` and `lpg.Session` — and it is
  carried through **Bolt**, so driver clients get it per connection. Measured cost:
  none.
- **Concurrent checkpointing** at a transactional instant, instead of excluding
  writers.
- **The official `neo4j-go-driver` can now materialise graph entities at all.**
  `Node`, `Relationship` and `Path` were being sent as PackStream maps where Bolt
  requires STRUCTURES, so the driver could not produce `dbtype.Node`,
  `dbtype.Relationship` or `dbtype.Path`. Pre-Bolt-5 arities are honoured too.
- **`PROFILE` with per-operator db-hits** and a faithful physical-plan `EXPLAIN` —
  the module can now be asked *why* a query was slow. `Engine.Explain` previously
  rendered the logical IR and re-derived physical decisions, so a reader could be
  shown `O(n·m)` where `O(n+m)` ran.
- **Bulk import** — `store/bulkimport.Publish` and `cmd/gograph-import`: 20 000
  nodes and 200 000 edges in **233 ms** (0.86 M edges/s), ~**690×** the Cypher route
  on the same task. **The trade must be stated with the number:** it writes no WAL,
  is not a transaction, cannot be rolled back, requires an empty directory, and is
  concurrent with nothing.
- **A HIGH-severity default closed:** both engine-wide memory ceilings resolved to
  **unlimited** whenever `GOMEMLIMIT` was unset, which is the Go runtime's default
  state.

## Performance — the honest account

Full detail in [`docs/benchmarks/v0.11.0.md`](../docs/benchmarks/v0.11.0.md); the
end-to-end two-revision comparison is
[`release-delta-v0.10.0-to-head-2026-08-10.md`](../docs/benchmarks/release-delta-v0.10.0-to-head-2026-08-10.md),
which is measured five sprints behind this tag and is annotated accordingly.

### What got faster

| Axis | Result |
|---|---|
| Durable write scaling, 1 → 1024 writers | **415×** (store API), **425×** (Cypher) — monotonic |
| Parameterised point lookup | **50–65×**, up to 267× at 20 000 nodes |
| LDBC Interactive Complex, 15 queries | geomean 25.70 → 18.44 µs (**−28.24 %**) |
| Bulk delete, sixth seed-and-wipe cycle | 4.622 s → **77.2 ms**; `DETACH DELETE` **22.2×**; a 90 000-node statement 15.97 s → **375.6 ms** |
| Memory per relationship | **−2.74×** |
| Bolt CPU on a 1000-row result | **−6.03×** |
| Autocommit write, engine level | **−80.22 %** (5.714 → 1.130 µs), −38 % allocations |
| Commit allocations | 56 → **43** per `CREATE` (−23.2 %) |
| Graph algorithms | triangle counting −38.16 %, Hopcroft–Karp −16.09 %, Prim −8.38 % |
| Steady-state heap | +1.3 % heap in use, **−10.6 % mallocs** |

### What got slower — measured, not minimised

| Axis | Cost |
|---|---|
| **Selective multi-label query, default config** | **≈21.6× slower** — a defect, see [Known issues](#known-issues) |
| Graph iteration and bulk write, 7 independent benchmarks | **+7–16 %** |
| WAL recovery, 15 000 ops | 5.680 → 8.561 ms (**1.51× slower**) |
| On-disk bytes per node | 278 → 286 (**+2.9 %**) — the commit timestamp |
| `DIMACS_SF1_SSSP` tail latency | p95 338.9 → 442.6 µs (**+30.58 %**) |
| Headline guard-band set | **+1.47 % to +4.02 %** on time; every allocation count identical |
| Uncontended hot-key intern | 7.68 → 8.782 ns (**+14.35 %**) |
| Constrained write throughput | **−3 to −10 %** (rmp #2425, open) |
| CSR build / checkpoint | 2.5–34× build, **+16.52 %** checkpoint |
| Relationship creation | **+1.92 %** (the in-edge index that fixed bulk delete) |

The recovery and iteration costs are **the coherent price of MVCC and are bounded**:
recovery is a one-off, and the iteration tax is a few percent of a read. The
`WriteCSV` case is the cleanest evidence that it is real — its B/op and allocs/op are
**byte-identical** across revisions while its time rose 15.72 %, which is pure CPU on
the read path. Attribution of these to MVCC specifically is **inference, not proof**:
the MVCC on/off switch was deliberately removed, so no within-revision A/B exists.

## Known issues

### rmp #2431 — the parallel-scan tier outranks a selective label anchor (OPEN, severity 7)

On a fixture of 100 000 `:Common` nodes of which 1 000 also carry `:Rare`,
`MATCH (n:Common:Rare) RETURN n.k` regressed from **230.3 µs at `v0.10.0` to
4.98 ms** — **≈21.6×** — with 131× more allocations.
`BenchmarkMinLabelScanSelective_MinLabel` is now **slower than its own
`_FirstLabel` control**, which is the relationship its name asserts.

Attributed at this tag by sweeping `cypher.EngineOptions`, **asserting 1 000 rows in
every arm**, best of 30:

| Configuration | best | Chosen plan |
|---|---:|---|
| **default** | **4.087 ms** | `Project / ParallelScanProject` |
| `DisableParallelScan` | **0.194 ms** | `ColumnarProject / Filter / NodeByLabelScan [Rare]` |
| `DisableBitmapIntersection` | 4.078 ms | unchanged — not implicated |
| `DisableMinLabelScan` (legacy) | 3.308 ms | `NodeByLabelScan [Common]` |

**The min-cardinality anchor still works** — at 0.194 ms it is *faster* than
`v0.10.0` — **it is simply never chosen**, and the parallel-scan plan is worse than
even the legacy plan the anchor was built to replace. This is a gate admitting a plan
it should reject, not a trade-off.

**Workaround:** set `cypher.EngineOptions.DisableParallelScan` if your workload is
dominated by selective multi-label patterns. Note that this also disables
intra-query parallelism for label scans generally, which is a real loss on
analytical shapes — measure both ways for your workload.

| id | severity | issue |
|---|---|---|

| **#2404** | 6/2 | Cypher's synthetic string node key costs **44.55 B/node** for an identity it never exposes. |
| **#2405** | 7/3 | A per-node record versus three sharded hash maps costing 2.2–2.4× their payload. An architecture decision, deliberately left to the user. |
| **#2407** | 4/3 | Peak memory during node growth is unmeasured and exceeds steady state: 64 shard maps rehash together. |

### Behavioural changes that are not defects but will surprise

- **`MERGE` is no longer idempotent under concurrency without a `UNIQUE`
  constraint.** With nothing serialising writers, two concurrent `MERGE` statements on
  the same pattern can both find no match and both create — measured at **eight
  duplicates from eight writers**. This is inherent to MVCC and matches Neo4j, which
  requires a uniqueness constraint for the same reason. **With a `UNIQUE` constraint
  the duplicates collapse to exactly one.** If you rely on `MERGE` being idempotent
  under concurrency, declare the constraint.
- **A write–write collision is refused at the conflicting statement, not at
  `COMMIT`.** `ExplicitTx.Exec` returns an error wrapping
  `mvcc.ErrSerializationConflict`. Over Bolt it maps to a `TransientError`, so the
  official driver's managed transactions retry it automatically; callers driving
  explicit transactions by hand should roll back and retry.
- **An open transaction pins the reclamation horizon.** No version it can still reach
  is freed while it lives. This replaces the old cost (an open write transaction
  blocked every other writer in the process) with a resource cost.
  `DefaultMaxTxIdleTime` (5 s) bounds the exposure over Bolt.

## Upgrade notes

### Breaking API changes

| Removed / changed | Migration |
|---|---|
| `Graph.DisableMVCC`, `Graph.EnableMVCC`, `Graph.MVCCEnabled` | **Delete the calls.** MVCC is armed by `lpg.New` and cannot be disarmed; there is no replacement and none is needed. |
| `Graph.View` | Reads no longer need a barrier. `LockBarrier`/`UnlockBarrier`/`ApplyInsideLocked` remain for genuine exclusive access, but **must not** be used to hold a transaction — `ApplyInsideLockedTx` resolves from the graph's *ambient* slot, which two concurrent transactions overwrite. Use `Graph.BeginVersionedTx` / `ApplyInVersionedTx` / `EndVersionedTx`. |
| `wal.Writer.AppendRun` | Now returns `(int64, error)` — the run's own end offset. |
| `wal.Writer.SyncGroup` | Now takes `target int64`, the offset from `AppendRun`. The offset cannot be recovered after the fact: the writer's accepted offset is shared, so a committer reading it later was asking about somebody else's frames. **`Writer.SyncBuffered` is for callers with nothing of their own to acknowledge and must never be used to decide a commit's fate.** |
| `MVCCStats.ActiveReaders` (field) | → `ActiveSnapshots`. It counted writers too, since writers hold a snapshot. `ActiveReaders()` is now a derived *method* excluding writers. |
| `MVCCStats.OldestReaderAge()` | → `OldestSnapshotAge()` |
| `MVCCStats.UnregisteredReaders` | → `UnregisteredSnapshots` |
| `AdjList.Reclaim` | Now takes a `*mvcc.DepthHist`. |
| `AdjList.BeginCommit`, `Tx.CommitWALOnly` | Removed. |
| `internal/ctxlock` | Retired; the MVCC substrate re-establishes what it guarded. |

### Metrics series renamed

| Old | New |
|---|---|
| `lpg.mvcc.readers.unregistered` | `lpg.mvcc.snapshots.unregistered` |
| `lpg.mvcc.oldest_reader_age` | `lpg.mvcc.oldest_snapshot_age` |

Per-store conflict series now use underscored store names. **Update dashboard
queries.**

### On-disk format

**Snapshot `labels.bin` bumps 1 → 2.** The edge record gains a `Slot` field. This
closes a durability gap rather than adding a feature: a committed relationship
*type* did not survive a checkpoint, because `labels.bin` stored
`EdgeLabelEntry{Src, Dst, StringIdx}` with no slot ordinal, so parallel edges folded
into one key on disk, and the adjacency label column was never persisted at all —
only reconstructed by replaying per-pair `SetEdgeLabel`.

The snapshot manifest stays at version **3** and the WAL frame at **1**, so an
existing store opens without migration.

### Changed default

**`bolt/server.DefaultMaxOpenTxPerPrincipal` rises from 16 to 2048.** A single
principal could not otherwise reach the concurrency levels this module publishes
through explicit transactions. Because a connection holds at most one open
transaction and `MaxConnections` defaults to 1024, this quota can no longer bind
under the default configuration — the connection ceiling is what bounds the
resource. **If you relied on the previous tight bound, set
`Options.MaxOpenTxPerPrincipal` explicitly.**

## What is not established

The production certification is granted **within an envelope**, and the envelope is
part of the verdict rather than a footnote to it. Restated from
[`docs/certification-2026-08-13.md`](../docs/certification-2026-08-13.md) §5:

1. **Latency percentiles at the published concurrency levels were not measured.**
   Throughput is; p50/p99 at 1/8/64/256/1024 is not. Unmet for three consecutive
   certifications.
2. **The whole-tree soak layer was not run** — now four consecutive cycles. The
   artefacts in `soak-artefacts/` are from 2026-05-30 at commit `b5453b9`.
3. **No container was ever run.** rmp #2421 derives the engine-wide ceilings from a
   cgroup limit and is unit-tested against injected limits, but the cgroup read paths
   have never executed: the certification host is `darwin/arm64` and has no cgroup
   filesystem.
4. **Single host, single architecture** — Apple M4, 10 cores, `darwin/arm64`. No
   Linux, no NUMA, no multi-socket.
5. **rmp #2423's sibling rewrites are fixed as LATENT, not demonstrated.** Only the
   hash-equality shape reproduced; the range, prefix, numeric-equality and key-set
   shapes are guarded on the strength of a code reading plus a control that the seeks
   still fire — not on a reproduction.
6. **The memory findings are untouched** — rmp #2404, #2405, #2407.
7. **rmp #2366's write-contention criterion is not discharged.** The change's
   direction is favourable by construction, but "favourable by construction" is
   exactly the kind of claim this project requires to be measured.
8. **Attribution of the iteration costs to MVCC is inference, not proof** — the
   on/off switch was removed, so no within-revision A/B exists.

The honest reading of this cycle is not "the module is now correct" but **"this
module rewards being measured, and the measurements are not exhausted"**: three of
the four defects closed in the final certification were found *by* it rather than
inherited by it, and two of those were found by fixing another defect or by running
an arm a criterion demanded.
