## Read this first

**`v0.14.1` can tell you it did something it did not do.** Every fix in this release is an
instance of one defect: the effect GoGraph *reported* was not the effect GoGraph *applied*.
Two of them lose data silently.

1. **A `SET` whose value is a node, a relationship or a path is discarded, and the statement
   reports success** (#2816). On the REPLACE forms — `SET n = {…}`, `SET n += {…}` — the
   discarded entry still clears the node's existing keys first, so **`SET a = {other: b}`
   answers `ok` with `propertiesRemoved=1` and leaves the node with no properties at all.**
   If you write a property from another bound entity, you have been losing data without an
   error. This is the reason to upgrade.
2. **An undirected `SET` over a reciprocal relationship pair writes only one of the two**
   (#2817). `MATCH (a)-[r:R]-(b) SET r.v = $v` over a pair that exists in both directions
   reports two property writes and performs one: one edge is stamped twice, the other never.
   The count was right; the write was missing.
3. **A statement that failed and rolled back still reports the counters for the work it undid**
   (#2823), and **`DROP INDEX … IF EXISTS` reports a removal it did not perform** (#2818). If
   you drive schema changes or reconciliation from reported counters, they have been lying to
   you in both directions.

**There is nothing to migrate.** No on-disk format changed, no exported identifier changed, and
a store written by `v0.14.1` opens unchanged. The upgrade is a version bump.

**One cost is published rather than buried:** the fix for #2818 adds an existence read that
costs **+115 ns and +2 allocations** on an absorbed `DROP INDEX … IF EXISTS`. It is measured,
it is real, and it is set out in full under [*Measured results*](#measured-results).

Its subject is reporting integrity. Sprint 361's macro objective was to *resolve the defects

## Semantic-versioning rationale

**`v0.14.2` is a PATCH, and this time by the rule rather than by decision.**

**The exported API is unchanged.** Five functions were added and **all five are unexported** —
`relStorageDirection`, `isEntityPropertyValue`, `exprValueIsEntity`, `errEntityPropertyValue`
and `dropIndexCounter`. **No exported identifier was added, removed or re-signed; no exported
struct gained a field; no exported constant changed value.** Under
[`docs/semver.md`](../docs/semver.md) a new exported identifier is the MINOR trigger, and there
is not one.

**No change is marked breaking** — no commit in the window carries a `BREAKING CHANGE` footer
or a `!` subject, verified over the full commit bodies rather than the subjects alone.

This is the opposite situation to `v0.14.1`, and the contrast is worth stating because it
changes what the number promises. `v0.14.1` shipped a genuine MINOR surface — 31 new exported
identifiers and four exported constants that changed value — as a PATCH **by explicit
decision**, so its number under-described it and its *Changed* section had to be read as the
checklist a MINOR bump would have signalled. **`v0.14.2` carries no such caveat.** Nothing in
the API surface moved, so the PATCH number means exactly what Semantic Versioning says it
means.

**What does change is behaviour, and every change replaces a wrong answer with a right one.**
Three of them are observable to a caller and are itemised under
[*Behaviour a caller can observe*](#behaviour-a-caller-can-observe--the-compatibility-surface).
A statement that previously succeeded while silently discarding a value now returns an error;
that is a compatibility surface, and it is treated as one below rather than waved past as
"just a fix".

**Pre-1.0 stability.** This is a `0.y.z` release: the public Go API may change without a
major-version bump until `1.0.0`. Pin the exact version you depend on.

## Compliance mandates

- **100 % openCypher TCK-compliant at the execution level** — **3 897 / 3 897 scenarios**,
  against `const tckExecutionBaseline = 3897` in `cypher/tck/runner_test.go`, which is
  untouched. **No `.feature` file changed in this window**, so the scenario population is the
  one `v0.14.1` was measured against. This release **preserves** the compliance; it does not
  extend it.
- **The TCK corpus decided one of the fixes.** #2823's corrected behaviour was not chosen from
  intuition. **The specification's own corpus never asks for counters from a statement that
  raised.** Of the 1 615 scenario blocks in `cypher/tck/features/`, **192 carry a "should be
  raised" step and 1 423 carry a side-effect assertion, and the intersection is empty.**

  The 1 423 counts **both** forms the TCK uses to assert about side effects, because both are
  assertions: **244** state them as an explicit `the side effects should be:` table, and
  **1 179** use `no side effects`, which asserts just as positively that the statement changed
  nothing. They partition cleanly — 244 + 1 179 = 1 423 — so no block carries both forms.
  Counting only the explicit-table form would understate the evidence by a factor of six and
  leave a reader properly asking what the other 1 179 do.

  The same holds on the executed population: those blocks expand to the 3 897 scenarios the
  baseline counts, of which 695 raise and 3 202 assert side effects, and **0 do both**. Two
  further sources agree: a Bolt `FAILURE` message carries no stats field, and the reference
  driver returns no summary when the query failed.
- **100 % ACID-compliant.** #2816 and #2817 are Consistency failures in the sense that reaches
  a caller: a statement that reports an effect it did not apply leaves the caller's model of
  the graph disagreeing with the graph. #2823 closes a result that described state a rollback
  had already removed.
- **No durability path changed in this window.** `store/wal`, `store/recovery`,
  `store/checkpoint`, `store/snapshot` and `store/txn` are byte-identical to `v0.14.1`
  (`git diff --name-only v0.14.1..92c47fda -- store/` is empty). #2818 alters a **counter**,
  never a WAL frame: nothing was ever written on the absorbed `IF EXISTS` path, and nothing is
  written now.
- **Extreme-concurrency and ultra-efficiency mandates.** No concurrency contract changed. The
  efficiency mandate is where this release pays something rather than saves it, and the price
  is measured and published below rather than asserted away.

## Highlights

### A `SET` could discard your value and destroy the node's other properties

`isStorableProperty` rejected only maps. A node-, relationship- or path-valued property
therefore came back `ok=false`, and **five separate write paths each read that as "no value was
produced" and moved on** — no error, no warning, a success reported to the caller.

**The defect was wider than it was reported.** The report described a dropped value. The root
cause showed that on the REPLACE forms the dropped entry *still cleared the existing keys
first*, so the statement did not merely fail to write — it **removed properties the caller never
asked it to remove**:

```cypher
MATCH (a:N {id: 1}), (b:N {id: 2})
SET a = {other: b}
```

At `v0.14.1` this answers `ok`, reports `propertiesRemoved=1`, and leaves `a` **with no
properties at all**. At `v0.14.2` it raises `InvalidPropertyType` and `a` is untouched.

All five sites now raise `InvalidPropertyType`. Gated by
`cypher/set_entity_property_value_test.go`.

### An undirected `SET` wrote one of the two relationships it reported

`resolveRelBinding` keyed the edge-property mutation on the **row's traversal order**. The
reverse hop of an undirected pattern is the swap of the edge's **storage order**, so both rows
of `MATCH (a)-[r:R]-(b) SET r.v = $v` resolved to the *same* stored edge: one edge stamped
twice, the other never touched.

**The counter was right and the write was missing**, which is why this survived: `id(r)` returns
two distinct relationships, so under openCypher 9 relationship isomorphism the statement owes
two rows and two writes, and it reported exactly two. Only the graph disagreed.

`relStorageDirection` normalises the target from traversal order to storage order. Gated by
`cypher/set_undirected_reciprocal_test.go` and `cypher/exec/set_rel_storage_direction_test.go`.
**This fix has a measured allocation cost, and part of that cost is the write `v0.14.1` was
skipping** — see [*Measured results*](#measured-results).

### A failed statement reported the counters for the work it had undone

`rollbackUnderBarrier` did its job: every eager mutation was reversed. What it did not do was
clear `r.counters`, which went on pointing at mutations that no longer existed. A caller that
inspected the result of a *failed* statement was told about writes that had been rolled back.

**It is not MERGE-specific, as the report had it.** A plain multi-assignment `SET` and a
`CREATE … WITH … SET` reproduce it identically — the root cause is the rollback path, not the
clause. Gated by `cypher/failed_statement_counters_test.go`.

### `DROP INDEX … IF EXISTS` counted a removal that never happened

Both branches of `runDropIndex` bumped `IndexesRemoved` unconditionally, so absorbing a missing
index reported `indexesRemoved: 1` over an index listing that was **identical before and
after**. `dropIndexCounter` now reads for existence before the operator runs, and reports the
effect actually applied.

**WAL behaviour is unchanged** — nothing was ever written on the absorbed path; only the report
was wrong. This is the one fix in the release with an established time cost, priced in full
below.

### Three client faults the Bolt server was masking

Three errors a client could have acted on reached it as **"An internal error occurred"**, and
they were masked for three *different* reasons — which is why one fix would not have found all
three:

| Fault | Why it was masked | Now |
|---|---|---|
| `txn.ErrFieldTooLong` | no `FailureCode` case at all | `Neo.ClientError.Statement.ArgumentError` |
| unsupported-DDL refusal | arrives untyped, a wrapped `fmt.Errorf` from the hand-written DDL parser | `Neo.ClientError.Statement.SyntaxError` |
| `CREATE CONSTRAINT … IS NOT NULL` over violating data | `validatePreExisting`'s NOT NULL arm wrapped the bare **sentinel** where `errors.As` needed the **type** | `Neo.ClientError.Schema.ConstraintValidationFailed` |

The third is the sharpest: the UNIQUE arm returned a typed `*ConstraintViolationError` and
explained itself, while the identical NOT NULL refusal fell through to a server-fault code —
**an asymmetry no client could predict.**

**Each code follows precedent already in the module rather than being invented for the
occasion**, and the reasoning is recorded beside the branch that uses it:
`Neo.ClientError.General.LimitExceeded` was considered for the over-long field and **rejected**,
because rmp #2561 established that it does not appear in Neo4j's status codes at all.

**Every forwarded message was checked to carry only static text, the client's own tokens and a
format constant** — no server path, no Go type, no internal state — **and that check is now
asserted permanently** rather than performed once, in
`bolt/server/named_client_faults_wire_test.go`.

### An oracle that could not see what it was said to check

No DDL counter reached any oracle in the deterministic simulator, because the simulator
**discarded the `Result`**. The consequence is worth stating plainly: #2818's own oracle
acceptance criterion had been met **only vacuously**, by an oracle structurally incapable of
observing the quantity it was credited with checking.

The new oracle derives its expectation from the engine's own index and constraint registries,
read either side of the statement, and it was **proved to have teeth by a mutant**: restoring
the pre-#2818 unconditional increment turns it red. An oracle that has not been shown to fail on
a known-bad engine is not evidence, and this one has been.

`internal/sim/ddl_counters_oracle.go`, with `internal/sim/ddl_counters_oracle_test.go`.

### A flaky test that was not a flaky server

A metrics wire test failed about one run in seven. **It was not a server race.**
`ObserveLatency` interns the histogram *before* it records into it, so a scrape landing between
those two steps emits a complete, well-formed `_count 0` line — which the test's substring wait
accepted as "the metric has appeared", and then asserted on the zero it had just raced. The wait
now requires the **value**, not the line.

Recorded here because the distinction matters: a flake blamed on the server would have sent the
next investigator into `bolt/server` looking for a synchronisation defect that does not exist.

## Measured results

**Read the limits before the numbers.** [`docs/benchmarks/v0.14.2.md`](../docs/benchmarks/v0.14.2.md)
compares `v0.14.1` and `v0.14.2` first-hand — the `v0.14.1` tree extracted and re-measured from
scratch, three arms interleaved with the arm order rotated every round, a same-binary noise
floor measured in the same rounds, on one host (Apple M4, 10 cores, `darwin/arm64`, macOS
26.6.2, go1.27.1, no `-race`).

**The campaign was designed as six rounds and was stopped by decision after one complete round
plus a partial second**, when benchmark execution left the release path. That is the whole
evidence base; nothing was topped up afterwards. At `n ≤ 2` per arm:

- **No p-value is computed anywhere in that document**, and none is quoted here. A Mann-Whitney
  U needs `n ≥ 4` to have a usable distribution.
- **`benchstat`'s confidence interval is unavailable** — it needs six samples.
- **A row that separates but does not clear the campaign's own false-positive envelope is
  reported as *not adjudicable at this power*, never as unchanged.** 27 rows are in that
  category. Failing to resolve a difference is not evidence that there is none, and this
  release does not launder the one into the other.
- **Allocation counts are the exception and carry full weight.** `allocs/op` is a
  per-operation constant, not a statistic; where every sample within each arm is equal and the
  two constants differ, the difference is real **at any sample size**. Every allocation figure
  below is of that form.

### What is proved, not measured

**`search`, `search/centrality` and `graph/index/count` compile to byte-identical test
binaries** at `v0.14.1` and `v0.14.2` (sha256 under `-trimpath`). Those three packages host the
**entire headline benchmark set** — `Dijkstra_PostWarmup`, `Dijkstra_Large`,
`BFSDirectionOpt_PowerLaw`, `Yen_K100`, `Brandes_RandomGraph` — so **the headline benchmarks
execute identical machine code at both releases.**

This is stronger than any benchmark result in the document, and it cost nothing to establish. A
hash proves **equality**; a benchmark can only ever **fail to detect** a difference. No
campaign, at any sample size, could add to it. Their measured rows are consequently used as a
cross-arm noise floor, not as results.

### The one established time cost

**`DROP INDEX … IF EXISTS` on the absorbed path: 1.003 µs → 1.117 µs, +115 ns, +11.4 %, and
+2 allocations** (#2818).

| arm | samples (ns) | `allocs/op` |
|---|---|---:|
| `A` = `v0.14.1` | 1 000, 1 006 | **25** |
| `B` = `v0.14.2` | 1 124, 1 111 | **27** |
| `B2` = noise floor | 1 150, 1 101 | **27** |

Every one of arm `A`'s samples lies below every one of the four `B`/`B2` samples, with the
ranges fully disjoint. The arm order was rotated between rounds, so arm `A` ran **first** in
round 1 and **last** in round 2 and was faster in both. It is the only row in the campaign to
clear the calibration on both `|Δ|` and range gap — by a factor of 2.6 and 3.0 respectively.

**In proportion this is a DDL statement's cost, not a query path's.** `DROP INDEX` runs once per
statement under the engine's exclusive DDL lock. **On the real-removal path the added read does
not rise above the floor at all**: `H_CreateDropIndex`, which pays a `CREATE INDEX` in the same
iteration, measures 19.02 → 18.77 µs with allocations unchanged at 108.

The 115 ns buys a counter that stops `DROP INDEX <missing> IF EXISTS` reporting
`indexesRemoved: 1` over an index listing identical before and after. That is the trade, stated
so a reader can disagree with it.

### The allocation costs, as exact per-operation constants

| Benchmark | `allocs/op` | `B/op` | What it prices |
|---|---|---|---|
| `H_SetRelPropUndirected` | **251 → 261 (+10)** | 44 654 → 45 112 (**+458**) | a two-row undirected relationship `SET` (#2817) |
| `H_DropIndexMissing` | **25 → 27 (+2)** | 1 313 → 1 313 (**+0**) | an absorbed `DROP INDEX … IF EXISTS` (#2818) |
| `H_SetRelPropDirected` | **214 → 215 (+1)** | 41 434 → 41 469 (+35) | a one-row directed relationship `SET` (#2817) |

**No other benchmark in the campaign moved an allocation count** — not one of the 182 `allocs/op`
comparisons outside the purpose-built harness, and none in the three byte-identical packages.

**Part of #2817's +10 is not overhead — it is the write `v0.14.1` was skipping.** The directed
and undirected figures do not decompose to the same per-row constant, and the change itself
explains why: at `v0.14.1` both rows of an undirected match wrote to the *same* pair (that was
the bug), while at `v0.14.2` the reverse-hop row is normalised and writes to the **second,
distinct edge**. So part of the +10 is `relStorageDirection`'s by-handle probes and part is a
property write that never happened before.

**That split is a hypothesis consistent with the diff, not a measured attribution.** Separating
the two would need a third arm with the normalisation disabled, and none was built. It is
labelled as a hypothesis in the benchmark document and it is labelled as one here.

### What showed no cost

**#2816's `SET` entity-value rejection does not show.** The three node-`SET` shapes — the scalar
form, the REPLACE-map form, and a plan-miss form that forces a fresh plan build — hold their
allocation counts **exactly** at 101, 130 and 102 across both arms, and their timings sit inside
the false-positive envelope. The guard is a type switch on a value the evaluator already holds.

**`bolt/server` changed and did not move.** Its edit is on the **error** path; none of its 24
benchmark functions names `FailureCode`, `sanitiseErr` or `isClientFaultErr`, so no benchmark
reaches the new code and none was expected to. All 27 rows were run anyway — block geomean
+0.10 % against a +0.32 % same-binary floor.

### One result that is reported without being claimed

`exec/BuildReverse_vs_E/E=1000000` **improves 8.61 %** and clears the calibration, and **no
changed symbol explains it.** Nothing in `cypher/exec/set.go` or `set_all.go` is on the
reverse-adjacency build path. `B` and `B2` agree to 0.1 % while `A` sits ~8 % above both, in
both rounds and in both arm orders. The plausible reading is a code-motion or layout effect from
the package binary changing — which is exactly what a whole-package regression watch exists to
detect — but **attribution is not established**, and at `n = 2` it cannot be separated from a
two-round coincidence. It is reported as unexplained.

Of the **212 comparable rows** in the four packages whose binary did change, **2 clear the
calibration, 27 separate without clearing it, and 183 overlap.**

## Behaviour a caller can observe — the compatibility surface

No exported identifier changed, so nothing here breaks a build. All of it can change what your
code *sees at runtime*.

### A statement that used to succeed now returns an error

Writing a node-, relationship- or path-valued property now raises `InvalidPropertyType` where it
previously reported success and discarded the value (#2816). **If you have code that relies on
that silent discard, it will now see an error** — but it was not writing what it thought it was
writing, and on the REPLACE forms it was also destroying the target's other properties. Pass a
scalar, a list of scalars, or the entity's own property value (`b.name`), not the entity.

### An answer changes, for the better

`MATCH (a)-[r:R]-(b) SET r.v = $v` over a reciprocal pair now writes **both** relationships
(#2817). A graph that has been through the old path may contain a relationship that was never
updated; re-running the statement on `v0.14.2` will now reach it. Nothing repairs such a graph
automatically, because GoGraph cannot know which writes were intended.

### Reported counters change, in both directions

- A **failed** statement now reports **no** counters for the work it rolled back (#2823). If you
  read counters from a failed result, you were reading a description of state that no longer
  existed.
- `DROP INDEX … IF EXISTS` that removes nothing now reports `indexesRemoved: 0` (#2818).

Both are corrections. Code that asserted on the old values will need updating, and code that
*acted* on them was acting on a falsehood.

### Bolt clients receive three new status codes

Conditions that previously arrived as `Neo.DatabaseError.General.UnknownError` with the message
"An internal error occurred" now arrive as `Neo.ClientError.Statement.ArgumentError`,
`Neo.ClientError.Statement.SyntaxError` or `Neo.ClientError.Schema.ConstraintValidationFailed`,
each carrying the client's own diagnostic (#2819). A driver that classifies retryability from
the status code will now classify these **correctly** as client faults — that is the point — but
it is a change in what the wire carries, so it is listed here.

### What you must do

**Nothing, to upgrade.** No migration, no format change, no configuration change, no API change.
Read the two items above that change an error or a counter, and check whether your code reads
either.

## Security posture

- **No security defect was found or fixed in this window**, and none is claimed. This section
  exists to record what was *verified*, not to manufacture a finding.
- **Three new error paths forward a message to an unauthenticated-capable client, and each was
  audited before it shipped** (#2819). Every forwarded message was checked to carry only static
  text, the client's own tokens and a format constant — **no server path, no Go type, no
  internal state** — and that property is now asserted by a permanent wire test rather than
  established once by inspection. Widening what a server tells a client is exactly where
  information disclosure enters, and it was treated that way.
- **`go.mod` and `go.sum` did not move**, so no dependency advisory is in scope for this
  release. `govulncheck` runs inside `make ci` and is part of the release gate.
- **The `v0.14.1` exposure is unchanged and still applies.** That release disabled the Bolt
  server's four timeout defaults, so an unauthenticated client that completes the handshake and
  then falls silent before LOGON holds a connection slot indefinitely. **`v0.14.2` does not
  change this.** An operator exposing the server to an untrusted network should still set
  `Options.ConnTimeout` and `Options.MaxTxIdleTime` explicitly.

## Premises refuted — the negative results

**Two of the twelve tasks refuted their own premise and shipped no fix.** Sprint 361 required
every reported premise to be re-validated at `HEAD` before any code changed, precisely because a
report can be stale or can describe a cause that does not exist. Both results are recorded here
in full, because a refuted premise is a result — and because the alternative, quietly closing
the task, destroys the evidence that would stop the same report being filed again.

### #2815 — the relationship-property read divergence does not reproduce

The report described a divergence in how a relationship property reads back. **It could not be
reproduced at `HEAD` on any path tried**, and the search was deliberately exhaustive rather
than cursory:

- the embedded Go API, and the Bolt server at **both** protocol versions (4.4 and 5.0);
- **autocommit** statements and **managed transactions**;
- **directed** and **undirected** match patterns;
- a **multigraph** and a **simple** graph;
- **WAL-backed** storage, and **across a store reopen**.

Every combination agreed. The task shipped as **permanent regression coverage rather than a
fix** — `cypher/rel_accessor_agreement_test.go` and
`bolt/server/rel_accessor_agreement_wire_test.go` — so the agreement the report doubted is now
defended by a test on both the embedded and the wire path, whatever the original observation
was.

**What this does and does not establish.** It establishes that the divergence is not present at
`HEAD` on any of those paths. It does **not** establish that the original reporter saw nothing:
an earlier tree, or a path not in the list, remains possible. That is why the outcome is
coverage rather than a closed "works as intended".

### #2820 — the `DROP CONSTRAINT` twin of #2818 cannot exist

#2818 found `DROP INDEX … IF EXISTS` counting a removal that never happened, and #2820 was
opened on the reasonable assumption that `DROP CONSTRAINT … IF EXISTS` would share the defect —
the two statements are siblings and the counting wrapper is shared.

**It does not, and the reason is structural rather than incidental.** `dropConstraintLocked`
**must resolve the name to a kind, a label and a property before it can act at all.** On an
unresolved name it returns the empty result **before the counting wrapper is ever reached**, so
there is no path on which an unconditional increment could fire. The asymmetry with the index
path is not an oversight in the constraint path; it falls out of the constraint path needing
more information to do its job.

Shipped as `cypher/drop_constraint_if_exists_counter_test.go`, so that if the resolution step is
ever moved or short-circuited, the absent defect becomes a present test failure.

### Two premises that were narrower than the defect

The same re-validation rule worked in the other direction twice, and both are in the fixes
above:

- **#2816** was reported as a dropped value. The root cause showed the REPLACE forms also
  **cleared the node's existing properties** while reporting `propertiesRemoved=1` — silent data
  destruction that the report had not seen.
- **#2823** was reported as MERGE-specific. It is not: a plain multi-assignment `SET` and a
  `CREATE … WITH … SET` reproduce it identically, because the cause is the rollback path rather
  than any clause.

**Four of twelve reports were materially wrong about their own subject** — two refuted, two
understated. That is the argument for the re-validation rule, stated with the number it earned.

## What this release does not do

- **It does not extend openCypher coverage.** 3 897/3 897 is preserved, not raised; no
  `.feature` file changed.
- **It does not change any durable format.** No snapshot, manifest or WAL record layout moved.
  There is no migration and no index rebuild.
- **It does not change the exported API**, add a feature, or change a default.
- **It does not address the Bolt properties-set counter divergence in code** (#2791). That
  counter carries removals as well as additions. It is **declared as a protocol-conformance
  divergence in [`docs/bolt.md`](../docs/bolt.md), with its reproduction**, because the
  incumbent implementation has no separate counter either — changing the number would diverge
  from the implementation every client is written against. Documented, deliberately, rather than
  fixed.
- **It does not re-measure the concurrency ladders.** See below.
- **It does not carry a production certification.** The most recent was taken at the `v0.11.0`
  commit.

## Test evidence summary

### Established in the sprint

- **11 new regression test files carrying 24 top-level test functions**, plus 2 existing test
  files modified — 13 files, **2 254 insertions against 10 deletions**. Every fix in this window
  closes with a test that fails on the old behaviour and passes on the corrected one, by the
  sprint's own rule.
- **One oracle was proved to have teeth by a mutant.** The new DDL-counter oracle
  (`internal/sim/ddl_counters_oracle.go`) was checked against an engine with the pre-#2818
  unconditional increment restored, and turned red. This matters more than its size suggests:
  the oracle it replaces had satisfied #2818's acceptance criterion **vacuously**, while being
  structurally unable to observe a DDL counter at all.
- **Two refuted premises shipped as coverage, not as closures** — #2815 across the embedded API
  and both Bolt protocol versions, #2820 on the constraint-drop path.
- **A message-disclosure property is now asserted permanently** rather than checked once
  (`bolt/server/named_client_faults_wire_test.go`).
- **A one-in-seven flake was diagnosed to the test rather than to the server** (#2821), and the
  diagnosis is recorded so the next investigator does not go looking for a server race that does
  not exist.

### Established by the release gate, not here

**The gate is a precondition of tagging, and it is run by the releaser immediately before the
tag is pushed.** These notes do **not** record it as already passed:

```
VERSION=v0.14.2 make release-preflight
```

That target runs `release-accuracy` (release-document consistency) and then the full `make ci`
exactly once: `go mod tidy`, `gofmt`/`goimports`, `go vet ./...`, `go build ./...`,
`govulncheck`, `go test -race ./...` — which contains the `cypher/tck` `TestTCKExecution`
`=100 %` execution baseline, so a TCK regression fails the gate — `golangci-lint run ./...`, the
coverage gate (≥ 85 % aggregate, ≥ 75 % per package) and `ci-kg-verify`.

**`ci-kg-verify` needs a running `rmp graph serve`**, or `make ci` fails for a reason unrelated
to the change being gated.

### What was not run

Stated plainly, because a release that lists only what it verified is not a faithful one.

1. **Rounds 2 through 6 of the benchmark campaign.** One complete round plus a partial second
   were collected out of six planned. **The campaign was stopped by decision**, when benchmark
   execution was removed from the release path — not because the numbers looked acceptable. All
   the statistical limits in [*Measured results*](#measured-results) follow from this.
2. **The published concurrency ladders were not re-measured.** The `-test.cpu=1,8,64,256,1024`
   ladders `v0.14.1` published were in the six-round design and **were dropped with the
   campaign**. The concurrency levels this project publishes are **unmeasured for this release**.
3. **Latency percentiles at those levels** — unmeasured, for the ninth consecutive cycle.
4. **The durable commit path at any concurrency.** `store/txn` was not in the block set, because
   its source did not change.
5. **The soak and nightly layers**, and any production certification of this release.
6. **No `-race` benchmark figures and no profiles.** Every allocation number in this release is
   a non-race number and must not be compared against one taken under `-race`.
7. **No comparison against Neo4j, Memgraph or any other engine.**
8. **Attribution is established for nothing in the benchmark record.** No third arm was built
   with the normalisation or the existence read disabled, so every cause named is a hypothesis
   consistent with the diff. A profile would not fix this: a profile shows where time goes in
   one arm, never why two arms differ.

**A note on the gate itself.** Benchmark execution left the release path in this window's
release-preparation commits: `make release-accuracy` no longer requires a per-release benchmark
document to exist, and `make release-preflight` no longer runs the headline bench. **The
correctness gate is unchanged.** This is a change of *gate*, not of *standard* — measurement
still decides every performance question in this project, and `scripts/bench_gate.sh` still
compares a candidate against its baseline locally, before a change lands. What stopped is
producing a per-release campaign as a *precondition for tagging*.
