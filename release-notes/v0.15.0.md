## Read this first

**This is a performance release, and nothing in it asks you to change your code.** No exported
identifier was removed, renamed or re-signed; no on-disk format changed; no default numeric
result moved; the openCypher TCK held at 3 897/3 897 throughout. The upgrade is a version bump.

Three things are worth reading before you take it:

1. **The Bolt server's per-rejection log is now bounded to one line per second.** Refusing 500
   connections produces **1 log line** where `v0.14.2` produced 500. The counter
   `bolt.server.conn.rejected` still counts exactly 500, so no signal is lost — but **if you
   alert on the volume of that log line, your alert will stop firing.** Read
   [*Behaviour you can observe*](#behaviour-you-can-observe--the-compatibility-surface).
2. **An empty graph now costs 91 KiB more, and `graph/lpg.New` takes 57 % longer.** That is the
   published price of taking the property and label stripe count from 64 to 256, which bought
   +7.0 % throughput at 64 concurrent connections and +13.3 % at 1 024. If you create very many
   tiny graphs in a tight loop, this is the one line in the release that costs you something.
3. **Two exported identifiers were added, and both are opt-in.**
   `graph/index/label.(*Index).BitmapShared` returns a **shared, immutable** bitmap that the
   caller must not mutate — `Intersect` and `Union` are unchanged and still hand you a copy you
   own. `cypher/exec.ExpandConfig.EmitStoredDir` defaults to `false`; setting it appends a
   fourth column to `Expand`'s rows and makes the caller responsible for registering that
   column.

**The largest result in the release needs no opt-in at all.** `search`'s BFS built its frontier
queue at capacity one and grew it once per source. On a 100 000-user social-graph example that
was **2 026 768 allocations** in one call path; it is now **433**, and the example's CPU fell
**34.1 %**. If you call `Diameter` or the 2-sweep helpers on a large graph, you get that for
free.

## Semantic-versioning rationale

**`0.15.0` is a MINOR by the rule, not by decision.**

The exported surface was measured rather than asserted: every non-test Go file outside
`internal/`, `examples/`, `cmd/` and any `gen/` or `tck/` directory was parsed at `v0.14.2` and
at `19138042`, and the rendered exported declarations were diffed. **4 820 declarations before,
4 822 after.**

**That file set is deliberately a superset of the API surface
[`docs/semver.md`](../docs/semver.md) defines**, and the difference is worth naming: the policy
counts only `bench/ldbc`, `bench/dimacs9` and `bench/rmat` from `bench/`, while this scan
retained all of it (181 exported declarations). A superset cannot *miss* a change inside the
surface, only report one outside it — and no `bench/` file changed in this window, so the
result is identical under either reading.

The complete difference is two lines:

```
> cypher/exec	type ExpandConfig field EmitStoredDir bool
> graph/index/label	func (*Index) BitmapShared(label uint32) *roaring64.Bitmap
```

| Change | SemVer class under `docs/semver.md` |
|---|---|
| `graph/index/label.(*Index).BitmapShared` added | **MINOR** — "a new exported identifier is added (package, type, method, function, constant, error)" |
| `cypher/exec.ExpandConfig.EmitStoredDir` added | **MINOR** — a new exported field, and a new behaviour behind an opt-in flag |
| `cypher.csr_pair_cache.bypasses_no_cache`, `.bypasses_own_writes` | **Additive, outside the definition.** Metric names are not exported Go identifiers, so they are not public API under `docs/semver.md`. They are additive either way, and they are documented. |
| `examples/internal/exprof` gains `-contention` | **Not API.** `docs/semver.md` excludes `examples/` explicitly: the module neither imports nor depends on it. |
| Thirteen measured optimisations | **PATCH** — "an optimisation lands without changing observable behaviour (benchstat numbers improve; semantics unchanged)" |
| `make ci` composition and ordering | **Not API.** Build tooling. |

**No MAJOR trigger is present**, and this was checked against each of the four the policy lists:

- **No exported identifier was removed or renamed** — zero deletions in the surface diff.
- **No method signature changed incompatibly** — zero modifications in the surface diff.
- **No behavioural guarantee was weakened.** The two candidates were examined directly.
  `EmitStoredDir` is `false` by default, so every existing caller's row width and chunk schema
  are unchanged; the fourth column exists only for a caller that asks for it. `BitmapShared` is
  a **new** method returning a shared image — `Intersect` and `Union` keep their caller-owned
  contract, and a regression test deliberately mutates a single-label `Intersect` result to
  assert that ownership survived.
- **No on-disk format changed.** No file under `store/` was modified in this window at all.

**The module is pre-1.0, so a breaking change would have been permitted in a MINOR.** There is
none to declare, and this release does not use that allowance.

**Precedent, stated so it is not mistaken for a rule.** `v0.14.1` shipped a MINOR-sized surface
as a PATCH by explicit decision. That option exists again here — it would make this `0.14.3` —
but the strict reading of the project's own policy is MINOR, and that is what this document
recommends and what the version above reflects.

## Compliance mandates

All four of the project's non-negotiable invariants were exercised and held.

**100 % openCypher TCK.** `const tckExecutionBaseline = 3897` in `cypher/tck/runner_test.go` is
**untouched**, and **no `.feature` file changed in this window**, so the scenario population is
the one `v0.14.2` was measured against. Each campaign re-ran the gate rather than inheriting a
verdict; the release gate ran it once more, with the `cypher/tck` package reporting `ok` in
**47.061 s**.

**100 % ACID.** No commit, recovery, WAL or snapshot path was modified — `store/` is untouched
in the whole window. The Bolt write-coalescing change (#2834) moves *when the response bytes
reach the socket*, never when a transaction commits; the property-stripe widening (#2839) changes
the number of mutexes, not the protocol that acquires them. `-race` is clean across the module.

**Extreme concurrency.** This is the release's subject. The Bolt server was driven at 1, 8, 64,
256 and 1 024 connections plus saturation — the exact ladder `CLAUDE.md` names — across three
profiling rounds, and the campaign established that **nothing in the server scales with
connection count**: per-query write cost, read cost, syscall counts and allocation are flat over
a 16× range of N. One genuine contention defect was found and fixed (#2852, the plan cache), and
one contention *report* was refuted with numbers (#2867). Every window checked
`accepted == closed`, zero panics, no goroutine leak, no deadlock: 1 092 windows in the
transaction-shape pass alone.

**Ultra efficient.** Every claim below is an interleaved A/B against a byte-identical noise
control measured in the same session. Four optimisations were **built and then discarded**
because measurement refused to support them.

## Highlights

### The BFS frontier queue was 2 026 768 allocations, and is now 433

`search.bfsFarthest` built its BFS queue **inside the function, at capacity one**, and grew it
once per source. It was invisible in every CPU profile the project had read, because the cost
did not present as `bfsFarthest` — it presented as the Go runtime's allocator, **66.35 % of one
profile**.

The queue is now caller-owned scratch, pre-sized to `n` — a hard bound, since a BFS enqueues
each vertex at most once — and threaded through both 2-sweep calls and the level walk, with a
private queue per worker on the parallel arm.

On `11_social_network -users 100000`, three interleaved rounds:

| Quantity | Before | After |
|---|---:|---:|
| `diameter.allocs` | 2 026 768 | **433** (4 681×) |
| total allocation | — | **−99.49 %** |
| profile CPU | 221.18 s | **145.72 s (−34.1 %)** |
| Go-runtime bucket | 146.76 s (66.35 %) | **6.58 s (4.52 %)** |

Benchmarks fall **−25.64 %** and **−38.10 %** sec/op on the two diameter rows. **Traversal order
is unchanged, so results are bit-identical.** The campaign's causal hypothesis — that the runtime
bucket *was* this allocation — is one of the few that held.

### The label bitmap was cloned on every scan

`LabelBitmapAsOf` cloned the whole roaring bitmap each time a scan consulted it: **52.75 % of one
profile's allocation.** Each label entry now memoises an **immutable image**, published under the
entry's existing lock and dropped by the four mutators through the single `Index.mutate` funnel.
The warm path takes a read lock, returns the pointer, and **allocates nothing**.

**−28.71 % geomean** over 10 interleaved rounds, all four phases at p=0.000, against a noise
control in which **no row was significant**. The roaring clone chain leaves the allocation
profile **entirely** — 0.00 % at `-nodefraction=0`. Allocation falls **15 223 → 9 742 MB at
1.431× the operations**.

The correctness argument is the interesting part, because a memoised snapshot could easily be
stale. It is proven rather than argued: `acquire()` sits at the **exact position** `clone()` did,
and a published image is immutable, so a later `Clone()` reproduces the acquire instant. A test
re-runs the #2326 injection with the churn counters drained inside the closure; removing the late
clone fails it deterministically. Two further mutants are killed by eleven tests and by a
SIGSEGV. All 36 `Intersect` call sites were resolved by hand.

### Undirected expansion probed the topology twice per row

`exec.Expand` discarded the stored-direction bit it already knew, and the hydrator recovered it
per row with an **O(deg)** topology probe. Direction is now resolved at plan time for
`DirOut`/`DirIn` — no probe and no column, because a directed hop's orientation is a property of
the hop — and carried as a single bool cell only for `DirBoth`, the one direction under which it
varies row by row.

**Geomean −27.02 %** over 8 shapes, all at p=0.000, n=12, with four arms in one binary
interleaved per repetition against a same-arm control reading **+0.11 %**. Allocs/op **+0.00 %**.
The `DirBoth` column pays for itself: **−16.68 % to −41.44 %** on undirected shapes, flat
(p=0.64–0.98) on directed ones. `relStoredInverted` and `slotHoldsHandle` leave the profile
entirely; the surviving `relStoredInvertedForHop` is **0.032 %** against a 1 % target, and the
reference benchmark falls **118.05 s → 95.19 s** of CPU.

Two defects were caught inside the task itself and are recorded rather than buried: a
**name-collision premise that returned one row where two were required**, and an **inlining
regression** (+3.54 % / +6.98 %) caused by putting the cell inside `buildRow`, fixed by splitting
the store and now guarded by a field-offset test.

### The row path resolved the same six facts on every row

`populateRowCtx` re-derived per-row binding facts that are fixed for the whole plan.
`rowBindPlan` now resolves them once under a `sync.Once`, holding the kind as a **bitmask rather
than an enum**, because the original ladder falls through rather than branching.

`mapaccess2_faststr` attributable to `populateRowCtx` went from an **8.37 s mean** — 7.57 to
9.69 s over seven baseline runs — to **absent from the caller list entirely** at
`-nodefraction=0`. The absence was checked for vacuity: the function is still **22.28 s cum
(26.22 %)** of the profile, so the loop did not simply stop running.

Over 5 interleaved repetitions with complete separation, **p=0.0079** by exact permutation:
total CPU **96.76 s → 85.77 s (−11.35 %)**, wall **−13.29 %**, and **all 79 result lines
identical in all five repetitions**. Only about 8.4 s is attributed to the removed probes; **the
remainder is stated as unattributed** rather than claimed.

### The Bolt server wrote twice per query

`bolt/server` flushed on every non-RECORD message, so the server performed **2.00 `write(2)` per
query** where the client delivered RUN+PULL in **1.00** — 42.06 % of all process CPU at 256
connections, and flat in connection count: 800 761 syscalls for 400 000 queries.

`sendResponse` no longer flushes. The session loop carries one absolute obligation instead — the
response buffer is drained before the goroutine can block waiting for the client, and before
teardown — discharged in exactly two named places. `flushUnlessRequestPending` guards the only
blocking point by testing `len(msgCh) > 0`, which is **positive proof** the receive cannot block
because the loop is the channel's only receiver; reading zero costs one flush, exactly the old
behaviour. `flushOnTeardown` covers every return while the socket is still open, **under a fixed
deadline**, so a peer that has stopped reading cannot pin a handler goroutine and its semaphore
slot.

| Connections | write syscalls/query | throughput |
|---|---:|---:|
| 64 | 2.000 → **1.001** | **+20.66 %** |
| 256 | 2.000 → **1.002** | **+19.61 %** |
| 1 024 | 2.000 → **1.005** | **+16.99 %** |
| saturation | — | **+19.71 %** |

Against a same-versus-same noise floor of 0.57 %. p99 falls **17.84 %** at 64. Verified
independently at 256 connections: **192 540 q/s** against a 161 283 q/s baseline. Round 2
re-measured the gains at HEAD as +20.19 / +19.45 / +19.94 / +16.80 % with the floor re-derived at
1.08 % — a faster server has a wider floor.

**The shape was taken from Memgraph's rule, read in its source and reimplemented** for a reader
living on a separate goroutine; no code was copied. RECORD batching is unchanged and its three
regression tests are untouched. The syscall oracle **fails on the old build** at exactly 2.000
writes per query, and the deadlock gate drives a genuinely non-pipelining client.

### The plan cache did not scale with the cores it was given

Filed and worked as a **defect** (#2852), not a missed optimisation: under this project's
concurrency mandate a hot path that serialises every caller on one global lock is a defect. A
single mutex, LRU list and map carried **98.46 % of all mutex delay**, and one lookup cost
**15.04 ns at one core against 92.14 ns at ten** — the cache got slower the more cores it was
given.

It is now sharded 16 ways, each shard with its own mutex, LRU list and map, padded to a cache
line. **32 keys at ten cores: 119.10 ns → 42.42 ns, −64.38 %**, with no allocation added on any
row.

**16 shards, not the 256 that reaches the −83.7 % headline ceiling.** A second ladder priced the
difference: at 75 % load the hit rate falls from **99.5 % at 16 shards to 66.0 % at 256**, and one
lost hit-rate point costs about **18 ns per lookup against a measured 1.8 µs miss**. The headline
ceiling is therefore missed at the shipped count, and that is stated rather than smoothed — it
was derived from the one-key case, which sharding provably cannot address. A false-sharing
hypothesis raised during the work was refuted by an unpadded control that was indistinguishable
at one core, and the small single-core cost was attributed by single-variable experiment to the
split LRU splice, which is the accepted trade.

### `StripLiterals` allocated on every cache hit

`strip.go` called `strings.ToUpper` on every identifier token to test whether it was a clause
keyword — **78.6 % of all objects `StripLiterals` allocated**, paid on **every execution,
including plan-cache hits**, because `StripLiterals` runs before the cache is consulted.

`classifyClauseKeyword` now gates on length, folds the first byte, and compares the whole token
with an ASCII fold applied *during* the comparison, so `matches`, `setting`, `ordering`, `forall`
and `sets` remain identifiers.

Corpus **5.449 µs → 2.843 µs (−47.83 %)**, exceeding the −46.63 % ceiling the spike predicted;
allocations **148 → 32**, reaching the predicted bound exactly; the twelve quoted statements
**−52.02 %**. **All 78 non-hoisting statements now allocate nothing**, including seven that had
been paying up to 13 allocations per execution for no benefit.

The equivalence is proven, not assumed: over **213 749 exhaustive identifiers** plus every case
permutation of all 23 keywords. A second test walks all 256 byte values to pin the ASCII premise,
so a future widening of the alphabet fails *there* rather than silently invalidating the fold.

### Parsing bails on the accepting path

`ParseStatement` now runs a bailing stage first and re-parses under the full error strategy only
when that stage does not accept. Accepting path **1.798 ms → 1.690 ms (−6.01 %)**, allocations
**+0.31 %**.

**The error path costs +57.4 %, and that price is measured rather than assumed.** Error fidelity
is fenced by 21 statements compared field-for-field against literals captured before the change;
the two stages agree over **5 912 corpus prefixes** with a floor so the oracle cannot go silent;
fuzzing ran **1 035 449 executions** with no hang and no panic.

Prediction mode deliberately stays **LL**. `PredictionModeSLL` was the prior art's most promising
lever — Neo4j runs SLL with a bail strategy and retries under LL, the Go ANTLR runtime exports
both APIs, and GoGraph had never set either — and measurement refuted it at **−0.49 %, p=0.529**,
below the 1.05 % noise floor, on two independent runs. The whole **−6.46 %** the spike had
attributed to SLL belongs to the error strategy, and LL+Bail delivers it without touching
prediction semantics, which is strictly safer.

The bail strategy is **wrapped** because raw it writes to stdout and then panics on any input
failing at a token `Match` — verified in the ANTLR runtime source, not assumed — and the wrapper
doubles as the sentinel that keeps a genuine runtime panic from being read as a bail.

## Measured results

### The measurement discipline, because the numbers depend on it

**Every claim in this release rests on an interleaved A/B against a byte-identical noise
control, measured in the same session.** This is not ceremony. On the measurement host a
same-versus-same arm has produced **22 of 36 flat-by-construction rows as statistically
significant**. A comparison made without that control on this machine means nothing, and several
figures in this release exist only because the control caught an apparent effect that was not
there.

**Host**, identical for every number below: Apple M4, 10 cores, 32 GB, macOS 25.6.0,
**Go 1.27.1 `darwin/arm64`**.

**No rung of the Bolt ladder is certified idle, and every one publishes its own load.** A measured
120-second baseline of this host gives `loadavg1` median 2.19, so the project's
`NumCPU × 0.10` ideal is unreachable on it. The idle gate itself was **replaced mid-campaign**:
`loadavg1` is a ~1-minute exponential average against ~35 s rungs, so every gate was reading the
previous rung's own decay and the campaign was rejecting itself at ~70 s per rung. It now sums
`ps` %CPU over non-campaign processes plus a fixed cool-down, and gate attempts fell from 9 to 1.

**Noise floors are per-campaign and are not transferable**, and this release re-derived them
rather than reusing them: Bolt round 1 measured 0.57 %, round 2 re-derived **1.08 %** at the
faster HEAD, and the four transaction shapes each got their own (1.04–3.91 %). The parsing
laboratory's replica gives Full 1.05 %, PrepareCold 0.33 %, Parse 1.76 % — and **Visit 11.97 %**,
because it is a difference of two large prefixes.

**`pprof` defaults were corrected before any attribution was made.** `-nodefraction=0` is used
throughout, because the default drops every node under 0.5 % and on this campaign's own precedent
that silently hid **4.66 s of a 20.70 s total**. `pprof -show=<pkg>` is **never** used: it
redistributes a dropped node's cost into its nearest retained ancestor, so per-package "shares"
overlap rather than partition.

### The costs, published rather than buried

- **256 property stripes cost 91 KiB on an empty graph, and `graph/lpg.New` takes 57 % longer**,
  because `New` eagerly allocates one map per stripe in three of the nine shard arrays (#2839).
- **The Cypher error path costs +57.4 %** under two-stage parsing (#2850). A statement that
  parses pays −6.01 %; a statement that does not parse pays the retry.
- **Sharding the plan cache adds a small single-core cost**, attributed by single-variable
  experiment to the split LRU splice, and accepted as the trade for −64.38 % at ten cores
  (#2852).

### What did not move

- **`propMapShards` 64 → 256 is a level shift, not a change of scaling behaviour**, exactly as
  its design predicted: the collapse from 64 to 1 024 connections moves only **0.660 to 0.698 of
  peak**. Four times the stripes buy a better constant, not a better curve. **4 096 was rejected
  on measurement** for penalising the single-threaded scan (+43.8 %) and write (+41.7 %) alike,
  and a full-scan read at 256 stays indistinguishable from 64, so the read path the earlier
  16→64 widening bought is not surrendered.
- **No default numeric result changed anywhere in this release.** The two float reassociations
  that would have changed one were discarded — see below.

### Benchmark evidence summary

**The full measured record is [`docs/benchmarks/v0.15.0.md`](../docs/benchmarks/v0.15.0.md).**
It is a required release artefact: `internal/docscheck`'s
`TestPerReleaseBenchmarkReportExists` runs inside `make ci` and fails the gate when
`docs/benchmarks/<version>.md` is absent, guarding rmp #1398 on the rule that "each release must
record its benchmark/load-test numbers". What left the release path in `v0.14.2` was benchmark
*execution* — neither `make release-accuracy` nor `make release-preflight` runs a benchmark —
not the report.

**Four things that record is explicit about, because they bound what this release can claim:**

1. **No release-time campaign was run.** Every figure is a development-time A/B measured by the
   task that shipped the change, at that task's own commit, against that task's own control. A
   release campaign would have extracted both trees and re-measured them side by side; this did
   not. **So no whole-release delta is claimed, the thirteen results are not additive, and
   nothing here establishes that code no task touched did not regress.**
2. **No load test at the published 1/8/64/256/1024 concurrency ladder was run for this
   release.** The Bolt campaign drove exactly that ladder, but as campaign evidence at its own
   commits rather than as a release exercise. The ladder figures above are those, and the report
   marks them as such.
3. **Two of the three campaigns' raw artefacts are outside this repository.** The Cypher-parsing
   and plan-cache work deposited full benchstat series under `docs/benchmarks/` —
   `cypher-parse-lab-2026-09-16-raw`, `…-replica-raw`, `…-round1`, `…-spike2846`,

## Behaviour you can observe — the compatibility surface

**Nothing here requires a code change.** Four things change in ways an operator or a caller
could notice.

### 1. The Bolt rejection log gets much quieter

Refusing 500 connections now produces **1 log line** per one-second interval instead of 500, and
the log argument is lazy: `RemoteAddr` is resolved **0** times at `LevelError` and **1** time at
`LevelWarn` across 100 refusals.

**No signal is lost**: `bolt.server.conn.rejected` still counts **exactly 500**. **If you alert
on the rate of that log line rather than on the counter, move the alert to the counter.**

The bound is on **time, not a one-in-N sample**, deliberately: a count-based sample still grows
linearly with a flood's rate, which is precisely the property that had to go. `rejectLogInterval`
is a fixed one-second package constant following the `handshakeTimeout` precedent, and is
**deliberately not an `Options` field**, so the change does not widen the public API. Admission,
the semaphore and its capacity are byte-identical.

### 2. The Bolt server issues one `write(2)` per query instead of two

Protocol bytes are unchanged; what changed is how many syscalls deliver them. Two consequences a
deployment could see: a packet capture or `strace`/`dtrace` trace looks different, and **a peer
that stops reading is now disconnected on a fixed teardown deadline** instead of pinning a
handler goroutine and its semaphore slot indefinitely. The second is a strict improvement under
load, and it is the reason the deadline exists.

### 3. `graph/lpg.New` is slower and an empty graph is larger

`New` takes **57 % longer** and an empty graph grows **91 KiB**. This is the published price of
256 property stripes. It is a per-graph constant, not a per-operation cost, so it is visible only
if you create very many small graphs.

### 4. Two new opt-in entry points

**`graph/index/label.(*Index).BitmapShared(label uint32) *roaring64.Bitmap`** returns the
memoised immutable image **without copying it**. **The caller must not mutate the result.**
`Intersect` and `Union` are unchanged and still return a bitmap the caller owns — a regression
test mutates a single-label `Intersect` result specifically to assert that.

**`cypher/exec.ExpandConfig.EmitStoredDir bool`** defaults to `false`. Set, it appends a **fourth
column** to every row `Expand` emits, carrying the edge's stored orientation relative to the
emitted traversal orientation: `false` for a row the forward pass produced, `true` for one the
reverse pass produced. It is meaningful only for `DirBoth`. **A caller that sets it owns
registering the fourth schema column**, or the row and `schemaWidth` disagree. The cell is an
`expr.BoolValue` and is read by **type assertion**, so a coordinate that has gone stale across a
projection lands on a non-Bool and falls back to the old ladder — slow, never wrong — instead of
reading a node id as a direction.

### What you must do

Nothing. `go get github.com/FlavioCFOliveira/GoGraph@v0.15.0`, rebuild, and review your Bolt
rejection alerting if you have any.

## Premises refuted — the negative results

Seven premises died on numbers in this window. Four had working code behind them when they died.

### Two float reassociations were built in full and then discarded

Opt-in non-bit-reproducible variants of Betweenness and PageRank (#2870) were **implemented,
validated and measured**, and then thrown away, because **neither reassociation is faster**. Two
independent realisations, 7 interleaved samples each with rotated arm order: **every row flat**,
geomean **+0.24 %** and **+0.22 %**, against a byte-identical control reading **+0.81 % at
p=0.017**. The noise floor was wider than the effect sought, on rows proven able to resolve
2–3.5 %.

The assembly says why. The removed division **hides behind** the `delta[v]` read-modify-write and
the `sigma[v]` gather; PageRank's pull loop is bound by **two random gathers**, not by the
arithmetic between them. **The 8.89 s and 1.87 s of profiled self-time that motivated the work
were self-time on instructions off the critical path.**

An entry point named for speed that is not faster would have cost **+4.85 % B/op**, cost
bit-reproducibility, and widened the public API for nothing measured. Shipping it would have been
a defect against the efficiency mandate. **The lesson generalises and is recorded for every other
row that rests on self-time alone: self-time charged to an instruction is not work saved by
removing it.**

### The `Snapshot.visible` contention does not exist

`Snapshot.visible` accounts for **0.046 % / 0.027 % / 0.196 %** of `37_mvcc_write_contention`'s
mutex delay across three passes, and **does not appear at all** in
`36_mvcc_snapshot_topology` (#2867). None of it is the `sync.Mutex` the report named: `visible`'s
only children are `runtime.mapassign_fast64ptr` (93.64 %) and `makemap_small` — the runtime heap
lock **inside** the map insert, which is the *allocation* the memo causes, not the lock guarding
it. Row 37's real mutex delay is **75.63 % `RWMutex.Unlock`** under the versioned-write path, a
different finding. No code changed; the allocation cost is real and is filed as #2873.

### Throttling the MVCC vacuum cannot help, and mutex delay is not a cost function

A ceiling probe ran with `reclaimPropVersions` **disabled entirely**, not throttled:
**12 543 q/s against a base of 12 669 — a −1.0 % difference, exactly the noise floor** —
although the vacuum held **21.0 % of all Go-mutex delay** at 1 024 connections (#2840). Deleting
the work is the most generous version of any scheduling change, and it bought **zero
throughput**, which bounds every possible fix from above.

**It also corrects the premise the task was written on.** A component can dominate a mutex
profile and cost nothing, because delay counts time goroutines spent *waiting* rather than time
the workload *lost* — and with far more goroutines than cores, a goroutine that waits is not a
goroutine that would otherwise have been running. The campaign's ranked tables were re-read
against this, and **no other row depended on the mistaken reading**.

### Removing Bolt's per-chunk allocation is not worth its risk

The weight reproduces at HEAD — **1.18 KB and 25.9 objects per query**, 1.42 % of allocated bytes
and 1.60 % of objects (#2836). But GC mark CPU is only **0.62 / 0.92 / 1.06 %** of process CPU at
64 / 256 / 1 024 connections, and `runtime.mallocgc` does not clear the CPU profile's 0.27 s
reporting threshold. The gain has a ceiling of roughly **0.015 % of process CPU — about 70×
below the noise floor** — on the inbound reassembly path that the size budget and length-bound
tests guard. **GC would have to become ~70× more expensive for this to matter, and round 2
measured GC falling, not rising, with connection count.** This is the campaign's stopping rule
working, not a task abandoned.

### SLL prediction bought nothing

See [*Parsing bails on the accepting path*](#parsing-bails-on-the-accepting-path). The prior
art's most promising structural lever measured **−0.49 %, p=0.529**, on two independent runs.

### The 256→1024 Bolt knee was the measurement, and partly the laboratory itself

The apparent −17 % throughput knee is a **measurement-window artefact**: varying only the window
gives −14.90 % at 20 k queries, −6.89 % at 100 k and **−4.40 % at 400 k**, a fixed 24–31 µs
per-connection start-up amortised over fewer queries. **Half of what remained was the
laboratory's own descriptor walk** — `os.ReadDir("/dev/fd")` lstat-ing every entry 40 times a
second, 0.62 / 2.32 / 5.78 % of CPU at 64 / 256 / 1 024. A one-variable A/B puts the walk at
+4.65 % throughput and −12.76 % p999 at 1 024, and halves the apparent penalty from −6.49 % to
−3.18 %. **Round 1's ladder carries the same bias**, and says so.

Relatedly, **the second `read(2)` per query is the Go runtime's own EAGAIN retry in
`internal/poll`**, not a protocol read: an AF_UNIX control differing only in blocking mode
measures **2.0004** reads per logical `Read` through the poller against **1.0002** blocking.
Real, 9.6 % of process CPU, and **unreachable from module code**.

### Two standing backlog items were refuted on their own numbers

#2661 — `canonicalRelTypesKey` has **zero occurrences at HEAD**. #2391 — `buildReadPhysical` is
**25.61 %, not 59.56 %**, and `ResolveLabelBitmap` is **52.75 %, not 10.42 %**, which inverts its
own priority ordering. Of thirteen reconciled backlog items, seven were supported and one
(#2404) refined: **58.31 % of the string-map cost is `populateRowCtx`**, which that item does not
name.

## What this release does not do

- **It does not change any ACID guarantee, any on-disk format, or any recovery path.** No file
  under `store/` was modified.
- **It does not change any openCypher behaviour.** The TCK baseline is untouched at 3 897/3 897
  and no `.feature` file changed.
- **It does not change any default numeric result.** The only changes that could have — the two
  float reassociations — were discarded.
- **It does not implement a new CSR pair-cache key** (#2866). The hit rate was measured instead:
  read-only **99.98 %**, the topology row **19.5 %** at `-spokes 400` and **8.5 %** at 4 000.
  Three candidate keys are stated with their soundness and rebuild cost, four are rejected — one
  on measurement rather than argument — and the recommendation is to **implement none yet**,
  because the ceiling of two of the three is a quantity no row measured here supplies.
- **It does not change MVCC visibility.** The prior art (#2860) **closed** that direction rather
  than opening it: GoGraph's predicate tests a contiguous frontier where PostgreSQL (`REL_17_5`,
  `heapam_visibility.c`) and Neo4j (`5.26.0`, `VersionContext`) both test a high-water mark **plus
  an exception array**. There is no array to search, so the predicate was never the problem.
  Memgraph (`v3.2.0`, `mvcc.hpp`) pays the same two dependent dereferences GoGraph pays and
  carries a `TODO: optimize with in-place copy` directly above the field. Four options are costed
  in [`docs/prior-art-mvcc-visibility-2026-09-16.md`](../docs/prior-art-mvcc-visibility-2026-09-16.md);
  **the decision is left to the user.**
- **It does not run the whole-tree soak.** `soak-artefacts/` is unchanged; see *Test evidence*
  below.
- **It does not close the 1.0.0 gates.** [`docs/semver.md`](../docs/semver.md) records three of
  four met, with the whole-tree soak against the release commit outstanding.

### One limitation of the Bolt figures, stated by the campaign itself

A GoGraph-free loopback control replying with **one** write measures **202 252 req/s**, against
which this server's 192 649 is **95.3 %** — 4.98 % of headroom. Round 1's claim that "no gain is
measurable above ~160 k q/s" was **wrong and is corrected**: its control replied with *two*
writes per request, so its ceiling was a two-writes ceiling, not the platform's. Putting the
control back into its two-writes shape reproduces the old 159 579 to 0.03 %, which validates the
instrument rather than the old conclusion.
