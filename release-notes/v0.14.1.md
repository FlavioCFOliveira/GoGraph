## Read this first

**`v0.14.0` returns wrong answers for a `MATCH` on an indexed property, and `v0.14.1` is
the fix.** The equality index seek ignored writes the statement itself had made, so a query
could both **lose rows the transaction had written** and **return rows that no longer
matched**. It needed no explicit transaction — one autocommit statement was enough. If you
are on `v0.14.0` and you have created any index or any uniqueness or existence constraint,
upgrade.

Three further consequences follow, and each is stated in full below:

1. **A store written by `v0.14.0` or earlier rebuilds its secondary indexes once on first
   open.** That is deliberate, requires nothing of you, and is what removes any index entry
   the fabrication defects could have written to disk.
2. **The Bolt server's four timeout defaults are now zero, which means disabled.** If you
   relied on the previous 30 s / 5 s defaults to reclaim idle clients, set them explicitly.
   The security consequence is set out under [*Security posture*](#security-posture).
3. **`make ci` now needs a running `rmp graph serve`.** This affects contributors, not
   consumers.

## Semantic-versioning rationale

Shipped as **PATCH** under [Semantic Versioning 2.0.0](https://semver.org/) as this project
applies it pre-1.0 ([docs/semver.md](../docs/semver.md)). The facts behind the digit are
recorded here in full, including the one that argues the other way, because a version
number that hides its own basis is worse than one that states it.

**What argues PATCH.** The release is overwhelmingly bug fixes that restore documented
behaviour: 26 of 50 commits are `fix`, and the six largest — #2814, #2778, #2792, #2793,
#2749, #2794 — each replace a wrong answer or a false report with a correct one. Nothing
was removed. No commit carries a `BREAKING CHANGE` footer or a `!` subject, verified over
the full commit bodies rather than the subjects alone. `go.mod` and `go.sum` did not move.

**What argues MINOR, stated plainly.** The exported surface **grew**, and
[docs/semver.md](../docs/semver.md) makes a new exported identifier the MINOR trigger. The
delta, derived by diffing the two trees' declarations rather than read off the commit log:

| | count |
|---|---:|
| new exported top-level declarations (types, funcs, methods, consts, vars) | **31** |
| new exported struct fields | **6**, of which **4** on pre-existing exported types |
| exported identifiers **removed or renamed** | **0** |
| exported signatures changed | **1** (source-compatible — see below) |
| exported constant **values** changed | **4** |

Every added declaration is in a package [docs/semver.md](../docs/semver.md) names as public
surface: `bolt/server`, `cypher`, `cypher/exec`, `graph/index`, `graph/index/btree`,
`graph/index/hash`, `store/recovery`, `store/snapshot`, `store/txn`. None is under
`internal/`, and none falls in one of the three excluded categories. The full itemisation is
in [CHANGELOG.md](../CHANGELOG.md) under *Added*.

**The two changes a caller can actually feel.**

- **Four exported default constants changed value** — `bolt/server.DefaultConnTimeout`
  (30 s → 0), `DefaultTxTimeout` (30 s → 0), `DefaultStatementTimeout` (30 s → 0) and
  `DefaultMaxTxIdleTime` (5 s → 0) — and `NewServer` now **refuses** a negative timeout
  where it previously coerced it to the default. A caller that read those constants, or that
  passed a negative value and got a working server, sees different behaviour from the same
  code. See [*The Bolt timeout posture*](#the-bolt-timeout-posture-changed-on-purpose).
- **`cypher/exec.NewColumnarExpand`'s declared return type changed** from `ChunkProducer` to
  the new `ChunkOperator`, and it is **not** a source break. `ChunkProducer` already embeds
  `Operator`, so `ChunkOperator` (`Operator` + `ChunkProducer`) has an **identical method
  set** and remains assignable to a `ChunkProducer` variable. Verified by compiling the
  `v0.14.0` caller shape unmodified against this tree:

  ```go
  var p exec.ChunkProducer
  var ok bool
  p, ok = exec.NewColumnarExpand(e)   // exit 0 against v0.14.1
  ```

- **Adding a field to an exported struct breaks an *unkeyed* composite literal.** Four
  pre-existing exported structs gained one: `cypher.EngineOptions` (`DisableIndexSeek`,
  `DisableExpandLabelPush`), `store/recovery.Result` (`MaxTxnOps`) and
  `store/snapshot.Manifest` (`IndexBuilderEpoch`). Keyed literals are unaffected, and keyed
  is the form every example and every doc uses.

**On-disk formats.** No format version was stepped. The snapshot manifest gains a third
**additive** field, `index_builder_epoch`, on the same terms as the two `v0.12.0`
additions: absent means never hydrate, so an older reader is unaffected and there is no
migration. Recorded in [docs/semver.md](../docs/semver.md)'s format table.

## Compliance mandates

Both non-negotiable invariants remain in force, and this release is where several of the
second one's guarantees stopped being merely asserted.

- **100 % openCypher TCK-compliant at the execution level** — **3 897 / 3 897 scenarios**,
  0 failed, 0 undefined, 0 inconclusive, against `const tckExecutionBaseline = 3897`. The
  constant is untouched and **no `.feature` file changed in this window**, so the population
  is exactly the one `v0.14.0` was measured against. This release **preserves** the
  compliance; it does not extend it.
- **100 % ACID-compliant.** Unlike the previous two releases, this one moved ACID paths, and
  each fix maps onto a named property:
  - **Isolation** — #2814. An index seek returned rows that violated the statement's own
    writes, and omitted rows the statement had written. Visible with no concurrency at all.
  - **Consistency** — #2778, #2792, #2793, #2799. Four routes by which a secondary index
    could disagree with the graph it indexes: three that could fabricate an entry, one that
    could lose one. #2797 extends the repair to stores already on disk.
  - **Durability** — #2749, #2780, #2794, #2530. Three routes by which a failure was
    reported as clean, and one by which committed data was made unreplayable.
  - **Atomicity** — #2750, #2783, #2784. Three values that committed durably and could then
    never be checkpointed, or were silently dropped on replay. All three are now refused at
    commit, where the caller can act.

  Verified by the WAL recovery tests in `store/wal` and `store/recovery` and the
  deterministic crash-injection battery in `internal/crashinject`.

## Highlights

### The index seek returned wrong answers, and needed no transaction to do it

**rmp #2814 — priority 9, severity 9.** This is the release.

`v0.14.0` planned an equality seek on a hash index and a range seek on a B-tree index by
reading the **committed** index only. A statement's own pending mutations were invisible to
it. Two wrong answers followed from that one cause:

- **Rows were lost.** A node created or updated by the same statement, whose new property
  value matched the predicate, was **not returned** — the committed index did not know
  about it yet.
- **Rows were fabricated.** A node whose indexed property had been changed *away* from the
  sought value was **still returned** — the committed index still carried the old entry.

No explicit transaction was required. A single autocommit statement that wrote and then read
the same indexed property was enough, which is why the defect reached a published release
without being caught: every existing test either wrote or read, and the seam is where the
two meet inside one statement.

**The fix declines rather than repairs.** Building a correct merged view of a committed
index plus a pending delta at plan time is the expensive answer; declining the access path
is the cheap and obviously-correct one. The engine now tracks the `(label, property)`
coordinates the transaction has dirtied and refuses the index access path for exactly those,
falling back to the label scan that has always been correct. Precision matters here — a
blanket "never seek on a write path" would have cost every write-path query its index — so
the guard is keyed per coordinate, and the test proves the precision as well as the fix.

**It was specified wrongly and re-measured.** The task prescribed a buffer-only guard. That
was **measured and could not reach the single-statement case**, because a single statement's
writes are not in the buffer the guard would have consulted. A plan-footprint half was added
after the measurement refuted the specification.

**Gated from both sides.** `cypher/index_seek_uncommitted_write_test.go` was mutation-tested
in both directions: disabling the guard turns all four behavioural cases red, and forcing a
blanket decline kills the precision cases. A test that only proved the fix would have passed
for "never seek", which is not the shipped behaviour.

`EngineOptions.DisableIndexSeek` is the kill switch, and
`TestPendingIndexDelta_DisableIndexSeekOption` asserts that turning the seek off changes the
**access path** and not the **answer**.

### Four ways an index could disagree with the graph

An index is a promise that a seek and a scan return the same rows. Four routes broke it.

- **#2778 — the backfill read uncommitted mutations.** `CREATE INDEX` populated from the
  live property bag, which contains writes no reader is entitled to see. A row that was
  never committed could be indexed, and a later seek would return it: a **fabricated row**,
  delivered with the authority of an index hit. The build now runs against a snapshot.
- **#2792 — `CREATE CONSTRAINT` had the same defect**, and its uniqueness seed is now taken
  from the same read its index is built from, so the two cannot disagree about what exists.
- **#2793 — `FinishBuild`'s replay resolved against the live bag.** Concurrent writes were
  reconciled at the end of the build against whatever state the graph had reached, so a
  write that landed mid-build could fabricate an entry. The replay now resolves against the
  change log it actually recorded. That log is **bounded** — `MaxBuildLogChanges` is 131 072
  — and reports reaching the bound as `ErrIndexBuildOverflow` rather than truncating
  silently, which is what the bounded-resource mandate requires of every new queue.
- **#2799 — `rewindConstraintDrop` read live state**, and this one is worth naming because
  the obvious fix was worse than the defect: it traded a fabricated entry for a **lost**
  one. Both failure directions are now covered.

**The repair had to reach stores already on disk, and #2797 is how.** A store written by an
affected build can hold fabricated entries inside its snapshot's index payloads, where no
amount of fixing the builder helps. The snapshot manifest now carries
`index_builder_epoch`, and a reader hydrates an `indexes/<name>.bin` payload **only** on an
exact match with `snapshot.CurrentIndexBuilderEpoch` (currently `1`). Absent, older or newer
all fall into the per-index rebuild path that already existed for a payload with no
watermark. The practical effect for a consumer: **a store written before this release
rebuilds its secondary indexes once, on first open.** No data is lost, nothing is required
of the operator, and the fabricated entries cannot survive it.

### The durability path stopped calling three different failures clean

- **#2749 — the checkpoint gate matched filenames.** Checkpoint phase 2 verified
  self-sufficiency by checking that the expected snapshot files *existed*, then discarded the
  WAL prefix. It never verified that the snapshot could be **read**. A snapshot that was
  present and unreadable therefore satisfied the gate, and the WAL that could have recovered
  the data was truncated behind it. Phase 2 now reads the snapshot back.
- **#2780 — the readback covered the reader but not the applier.** The fix above verified
  that recovery's *reader* could parse the image. Recovery also has an **applier**, and a
  mapper that parses can still fail to decode. The readback now decodes the mapper
  (`snapshot.VerifyMapperDecodable`), not merely parses it.
- **#2794 — `ReplayWAL` called corruption inside a committed frame benign.** A torn or
  truncated WAL *tail* is the normal state after a crash and is correctly treated as such.
  Genuine corruption inside a frame that was already acknowledged as durable is a different
  thing entirely, and it was being folded into the same "clean" verdict — contradicting the
  function's own documented contract that `IsClean` is the exact complement of the error
  return. It is now surfaced as `ErrCommittedTxnCorruptOp`.
- **#2530 — a producer op cap above the replay cap made committed data unreplayable.** The
  producer would accept a transaction larger than the replayer could ever read back, so the
  data was durable and unrecoverable at once. The cap is clamped at the reopen handoff and
  `recovery.Result` reports `MaxTxnOps`.

### Three values that committed durably and then blocked every checkpoint

Each of these is an atomicity failure of the same shape: the commit path accepted something
the snapshot path could never fold, so the data was durable but the store could never
checkpoint again. All three are now refused at commit, where the caller can see the refusal
and act on it.

- **#2750** — a property value between 1 GiB and 4 GiB.
- **#2783** — a nested property list. `encodeTxnListProp` had no `PropList` case, so a
  nested list survived the commit and **vanished on replay**: silent data loss, not a
  refusal. Now `ErrNestedPropertyList`.
- **#2784** — an edge-handle record count above the snapshot cap. Sizing the reproduction
  measured the write path's quadratic cost honestly: 16 k handles in 6.27 s, 32 k in 25.13 s
  (4.01×), 64 k in 101.81 s (4.05×), 128 k in 452.45 s (4.44×), which puts the cap's own
  boundary at **7.5 to 8.4 hours of CPU** on this host and is why the guard was chosen over a
  reproduction at full scale.

### Subqueries, projections and the counts they report

- **`COUNT { … }` block form now counts the rows its body returns** (#2675).
  `TranslateSubquery` dropped the body's trailing `RETURN`, so the count was taken over the
  wrong row set. The same defect in `existsSubPlan` is #2779 — and there the naive fix was
  **refuted by measurement** before the working one was found; the `SemiApply` inner schema
  is now isolated and the body's `RETURN` translated.
- **Pattern predicates and `EXISTS`/`COUNT` subqueries now run inside a writing statement**
  (#2660). The write path never wired the subquery and pattern evaluators, so a writing
  statement carrying either **refused to run at all**. Five `COUNT` block-form placements
  that bypassed `evalRow` entirely go with it (#2781) — including a property value, which is
  an ordinary expression and may therefore be a subquery.
- **Eighteen Cypher write-op call sites no longer discard the error the WAL layer uses to
  refuse** (#2747). A refused write was reported to the caller as a success.
- **A stale most-common-value estimate is demoted instead of being tagged exact** (#2772),
  and **the statistics now notice rows that left the label, not just writes** (#2785). The
  second is the sharper finding: `REMOVE p:Person` moved neither the delta counter nor the
  delete counter, dropped the live label count from 1 400 to 410, and the estimate was still
  tagged `estExact` at **100× wrong**. The drift numerator is now
  `Δ + max(0, N0 − N_live)`, read from **state** rather than from an event stream — because
  a counter sees only the routes it was wired into, and a label removed straight on
  `lpg.Graph` was measured leaving `Δ = 0` with the population down by 990.

**Read that table as a measurement of one commit, not as a property of the branch.** Every
subsequent commit that adds or deletes a declaration moves every figure in it, which is

### The Bolt timeout posture changed on purpose

Two tasks, in sequence, and the second reversed the first's reasoning rather than extending
it.

**#2806** raised `DefaultMaxTxIdleTime` from 5 s and `DefaultTxTimeout` /
`DefaultStatementTimeout` from 30 s, all three to 30 minutes, on the user's instruction.

**#2807** then asked what the peers actually practise, read their documentation, and found
the answer refuted the approach. PostgreSQL ships `statement_timeout`,
`transaction_timeout`, `idle_in_transaction_session_timeout` and `idle_session_timeout` all
at **0** — disabled — and advises against setting them globally. Neo4j ships
`db.transaction.timeout` at 0. **Neither uses a read deadline for liveness**: PostgreSQL
leans on TCP keep-alive, Neo4j on protocol-level NOOP chunks every minute.

**The number was never the defect.** The defect was that the server armed
`SetReadDeadline(now + ConnTimeout)` before **every** read of the post-handshake message
loop, and the reader goroutine sits in that read while the loop executes the client's own
statement. So the deadline ran against a **busy server**, not an idle client — a client
waiting for records it has just asked for sends nothing, and the deadline cannot tell that
apart from silence. Measured under #2806: with `ConnTimeout` at 100 ms, an autocommit
statement of about 900 ms had its connection closed at **110 ms**.

The four defaults are now `0` and the contract is three-way and explicit: **zero disables
the bound, a positive value sets it, and a negative one is refused**. Refused, not coerced —
the `if opts.X <= 0 { opts.X = DefaultX }` clauses are **deleted** rather than neutered,
because zero already means "no bound" at both points of use and those clauses were precisely
what swallowed a negative and substituted a number the caller never asked for.
`validateTimeouts` runs first in `NewServer` and returns `errors.Join` of one
`*NegativeTimeoutError` per offending field, so a caller with two mistakes learns both at
once.

**TCP keep-alive replaces the read deadline**, at 15 s idle + 3 probes × 5 s, and the test
for it had to be built against a **measured** trap rather than an assumed one:
`net.Listen`'s zero `ListenConfig` **already** enables `SO_KEEPALIVE` on accepted
connections at the Go defaults, so a test on a default listener could not have failed. The
test therefore serves a listener built with `KeepAlive: -1`, whose control arm reads the
option off, and asserts the server's own 15 s/5 s/3 through `RawConn.Control` and
`getsockopt` on the server-side accepted socket — values that match neither the Go nor the
platform default. A second measured trap: `SetKeepAliveConfig` applies `Enable` before the
parameters, so a poll that stopped at the enable bit read the platform defaults and failed as
a pure race.

**The bounds on count are untouched** — `MaxConnections` 1 024, `MaxOpenTxPerPrincipal`
2 048, `graph/mvcc.HorizonCapacity` 1 024 — which is what keeps the bounded-resource mandate
satisfied. PostgreSQL is unbounded in time and bounded by `max_connections` too.

**Fifteen dependent sites carried the old numbers as fact**, several written hours earlier by
#2806 and wrong again by #2807; all fifteen are corrected. **Four tests would have gone
vacuous rather than failed** — two slowloris tests passed `ConnTimeout: DefaultConnTimeout`,
which now resolves to zero and let the helper substitute its own value, so they had stopped
testing the default at all. Those now use a verbatim server.

### The count-store leaves report whether they walked, and how much

**#2777.** `AllNodesCountScan` and `LabelCountScan` both rendered `?` for db-hits, and the
question of what they *should* report had already been answered twice, differently. It is
settled here by **measuring which arm actually answers** on the shapes a real query plans.

The two leaves come out differently, and the difference is a seam rather than a cost.
`AllNodesCountScan`'s fallback is **inside** the operator — `Init` walks `WalkNodeIDs`
itself — so it can count it and now does: a real `0` when the O(1) live-node counter answers,
and one node reference per node id when it declines. The fallback is not hypothetical:
`ReadView.LiveNodeCountExact` declines whenever a node-life record is invisible to the
reader's snapshot, so a plain `MATCH (n) RETURN count(*)` takes the walk while any other
transaction holds an uncommitted create or delete. Measured on 64 nodes: **0** on a drained
substrate, **64** with one uncommitted `CREATE` open elsewhere, and **40** with an
uncommitted `DELETE`.

`LabelCountScan` stays `?`, and for a reason that is not the one previously given: its
record read did not disappear, it **moved below the interface** into
`lpg.Graph.LabelCountAsOf`, whose resolver reports only `(count, ok)`. The operator cannot
know which arm answered, and the correcting arm reads roaring containers rather than node
references — a unit this column does not have. A `0` would be false under any writer on the
label.

### Release-level: what a consumer actually feels

compilation of the candidate verified **byte-identical by sha256 for all 18 packages** —
interleaved with the arm order rotated every round, `n=6` per arm, load-gated, `uptime` and a
hot-process census bracketing all **192 invocations**, of which **192 exited 0** with **0

Apple M4, 10 cores, `darwin/arm64`, go1.27.1, no `-race`.

## Behaviour a caller can observe — the compatibility surface

Nothing here is a Go API removal. Everything here can change what your code does or how
fast it does it.

### An answer changes, for the better

- **A `MATCH` on an indexed property returns different rows than `v0.14.0` returned** — the
  correct ones (#2814). If you built a workaround for missing or spurious rows on an indexed
  predicate, remove it.
- **`COUNT { … }` returns a different number than `v0.14.0` returned** where the subquery
  body carries a trailing `RETURN` (#2675, #2779) — the correct one.
- **A writing statement carrying a pattern predicate or an `EXISTS`/`COUNT` subquery now
  runs** where it previously refused (#2660, #2781).
- **A write that the WAL layer refuses now reports an error** instead of succeeding (#2747).
- **`EXPLAIN`/`PROFILE` estimates render differently** where a most-common-value estimate
  was stale: it is now marked approximate rather than exact (#2772, #2785).

### A commit that used to succeed now fails

Three refusals, all of them replacing a durable-but-unusable state:

- a property value between 1 GiB and 4 GiB (#2750);
- a nested property list — previously accepted and then **silently lost on replay** (#2783);
- an edge-handle record count above the snapshot cap (#2784).

If your workload writes any of these, it now gets a typed error at commit rather than a
store that can never checkpoint again.

### The store rebuilds its indexes once

A store whose snapshot manifest carries no `index_builder_epoch` — every store written by
`v0.14.0` or earlier — rebuilds its secondary indexes on first open under `v0.14.1` (#2797).
Expect one slower open, proportional to the indexed population. Nothing is required of you.

### The Bolt server's defaults are disabled

`DefaultConnTimeout`, `DefaultTxTimeout`, `DefaultStatementTimeout` and
`DefaultMaxTxIdleTime` are all `0` (#2807). If you constructed a server with the zero
`Options` and relied on the previous bounds, **set them explicitly**. A negative value is
now an error from `NewServer` rather than a silent substitution.

### One exported signature changed, compatibly

`cypher/exec.NewColumnarExpand` returns `ChunkOperator` rather than `ChunkProducer`. The
method sets are identical, and the `v0.14.0` caller shape compiles unchanged — proven, not
assumed; the probe is in
[*Semantic-versioning rationale*](#semantic-versioning-rationale).

### What you must do

1. **Upgrade if you use any index or constraint.** #2814 is a wrong-answer defect in a
   shipped release.
2. **Expect one slow open** on an existing store, once.
3. **Set your Bolt timeouts explicitly** if you were relying on the defaults, and read
   [*Security posture*](#security-posture) before exposing the server to an untrusted
   network.
4. **Nothing else.** No configuration file changes, no data migration, no format step.

## Security posture

Disabling the four timeout defaults is a **deliberate trade**, and both sides of it are
recorded here rather than in a footnote.

**What it costs.**

- **An unauthenticated client can hold a connection slot indefinitely.**
  `DefaultHandshakeTimeout` bounds version negotiation only, so a client that completes the
  handshake and then falls silent **before LOGON** holds one of the 1 024 connection slots
  and its two goroutines for as long as its TCP stack answers keep-alive probes. PostgreSQL
  bounds that window with a separate `authentication_timeout` (1 minute by default);
  **GoGraph has no such bound today.** An operator exposing this server to an untrusted
  network should set `Options.ConnTimeout` explicitly until it does.
- **A live-but-silent client is no longer reclaimed at all.** TCP keep-alive reclaims a peer
  that has *vanished* — a pulled cable, a dropped NAT binding, a host gone without a FIN —
  within roughly 15 s + 3 × 5 s. It does not reclaim a peer whose stack answers probes while
  its process never sends another Bolt message. Where such a client left an explicit
  transaction open, that transaction pins the MVCC reclamation horizon and one of its 1 024
  slots for exactly as long as the connection lives, so **horizon exhaustion is reachable by
  silence alone**. The remedy is the operator's, and it is the one PostgreSQL offers for the
  same exposure: set `Options.MaxTxIdleTime` and `Options.ConnTimeout`.

**What it buys.** The server no longer kills its own busy connections. The old default cut
off a client that was waiting for the records it had asked for, which is an availability
defect in normal operation rather than a protection against an attacker.

**What did not change.** Every bound on **count** is untouched: `MaxConnections` 1 024,
`MaxOpenTxPerPrincipal` 2 048, `HorizonCapacity` 1 024. Saturation is still answered with a
typed error or backpressure, never a crash.

**Two integrity failures that presented as normal operation are closed.** A refused write
reported as a success (#2747), and corruption inside an already-committed WAL frame reported
as clean (#2794).

**No dependency advisory is in scope.** `go.mod` and `go.sum` did not move. `govulncheck`
runs inside `make ci`, which the release gate runs once.

## Premises refuted — the negative results

Sprint 357 carried a rule from sprint 350: **re-validate every premise at `HEAD` before
acting on it.** It earned its place again. These are the findings that produced no code, and
they are recorded because a refuted premise is a result.

- **#2814's prescribed fix could not reach the case it was written for.** The task specified
  a buffer-only guard. Measured, it could not see a single statement's own writes, because
  those are not in that buffer. The plan-footprint half exists because the measurement
  refuted the specification.
- **#2799's obvious fix traded a fabricated entry for a lost one.** Reading committed state
  instead of live state fixes the fabrication and introduces the opposite defect. Both
  directions are now tested.
- **#2779's naive fix was refuted.** Translating the subquery body's `RETURN` the way #2675
  did does not work for `existsSubPlan`; the inner schema has to be isolated first.
- **#2734's own headline figure was unreachable.** The task claimed a 48.7 % cost on the
  undirected engine, which this module does not support. The reachable defect was measured
  on the directed engine instead: `MATCH (a)-[r:R]-(b) DELETE r` wrote **2.000 frames per
  relationship**, 39.2 % of the delete transaction, and a variant carrying an `UNWIND` wrote
  **4.000**.
- **#2813 refuted half of #2812.** The premise that no index makes `MERGE` stop scanning is
  real; the premise that an `UNWIND`-bound key fails to plan the index nested-loop join is
  **not** — the cost gate is working as designed, and the seek is numeric-only rather than
  gated off. #2812 was carried to sprint 358 on that basis.
- **#2807 refuted #2806, one day later.** Raising the timeout defaults was the wrong repair
  for the defect they were raised to fix, and the peers' own documentation is what showed it.
- **Twelve tasks were withdrawn to the backlog** rather than rushed into this release. One
  casualty is recorded honestly: **#2630's measurements were taken and not committed.**

## What this release does not do

- **It does not extend openCypher coverage.** 3 897/3 897 is preserved, not raised. No
  `.feature` file changed.
- **It does not fix the indexed-`MERGE` plan** (#2812, carried to sprint 358). `MERGE` on a
  node pattern still walks the label posting list instead of probing the property index. The
  cost premise is measured and confirmed: **120 µs, 276 µs, 625 µs and 1.28 ms per operation
  at label populations of 1 000, 2 000, 4 000 and 8 000.** The prerequisite — a seek that no
  longer loses or fabricates rows — is what #2814 landed, so the work is unblocked rather
  than done.
- **It does not close the columnar estimate gap.** The 2026-09-08 erratum to
  [`release-notes/v0.14.0.md`](v0.14.0.md#erratum--v0141) establishes by measurement that the
  columnar fusion chains **do** have a logical node carrying an estimate and that the
  physical plan loses it in the lowering — 12 of 157 `-` instances in a fresh census are a
  real figure lost, and forcing the columnar recognisers to decline moves the estimate count
  from 71 to 83. **The code fix is a separate task.** What this release adds is the durable
  guard against the *claim* drifting again, `cypher/plan_estimate_columnar_gap_test.go`.
- **It does not pay the knowledge-graph provenance debt.** `provenance-no-node` reads
  **257 of 3 137 declarations in 164 touched files** against a baseline of 160, and the
  check no longer gates `ci` (#2796). Excluding a check that cannot converge is not the same
  as paying what it measures. Three further backlogs are carried at their baselines rather
  than repaired: `symbol-file-absent` 40, `symbol-pkg-mismatch` 68,
  `edge-type-undocumented` 118.
- **It does not add an `authentication_timeout`.** The window between handshake and LOGON is
  unbounded by default; see [*Security posture*](#security-posture).
- **It does not run the soak or nightly layers, and carries no production certification of
  its own.** The most recent certification was taken at the `v0.11.0` commit. The whole-tree
  soak layer has now gone unrun for an eighth consecutive cycle.
- **It does not measure latency percentiles** at the published concurrency levels. That gap
  is now eight cycles old.
- **It does not measure on-disk footprint growth.** No benchmark reporting bytes written to
  disk exists in both trees.
- **It is one host, one architecture.** Apple M4, 10 cores, `darwin/arm64`. Every floor and
  every adjudication bar in the benchmark report is a property of that host and does not
  transfer.
