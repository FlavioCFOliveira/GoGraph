# Benchmarks — v0.9.0

Headline benchmark and load-test numbers for the GoGraph **v0.9.0**
release, measured first-hand on the release candidate.

> **What moved in v0.9.0.** This release's performance work is entirely in
> the **Cypher read path** (the columnar `Chunk` execution model and the
> columnar-first planner) — see
> [Read-path performance](#read-path-performance-columnar-cypher). The
> **headline guard-band set below exercises the search algorithms**
> (`search`, `search/centrality`), whose hot paths are **byte-unchanged**
> in v0.9.0. Their allocation columns are therefore identical to
> [v0.8.1](v0.8.1.md) / [v0.8.0](v0.8.0.md); the absolute `ns/op` figures
> differ only within cross-session measurement variance on the same class
> of hardware. The authoritative per-change regression guard is
> [`scripts/bench_gate.sh`](../../scripts/bench_gate.sh), run **in-session**
> against each change's baseline as it landed; the per-release figures here
> are a fresh, self-consistent snapshot.

> Re-measure on your own hardware before relying on any absolute
> number; these are medians from documented runs, not a guarantee.

## Headline benchmarks

The canonical regression-gate set, as defined by
[`scripts/run_headline_bench.sh`](../../scripts/run_headline_bench.sh). Each
figure is the **median of 6 samples**, measured first-hand at the release
candidate.

| Benchmark | Package | ns/op (median) | B/op | allocs/op |
|-----------|---------|---------------:|-----:|----------:|
| `BenchmarkDijkstra_PostWarmup` | `search` | 8,308,053 (≈ 8.31 ms) | 0 | 0 |
| `BenchmarkDijkstra_Large` | `search` | 8,366,864 (≈ 8.37 ms) | 1,129,716 (≈ 1.077 MiB) | 4 |
| `BenchmarkBFSDirectionOpt_PowerLaw` | `search` | 30,587,182 (≈ 30.6 ms) | 0 | 0 |
| `BenchmarkYen_K100` | `search` | 14,579,259 (≈ 14.58 ms) | 459,536 (≈ 449 KiB) | 1,280 |
| `BenchmarkBrandes_RandomGraph` | `search/centrality` | 8,178,889 (≈ 8.18 ms) | 62,208 | 10 |

The two post-warmup traversal paths (`Dijkstra_PostWarmup`,
`BFSDirectionOpt_PowerLaw`) allocate **zero** bytes per call, confirming the
zero-allocation hot-path mandate still holds for the reusable-state query
forms. Every allocation column (`0`, `4` / ≈ 1.077 MiB, `0`, `1 280` /
≈ 449 KiB, `10` / 62 208 B) is **identical to `v0.8.1` and `v0.8.0`**,
confirming no hot-path allocation regression; these benchmarks are not on
any code path v0.9.0 changed.

## Read-path performance (columnar Cypher)

The substantive performance work in v0.9.0 is a **column-major read path**
for the common `MATCH (n) WHERE <predicate> RETURN <scalar properties>`
shape: values are kept in typed, column-major buffers and boxed to
`expr.Value` only at the sink. Each figure below is the `benchstat` median
(n = 6) reported by the landing change, on the same Apple M4 / go1.26.5
environment. Correctness is byte-identical to the row path **by
construction** — the column fillers classify each value with the same
functions the row-at-a-time path uses — and the openCypher TCK holds at
3 897 / 3 897.

| Path | Benchmark | Before | After | Delta |
|------|-----------|-------:|------:|-------|
| Scalar-property projection (P1–P3) | `BenchmarkEngReadProject` (allocs/op) | 5,309 | 89 | **−98.3 %** |
| Scalar-property projection (P1–P3) | `BenchmarkEngReadProject` (ns/op) | ≈ 234 µs | ≈ 53.8 µs | **−77 %** |
| `WITH`-projection passthrough | `BenchmarkWithFilterPassthrough` (allocs/op) | 5,324 | 118 | **−97.8 %** |
| Grouping-key hashing | `BenchmarkAggGroupScalar` (allocs/op) | 15,598 | 1,889 | **−87.9 %** |
| Planner columnar-first (concurrent) | filtered scalar projection, 60k nodes (allocs/op) | 182,559 | 118 | **≈ 1 550× fewer** |
| Planner columnar-first (concurrent) | filtered scalar projection, 60k nodes (ns/op) | 6.08 ms | 1.94 ms | **≈ 3.1× faster** |

Supporting read-path changes with no dedicated headline benchmark:
`count(*)` over a bare label scan is pushed down to an O(1) index read
(8134796); the `graph/lpg` tombstone read path is lock-free, restoring read
scaling under concurrency (95da80d); non-test structs are field-reordered to
the size-optimal layout, removing compiler padding across 33 types and
trimming ≈ 7.5 KB of operator allocation size and GC mark work (a5d0fe7);
and all-scalar Bolt `RECORD` rows are streamed through a typed encoder with
no per-cell boxing (2749809).

## Load test — read-path concurrency sweep

CLAUDE.md requires a load-test report "at multiple concurrency levels
(1, 8, 64, 256, 1024 goroutines)". As in
[v0.8.1](v0.8.1.md#load-test--read-path-concurrency-sweep), we sweep
`GOMAXPROCS` over the `b.RunParallel` hot-key intern benchmark — the
tightest shared-state contention point in the read path, where every
goroutine interns the **same** key and competes for the same cache line.
Each figure is the **median of 5 samples**, measured first-hand at the
release candidate.

| Goroutines (`GOMAXPROCS`) | ns/op (median) | B/op | allocs/op |
|--------------------------:|---------------:|-----:|----------:|
| 1 | 8.04 | 0 | 0 |
| 8 | 71.90 | 0 | 0 |
| 64 | 88.33 | 0 | 0 |
| 256 | 88.45 | 0 | 0 |
| 1024 | 88.25 | 0 | 0 |

**Reading the sweep.** From 8 to 1024 goroutines (a 128×
over-subscription of the 10 physical cores) per-op latency stays **flat at
≈ 72–88 ns/op with zero allocations** — the structure degrades gracefully
and predictably under massive over-subscription rather than collapsing, so
the bounded-resource and lock-contention mandates hold. The figures are on
par with `v0.8.1` (which reported ≈ 89–95 ns/op at the same levels) and
marginally better at the highest concurrency.

## Reproduce

```
# Headline / guard-band set (median of 6)
./scripts/run_headline_bench.sh

# Read-path concurrency sweep (median of 5)
go test -run='^$' -bench='^BenchmarkMapper_Intern_HotKey_Parallel$' \
  -benchmem -cpu=1,8,64,256,1024 -count=5 ./graph/

# Columnar read-path benchmarks
go test -run='^$' -bench='^(BenchmarkEngReadProject|BenchmarkWithFilterPassthrough|BenchmarkAggGroupScalar)$' \
  -benchmem -count=6 ./cypher/...
```

Per-change (rather than per-release) tracking lives in
[`history/`](history/) via
[`scripts/bench-history.sh`](../../scripts/bench-history.sh); the narrative
ledger is [`history/LEDGER.md`](history/LEDGER.md). The prior authoritative
baselines are [v0.8.0](v0.8.0.md) / [v0.8.1](v0.8.1.md).
