# Three-way head-to-head — consolidated results

First empirical comparison of GoGraph, Neo4j and Memgraph in this project's history.

**Setup.** Apple M4 (10 cores, 32 GB), macOS. Neo4j 5.26 Community and Memgraph 2.22.0 in Docker on
colima (6 CPU / 14 GB VM). Neo4j given 2 GB heap + 2 GB page cache. GoGraph runs in-process
(no serialisation) — its intended mode, and a handicap in GoGraph's favour that is stated openly.
Identical deterministic dataset (PCG seed 31,1), identical `UNWIND` batches, identical Cypher except
for index DDL syntax and Memgraph's `*BFS` in place of `shortestPath()`. Returned row counts were
cross-checked across every target before any timing was compared — all matched.

Harness: `bench/comparison/threeway_test.go` (build tag `threeway`).

## Scale A — 2 000 nodes / 19 931 edges, all four targets

Included because it is the only run where all four targets completed, and because the
`gograph-embedded` vs `gograph-bolt` pair isolates GoGraph's own transport tax.

| 2-hop DISTINCT | 845 µs | 1.152 ms | 7.134 ms | 373 µs |

| group-by + order + limit | 254 µs | 369 µs | 6.349 ms | 1.329 ms |

| **triangle count** | **2.164 s** | **1.703 s** | **26.285 ms** | **20.035 ms** |

**GoGraph's Bolt transport tax** (embedded → bolt, same engine, in-process loopback):
+46 µs on a single-node write, +88 µs on a point lookup, +264 µs on a global count. So roughly
50–250 µs per round trip. Neo4j and Memgraph pay a comparable-or-larger tax plus VM crossing, which
is why the `gograph-bolt` column — not `gograph-embedded` — is the fair comparison against them.

At this small scale GoGraph looks strong on almost everything. That impression does not survive scale.

## What the scaling comparison says

Between scale A and scale B the data grows 10×. GoGraph's costs grow far faster than either rival's:

| Query | GoGraph A→B | Neo4j A→B | Memgraph A→B |
|---|---|---|---|
| 1-hop expand | 845 µs → 8.711 ms (**10.3×**) | 4.231 → 0.937 ms (0.2×) | 601 µs → 286 µs (0.5×) |
| 2-hop DISTINCT | 845 µs → 14.046 ms (**16.6×**) | 7.134 → 1.260 ms (0.2×) | 373 → 341 µs (0.9×) |
| triangle | 2.164 → 22.506 s (**10.4×**) | 26.3 → 437.5 ms (16.6×) | 20.0 → 210.4 ms (10.5×) |
| LOAD | 19.31 s → 35 m 33 s (**110×** for 10× data) | 1.85 → 2.39 s (1.3×) | 0.127 → 0.977 s (7.7×) |

Neo4j and Memgraph *improve* in absolute terms between A and B on several queries, because at scale A
they were dominated by fixed per-query overhead (JVM/driver/VM round trip) that scale B amortises.
GoGraph has almost no fixed overhead — which is why it wins at scale A — but its per-query cost then
grows roughly linearly with the graph, which is the signature of scanning where the rivals seek.

**The load figure is the most severe.** 10× more data cost GoGraph 110× more load time, i.e. the load
path is quadratic in graph size. Neo4j grew 1.3× and Memgraph 7.7× for the same 10×.

## Memory (indicative only)

Container RSS after loading the identical 20 000-node / 199 941-edge dataset:

| Engine | RSS |
|---|---|
| Neo4j 5.26 | 2.505 GiB |
| Memgraph 2.22 | 101.6 MiB |

**Do not read these as a like-for-like memory comparison.** Neo4j's figure is dominated by the 2 GB
heap + 2 GB page cache it was explicitly configured to pre-allocate, not by the data. Memgraph's
includes a fixed baseline of tens of MB. GoGraph is not in this table because it is in-process, so
container RSS is not defined for it; Stream 3 measured GoGraph's data structures directly and that
is the authoritative memory evidence.

## Honest reading of these numbers

1. **GoGraph genuinely wins** on: global count (its exact count store beats both rivals' approaches),
   multi-label conjunction (54× — the Roaring bitmap path is excellent), single-node writes (21×),
   and small-graph latency generally, where having no server, no JVM and no serialisation is decisive.
2. **GoGraph genuinely loses**, badly and at scale, on: **traversal** (30–60×) and **cyclic patterns**
   (107×) — which is the core competence of a graph database — and on **bulk loading** (2 184×).
3. The losses are not diffuse. They trace to a small number of identified defects: numeric properties
   are never indexed, correlated `UNWIND`-driven `MATCH` never reaches an index, bound-destination
   expansion has no `ExpandInto`, and there is a residual per-expand constant that Stream 5 was asked
   to explain. Each is a bounded engineering problem, not an architectural dead end.
4. **Neo4j Community is not Neo4j's best.** These figures exclude the Enterprise pipelined/Morsel
   runtime. Read the Neo4j column as a floor for Neo4j, not a ceiling.
5. The round-1 verdict that "gaps are BREADTH not core quality" is **refuted for query execution**.
   On the measured evidence the core traversal path is where GoGraph is weakest relative to both
   incumbents, and it is weakest precisely at the scales where a graph database earns its keep.
