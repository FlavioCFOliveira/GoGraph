# Benchmarks — v0.10.0

Headline benchmark and load-test numbers for the GoGraph **v0.10.0**
release, measured first-hand on the release candidate.

> **What moved in v0.10.0.** This release's performance work is entirely in
> the **Cypher query planner and execution engine** — the exact relationship
> count-store and planner statistics, the count-store-gated reordering
> peepholes, the columnar/vectorised execution deepening, and the broadening
> of automatic intra-query parallelism. See
> [Planner and execution-engine performance](#planner-and-execution-engine-performance).
> The **headline guard-band set below exercises the search algorithms**
> (`search`, `search/centrality`), whose hot paths are **byte-unchanged**
> in v0.10.0. Their allocation columns are therefore identical to
> [v0.9.0](v0.9.0.md); the absolute `ns/op` figures differ only within
> cross-session measurement variance on the same class of hardware. The
> authoritative per-change regression guard is
> [`scripts/bench_gate.sh`](../../scripts/bench_gate.sh), run **in-session**
> against each change's baseline as it landed; the per-release figures here
> are a fresh, self-consistent snapshot.

> Re-measure on your own hardware before relying on any absolute
> number; these are medians from documented runs, not a guarantee.

## Headline benchmarks

The canonical regression-gate set, as defined by
[`scripts/run_headline_bench.sh`](../../scripts/run_headline_bench.sh). Each
figure is the **median of 6 samples**, measured first-hand at the release
candidate.

| Benchmark | Package | ns/op (median) | B/op | allocs/op |
|-----------|---------|---------------:|-----:|----------:|
| `BenchmarkDijkstra_PostWarmup` | `search` | 7,969,444 (≈ 7.97 ms) | 0 | 0 |
| `BenchmarkDijkstra_Large` | `search` | 8,037,332 (≈ 8.04 ms) | 1,129,088 (≈ 1.077 MiB) | 4 |
| `BenchmarkBFSDirectionOpt_PowerLaw` | `search` | 28,935,085 (≈ 28.9 ms) | 0 | 0 |
| `BenchmarkYen_K100` | `search` | 14,253,317 (≈ 14.25 ms) | 459,651 (≈ 449 KiB) | 1,280 |
| `BenchmarkBrandes_RandomGraph` | `search/centrality` | 7,973,402 (≈ 7.97 ms) | 62,208 | 10 |

The two post-warmup traversal paths (`Dijkstra_PostWarmup`,
`BFSDirectionOpt_PowerLaw`) allocate **zero** bytes per call, confirming the
zero-allocation hot-path mandate still holds for the reusable-state query
forms. Every allocation column (`0`, `4` / ≈ 1.077 MiB, `0`, `1 280` /
≈ 449 KiB, `10` / 62 208 B) is **identical to `v0.9.0`**, confirming no
hot-path allocation regression; these benchmarks are not on any code path
v0.10.0 changed.

## Planner and execution-engine performance

The substantive performance work in v0.10.0 is in the **Cypher query planner
and execution engine**. Each optimisation was benchstat-gated against its own
baseline at the change that landed it, on the same Apple M4 / go1.26.5
environment; the figures below are those first-hand landing measurements. The
full per-change records — with the raw benchstat output, the differential
byte-identity proofs, and the guard-band confirmation for each step — live in
[`history/LEDGER.md`](history/LEDGER.md) (rows **0020–0025**). Every one of
these changes is either result-identical by construction, gated so it fires
only when provably result-identical, display-only, or a byte-identical-to-
serial parallel combine; the openCypher TCK held at 3 897 / 3 897 throughout.

### Count-store-gated reordering (rows 0020, 0022)

| Optimisation | Benchmark | Before | After | Delta |
|--------------|-----------|-------:|------:|-------|
| Min-cardinality multi-label anchor scan (#2077) | `BenchmarkMinLabelScanSelective` | 18.4 ms / 836 KB / 99.8k allocs | 223.6 µs / 37.8 KB / 818 allocs | **≈ 82× faster, ≈ 22× less memory, ≈ 122× fewer allocs** |
| Single-edge anchor-swap, OUT-only (#2090) | `BenchmarkAnchorSwapHub` | 5 967.7 µs / — / 39 685 allocs | 468.8 µs / — / 212 allocs | **−92 % time (≈ 12.7×), −99.5 % allocs, −18.5 % B/op** |
| Disjoint scan-component reorder (#2091) | `BenchmarkJoinReorderDisjoint` | 23.889 ms / 32.97 MiB / 1 259.8k allocs | 7.777 ms / 5.52 MiB / 359.4k allocs | **−67 % time (≈ 3.1×), −83 % B/op, −71 % allocs** |

Each peephole is inert on non-matching queries (the trigger shape is absent),
so the curated LDBC suite is **byte-identical** ON vs OFF; the result multiset
is proven identical by a differential harness.

### Columnar / vectorised execution deepening (row 0024)

| Optimisation | Benchmark | Before | After | Delta |
|--------------|-----------|-------:|------:|-------|
| Columnar aggregation, SoA scatter-add (#2104) | `BenchmarkColumnarAgg_SumCountGroupBy` (1M-row group-by) | 3 146 647 allocs/op | 803 allocs/op | **−99.97 % allocs, −43 % time** |
| `Expand` → `ChunkProducer` + filter-over-traversal (#2106) | `BenchmarkExpandFilter` (~64k edges) | 181 100 allocs/op | 25 allocs/op | **≈ 7 200× fewer allocs, B/op ≈ 4.1× lower** |
| Columnar hash-join, late materialisation (#2105) | `BenchmarkHashJoinDisconnectedEquiJoin` | — | — | **−22.4 % allocs, −0.84 % B/op, −5.7 % time** |

The chunk pipeline now stays unboxed end-to-end through scan → expand →
filter → aggregation; exact int/float semantics (CIP2016-06-14) are preserved.

### Automatic parallelism broadening (row 0025)

| Optimisation | Benchmark | Result |
|--------------|-----------|--------|
| Parallel `min` / `max` aggregation (#2111) | `BenchmarkParallelAggregate_Concurrent` | **≈ 2.83×** single-query (conc = 1); **parity at conc = 64** (no regression under saturation) |
| `O(1)` count-pushdown (#2113) | `BenchmarkCountPushdown_O1` vs `_FullScan` (200k nodes) | **5.516 µs vs 53.76 ms (≈ 9 700×, −99.99 %)**; allocs 30 vs 399.6k; independent of N |
| `budget == 1` inline-serial short-circuit (#2115) | `BenchmarkParallelAggregate_Concurrent` | conc = 8 **−2.43 %**, conc = 64 **−3.29 %** vs no short-circuit — removes per-query goroutine/channel/context overhead at budget 1 |

The `min` / `max` combine is position-carrying and byte-identical to the
serial left-fold for every tie representation (int/float, ±0, `NaN`); float
`sum` / `avg`, int `sum`, `collect`, `percentile`, and `stdev` stay serial
permanently.

### Write-path neutrality (rows 0021, 0023)

The count-store and the statistics collector are on the **write** path, so
their key acceptance criterion is **zero write regression**:

- **Count-store** (`BenchmarkEngWriteAutocommit`, n = 10): allocs/op
  **34 → 34** (all samples equal), sec/op +0.51 % (noise), B/op +2.36 %
  (fixed `O(1)` struct fields) — the #2051 alloc-explosion failure mode is
  provably absent.
- **Statistics collector** (`BenchmarkEngWriteAutocommit`, n = 10): with the
  collector lazy, a statistics-free write is byte-identical to pre-statistics
  (allocs 34 → 34, B/op flat, `p = 0.182`); with statistics active, the same
  property-write workload is **allocs/op and B/op byte-identical**
  DISABLED vs ENABLED (`p = 1.000`) — an `O(1)`, zero-allocation atomic delta
  per tracked `(label, property)`.

## Load test — read-path concurrency sweep

CLAUDE.md requires a load-test report "at multiple concurrency levels
(1, 8, 64, 256, 1024 goroutines)". As in
[v0.9.0](v0.9.0.md#load-test--read-path-concurrency-sweep), we sweep
`GOMAXPROCS` over the `b.RunParallel` hot-key intern benchmark — the tightest
shared-state contention point in the read path, where every goroutine interns
the **same** key and competes for the same cache line. Each figure is the
**median of 5 samples**, measured first-hand at the release candidate.

| Goroutines (`GOMAXPROCS`) | ns/op (median) | B/op | allocs/op |
|--------------------------:|---------------:|-----:|----------:|
| 1 | 7.68 | 0 | 0 |
| 8 | 73.23 | 0 | 0 |
| 64 | 89.71 | 0 | 0 |
| 256 | 89.62 | 0 | 0 |
| 1024 | 89.24 | 0 | 0 |

**Reading the sweep.** From 8 to 1024 goroutines (a 128×
over-subscription of the 10 physical cores) per-op latency stays **flat at
≈ 73–90 ns/op with zero allocations** — the structure degrades gracefully and
predictably under massive over-subscription rather than collapsing, so the
bounded-resource and lock-contention mandates hold. The figures are on par
with `v0.9.0` (which reported ≈ 72–88 ns/op at the same levels).

### Intra-query parallelism under concurrency

The release-specific parallel-aggregation load test (a real shared
`ParallelGovernor`, one `Engine`, `MATCH (n) RETURN min(n.v)` over a
200k-node graph, where one op is a batch of `conc` concurrent queries) was
measured first-hand at the landing change (`dc5ec3d`,
[`history/LEDGER.md`](history/LEDGER.md) row 0025):

| Concurrency (`conc`) | Parallel | Serial (`DisableParallelScan`) | Reading |
|---------------------:|---------:|-------------------------------:|---------|
| 1 | 29.59 ms | 83.84 ms | single-query parallel **≈ 2.83×** (idle-core-bound) |
| 8 | 231.2 ms | 211.3 ms | −8.6 % residual (pre-existing governor transition-zone over-subscription, #2125) |
| 64 (saturated) | 1.522 s | 1.516 s | **parity (`p = 0.739`): no regression** |

Intra-query parallelism is idle-core-bound: the win is at low concurrency, and
the governor correctly throttles it to neutral under saturation, honouring the
no-regression mandate.

## Reproduce

```
# Headline / guard-band set (median of 6)
./scripts/run_headline_bench.sh

# Read-path concurrency sweep (median of 5)
go test -run='^$' -bench='^BenchmarkMapper_Intern_HotKey_Parallel$' \
  -benchmem -cpu=1,8,64,256,1024 -count=5 ./graph/

# Planner / execution-engine benchmarks (each is an A/B pair on one binary)
go test -run='^$' -benchmem -count=6 ./bench/cypher_ldbc/ \
  -bench='^Benchmark(MinLabelScanSelective|AnchorSwapHub|JoinReorderDisjoint|HashJoinDisconnectedEquiJoin)_'
go test -run='^$' -benchmem -count=6 ./cypher/exec/ \
  -bench='^Benchmark(ColumnarAgg|ExpandFilter)_'
go test -run='^$' -benchmem -count=10 ./cypher/ \
  -bench='^Benchmark(ParallelAggregate_Concurrent|CountPushdown_O1|CountPushdown_FullScan)$'
```

Per-change (rather than per-release) tracking lives in
[`history/`](history/) via
[`scripts/bench-history.sh`](../../scripts/bench-history.sh); the narrative
ledger is [`history/LEDGER.md`](history/LEDGER.md) (rows 0020–0025 cover this
release). The prior authoritative baseline is [v0.9.0](v0.9.0.md).
