# Benchmarks — v0.15.0

The per-release measured record for `v0.15.0`, the twentieth release and the first whose
substance *is* its measurements. Sprint 362 turned the machine into a controlled performance
laboratory for three campaigns — Bolt extreme concurrency, Cypher statement parsing, and a
whole-surface sweep driven by the examples — and **thirteen measured improvements shipped**.

**Read [§0](#0-what-this-record-is-not) first.** Unlike `v0.14.2`, this release ran **no
release-time benchmark campaign at all**. Every number below was measured *during development*,
by the task that shipped the change, against that task's own control. That is a different — and
in one specific way weaker — kind of evidence than a release campaign, and §0 says exactly how.

**Headline: thirteen improvements, every one measured against an interleaved byte-identical
control, and the two largest are allocation defects rather than CPU costs.** The BFS frontier
queue fell from **2 026 768 allocations to 433** on a 100 000-user graph, taking that example's
CPU down **34.1 %**; the label bitmap stopped being cloned on every scan, for **−28.71 %
geomean** with the clone chain leaving the allocation profile entirely. Against that,
**four optimisations were built in full, measured, and discarded** because the measurement
refused to support them, and **no default numeric result moved anywhere in the release.**

## 0. What this record is NOT

This section is first because a benchmark report that buries its absences misrepresents the
cycle. Five things a reader may reasonably expect are not here.

**0.1 — No release-time benchmark campaign was run.** There is no `v0.15.0`-versus-`v0.14.2`
whole-module comparison in this document, because none was taken. Benchmark *execution* left
the release path in `v0.14.2` (see [`../release.md`](../release.md)), and this release did not
re-elect to run one. Every figure here is a development-time A/B measured by the task that
shipped the change, at that task's own commit, against its own control arm.

**What that costs, concretely.** A release campaign extracts both release trees and re-measures
them side by side on one host in one session. A development-time A/B measures one change against
the code immediately before it. So this record can say *what each change did* with high
confidence, and it **cannot** say what the thirteen changes did **in combination**, nor whether
anything regressed in code no task touched. **No claim of a whole-release delta appears below,
and none should be inferred by adding the rows up.**

**0.2 — No load test at the published concurrency ladder was run for this release.**
`CLAUDE.md` asks that each release ship latency and throughput at 1, 8, 64, 256 and 1 024
goroutines, recorded in `docs/benchmarks/`. **That was not done as a release exercise.** The
Bolt campaign drove exactly that ladder — 1/8/64/256/1 024 plus a saturation rung — but it did
so as *campaign* evidence at its own commits, to rank and then verify its own changes. The
ladder figures in [§3.1](#31-bolt-server) are those, and they are labelled as such. **A reader
wanting a release-commit load test will not find one here; it does not exist.**

**0.3 — Two of the three campaigns' raw artefacts are not in this repository.** Only the
Cypher-parsing and plan-cache work deposited raw series under `docs/benchmarks/`; those are
reproduced in full in [§4](#4-the-raw-series-that-are-in-this-repository) and are the strongest
evidence in this document. The **Bolt** and **whole-surface** campaigns wrote their profiles,
traces and benchstat output to a scratch root outside the repository, which no longer exists.
Their figures are attributed to the **task closing summaries in `rmp`** and to the **campaign
documents under `docs/`**, both of which are durable records — but they are a *transcription* of
a measurement, not the measurement. Every such row is marked **[campaign record]** in
[§3](#3-the-thirteen-shipped-results) so a reader can tell the two grades of evidence apart.

**0.4 — Two conventional companions are absent.** No **coverage** figure is published: the
coverage gate left `make ci` on 2026-09-15 and was not run deliberately for this release, so no
percentage is claimed. No **whole-tree soak** was run; `soak-artefacts/` is unchanged and still
predates `v0.9.0`. No production certification was taken in this window.

**0.5 — The `benchstat` p-values below are not release-level significance.** They are
within-experiment p-values from the task that ran the experiment, on that task's sample size.
Where a task ran two independent realisations, both are given. Where a figure rests on a single
sample, it says so.

## 2. Method, and the floor it establishes

### 2.1 The rule every result in this release obeys

**Interleaved A/B against a byte-identical noise control, in the same session.** Not a
before-run followed by an after-run; arms alternate within one invocation or one rotated
sequence, and a control arm that is *identical by construction* runs alongside them.

This is load-bearing, not ceremonial. **On this host a byte-identical control has read 22 of 36
flat-by-construction rows as statistically "significant", spanning −11 %…+4 %.** That is not a
figure from this sprint: it was established in **sprint 313** against `bench-history.sh`, which
compares runs back-to-back by construction, and it has governed every A/B in this project since
(LEDGER row 0031; cited in [`cyclic-join-2026-07-30.md`](cyclic-join-2026-07-30.md),
[`expand-into-symmetric-swap-2026-07-29.md`](expand-into-symmetric-swap-2026-07-29.md),
[`reltype-column-2026-08-29.md`](reltype-column-2026-08-29.md) and
[`../mvcc-p0-measurement.md`](../mvcc-p0-measurement.md)). The sprint-362 merge commit
`19138042` restates it as this sprint's governing constraint.

**A same-process A/B is immune to it**: one binary, one fixture, one thermal state, with
`-count` interleaving the arms — which is why every result below is shaped that way. A
comparison made here without a control means nothing, and several results below exist only
because a control caught an apparent effect that was not real.

### 2.2 The floors, per campaign — they are not transferable

There is no single project noise floor, and this release re-derived one per experiment rather
than reusing a number.

| Parsing laboratory replica — `Visit` | **11.97 %** | same — it is a *difference of two large prefixes*, which is why it is an order of magnitude wider |
| Bolt, round 1 | 0.57 % | **[campaign record]** |
| Bolt, round 2 re-derived at the faster HEAD | **1.08 %** | **[campaign record]** — *a faster server has a wider floor* |
| Bolt, four transaction shapes | 1.04 – 3.91 % | **[campaign record]** — "round 2's 1.08 % does not transfer" |
| Centrality harness (#2870's control) | **+0.81 % at p=0.017** | **[campaign record]** |

**The last row is the resolution floor that bounds what this release can claim.** A
byte-identical control that reads +0.81 % *significant* means any centrality effect smaller
than roughly 1 % is unresolvable on this host, whatever its p-value. That is precisely the
result that killed the two float reassociations in [§6.1](#61-two-float-reassociations-built-in-full-and-discarded).

**The plan-cache floor is the counter-example and is worth reading.** Its byte-identical arms
(`A1` vs `A2`) came back `~` on **every single row**, p=0.143–0.813. Different harness,
different floor. This is why §2.2 exists rather than a single headline number.

### 2.3 Two method corrections this sprint made, which change how its numbers read

**`pprof` defaults were falsifying attributions.** The campaign ran `-nodefraction=0`
throughout, because pprof's default drops every node under 0.5 % and on this campaign's own
precedent that **silently hid 4.66 s of a 20.70 s total**. `pprof -show=<pkg>` is **never**
used: it redistributes a dropped node's cost into its nearest retained ancestor, so per-package
"shares" overlap rather than partition — it inflated one split **3×**.

**Every replacement acceptance gate was made absolute rather than a profile share.** A share of
a profile that a *sibling* fix shrinks reads higher for unchanged absolute cost. This is why
#2864's and #2865's gates below are stated in seconds, not percentages.

### 3.1 Bolt server

Driven at the **1 / 8 / 64 / 256 / 1 024-connection ladder plus a saturation rung** — the
ladder `CLAUDE.md` names — across three profiling rounds. **[campaign record]** throughout;
see [`../campaign-bolt-extreme-concurrency-2026-09-16.md`](../campaign-bolt-extreme-concurrency-2026-09-16.md).

**#2834 — the two response writes coalesced into one per query** (`a1057d5c`). The server
flushed on every non-RECORD message, performing **2.00 `write(2)` per query** where the client
delivered RUN+PULL in 1.00: **42.06 % of all process CPU at 256 connections**, flat in
connection count, **800 761 syscalls for 400 000 queries**.

| Connections | `write(2)`/query | throughput | p99 |
|---|---:|---:|---:|
| 64 | 2.000 → **1.001** | **+20.66 %** | **−17.84 %** |
| 256 | 2.000 → **1.002** | **+19.61 %** | — |
| 1 024 | 2.000 → **1.005** | **+16.99 %** | — |
| saturation | — | **+19.71 %** | — |

Against a same-versus-same floor of **0.57 %**. Syscall counts from `runtime/trace`. Verified
independently at 256 connections: **192 540 q/s** against a 161 283 q/s baseline. **Round 2
re-measured the same gains at the new HEAD** — +20.19 / +19.45 / +19.94 / +16.80 % — with the
floor re-derived at 1.08 %.

**#2835 — the per-rejection log bounded per interval, and its argument made lazy**
(`a1057d5c`). Measured with all arms in **one binary**, so interleaved by construction:

| Arm | cost | allocation |
|---|---:|---:|
| unbounded (before) | 547.3 ns | 80 B / 4 allocs |
| **bounded (shipped)** | **34.9 ns** | **0 B / 0 allocs** |
| bounded, level off | 4.5 ns | 0 B / 0 allocs |

**−93.6 %**, reproduced independently at `-count=5`: unbounded 546.6–550.1 ns, bounded
34.47–35.09 ns. End to end, **500 refused connections produce 1 log line** while
`bolt.server.conn.rejected` counts **exactly 500**; `RemoteAddr` is resolved **0** times at
`LevelError` and **1** time at `LevelWarn` across 100 refusals.

**#2839 — `propMapShards` 64 → 256** (`13ad0ed2`). Landed explicitly as *a level shift, not a
fix for the scaling behaviour*.

| Rung | throughput | note |
|---|---:|---|
| 64 connections | **+7.0 %** | n=8 interleaved, order-rotated, **no overlap at all** between arms |
| 1 024 connections | **+13.3 %** | same |
| p99 / p999 | **−16.1 % / −14.8 %** | |
| one reader vs one writer | **−36.5 %** | |

Floor set by two **byte-identical binaries** that stayed indistinguishable: p=0.93 at 64,
p=0.17 at 1 024. Verified independently at +6.1 % and +12.9 % — on a host at loadavg **12.19**
against 2.19 for the baselines, so **the busier arm was the faster one**.

**The scaling curve did not move, exactly as designed**: the collapse from 64 to 1 024
connections goes 0.660 → **0.698** of peak. Four times the stripes buy a better constant, not a
better curve.

| | | `ImplParse-10` allocs/op | 27.09 k | 27.17 k | +0.31 % |
| | | `ImplParse-10` B/op | 1.668 Mi | 1.668 Mi | `~` (p=0.225) |

| | | `ImplParseErrors-10` B/op | 39.33 Ki | 62.21 Ki | **+58.20 %** |
| | | `ImplParseErrors-10` allocs/op | 537.0 | 894.0 | **+66.48 %** |

`strings.ToUpper` on every identifier token was **78.6 % of all objects `StripLiterals`
allocated**, paid on every execution *including plan-cache hits*, because `StripLiterals` runs
before the cache is consulted. The −47.83 % **exceeds** the −46.63 % ceiling the spike predicted,

allocate nothing.

1.05 % floor, on two independent runs. The whole −6.46 % the spike had attributed to it belongs
to the *error strategy*, which LL+Bail delivers without touching prediction semantics.

### 3.3 The plan cache — filed as a defect, not an optimisation

**#2852** (`6ca705e3`). **[raw in repo]** —
[`ab.benchstat.txt`](cypher-plan-cache-shard-2026-09-16-2851-2852/ab.benchstat.txt).

The cache got **slower the more cores it was given**: one lookup cost **15.04 ns at one core
against 92.14 ns at ten**, with **98.46 % of all mutex delay** on `planCache.get`. Under this
project's concurrency mandate that is a defect, and it was worked as one.

Three arms in one table — `onemutex` (base), `shard16` (**shipped**), `shard256`:

| Row | `onemutex` | `shard16` | Δ | `shard256` | Δ |
|---|---:|---:|---:|---:|---:|
| `SpikeWarmPrepareMultiKey` (1 core) | 21.09 n | 31.96 n | **+51.54 %** | 21.87 n | +3.67 % |
| `SpikeWarmPrepareMultiKey-2` | 54.15 n | 27.66 n | −48.91 % | 16.12 n | −70.23 % |
| `SpikeWarmPrepareMultiKey-4` | 121.30 n | 24.85 n | −79.52 % | 9.68 n | −92.02 % |
| `SpikeWarmPrepareMultiKey-8` | 113.45 n | 37.85 n | −66.64 % | 18.57 n | −83.63 % |
| **`SpikeWarmPrepareMultiKey-10`** | **119.10 n** | **42.42 n** | **−64.38 %** | 19.33 n | −83.77 % |
| **geomean** | 87.51 n | 67.22 n | **−23.19 %** | 52.87 n | −39.58 % |

n=20+10, p=0.000 on the shipped row. **No allocation was added on any row** (0 B/op, 0

[`confirm.benchstat.txt`](cypher-plan-cache-shard-2026-09-16-2851-2852/confirm.benchstat.txt)).

**The single-core cost is real, is visible in the table above, and is the accepted trade**:
+51.54 % at one core on the multi-key row, attributed by single-variable experiment to the split

indistinguishable at one core
([`false-sharing.md`](cypher-plan-cache-shard-2026-09-16-2851-2852/false-sharing.md)).

**Why 16 shards and not the 256 that reaches the headline ceiling** — see
[§5](#5-the-shard-count-decision-priced-on-two-ladders).

**#2864 — the stored direction carried on the expand triplet** (`f62a3c83`). Replaced an

## 5. The shard-count decision, priced on two ladders

The clearest piece of measurement in this release, and the reason the shipped plan cache has
**16** shards rather than the 256 that reaches the headline ceiling. From
[`shard-count.md`](cypher-plan-cache-shard-2026-09-16-2851-2852/shard-count.md): *"one ladder is
not enough. Raising the shard count buys concurrency and costs hit rate, and the two axes point
in opposite directions. The chosen value is the minimum of their **sum**."*

**Axis 1 — contention.** `Engine.parseAndAnalyse` on a warm cache, 32 distinct keys,
`b.RunParallel` at `-cpu=10`, `-benchtime=300ms`, 10 interleaved reps × 2 arms:

| shards | sec/op | vs 1 shard |
|---:|---:|---:|
| 1 | 126.9 n ± 1 % | — |
| 2 | 98.11 n ± 1 % | −22.7 % |
| 4 | 77.16 n ± 2 % | −39.2 % |
| 8 | 57.91 n ± 5 % | −54.4 % |
| **16** | **42.28 n ± 4 %** | **−66.7 %** |
| 32 | 33.12 n ± 6 % | −73.9 % |
| 64 | 26.85 n ± 8 % | −78.8 % |
| 128 | 21.57 n ± 12 % | −83.0 % |

**Axis 2 — capacity quantisation.** Steady-state hit rate of a cyclic scan (LRU's worst case)
over a working set at a given fraction of a 1 024-entry capacity, **16 independent caches per
cell** so 16 independent hash seeds, measured on the cache alone with no engine and no parser:

| shards | per-shard cap | 50 % load | **75 % load** | 100 % load |
|---:|---:|---:|---:|---:|
| 1 | 1024 | 100.00 | **100.00** | 100.00 |
| **16** | **64** | 100.00 | **99.47** | 52.55 |
| 64 | 16 | 100.00 | **87.19** | 46.07 |
| 256 | 4 | 85.10 | **66.01** | 43.82 |
| 1024 | 1 | 61.68 | **49.48** | 36.58 |

**Below 100 % load the damage is entirely a function of per-shard capacity.** A shard with 64
slots absorbs the binomial spread of a 75 %-loaded cache almost perfectly (**99.47 %**); one
with 4 slots does not (**66.01 %**). One lost hit-rate point costs about **18 ns per lookup**
against a measured **1.8 µs** miss — so 33 lost points at 256 shards buys back far less than it
gives away.

**At 100 % load every count above 1 roughly halves the hit rate**, and that is an accepted,
priced consequence of per-shard eviction rather than a defect.

**The −83.7 % ceiling is therefore missed at the shipped count, and that is stated rather than
smoothed.** The ceiling was derived from the one-key case, which sharding provably cannot
address.

**The first hit-rate measurement this project has ever taken** accompanies it
([`plan-cache-hit-rate.md`](cypher-plan-cache-shard-2026-09-16-2851-2852/plan-cache-hit-rate.md),
#2851), on the unsharded code and bit-identical after the sharding:

| Example | hits | misses | hit % | evictions |
|---|---:|---:|---:|---:|
| `19_pattern_query` | 85 | 4 | **95.51 %** | 0 |
| `22_cypher` | 14 | 17 | **45.16 %** | 0 |
| `24_social_network_cli` (5 processes) | 0 | 9 | **0.00 %** | 0 |
| `25_software_house_api` | 0 | 34 | **0.00 %** | 0 |

**It refutes the campaign's own ranking rationale**, which put the keyword fold ahead of
two-stage parsing on a 97.62 % break-even that **no example reaches, and three miss by a wide
margin**. Both changes had already landed, so nothing needed undoing; what is refuted is the
reasoning. Stated limit: these are short example runs, not a long-lived server, and what they
establish is that **the assumed high-hit-rate regime has never been measured anywhere in this
project.**

## 6. The costs and the refutations

A record of only the wins would misrepresent this cycle. Four changes were built in full and
discarded; three tasks closed on a measurement with no code written at all.

### 6.1 Two float reassociations, built in full and discarded

**#2870.** Opt-in non-bit-reproducible variants of Betweenness and PageRank were implemented,
validated and measured, then **thrown away**. Two independent realisations, **7 interleaved
samples each with rotated arm order**:

| | geomean | verdict |
|---|---:|---|
| realisation 1 | +0.24 % | every row `~` |
| realisation 2 | +0.22 % | every row `~` |
| **byte-identical control** | **+0.81 %** | **p=0.017 — "significant"** |

**The control moved further than either treatment, and with a lower p-value.** The floor is
wider than the effect sought, on rows *proven able to resolve 2–3.5 %*.

From the assembly: the removed division **hides behind** the `delta[v]` read-modify-write and
the `sigma[v]` gather, and PageRank's pull loop is bound by **two random gathers**, not by the
arithmetic between them. **The 8.89 s and 1.87 s of profiled self-time that motivated the work
were self-time on instructions off the critical path.** The general lesson, recorded for every
row that rests on self-time alone: **self-time charged to an instruction is not work saved by
removing it.**

Shipping it would have cost **+4.85 % B/op**, bit-reproducibility, and a wider API, for nothing
measured.

### 6.2 Three tasks closed on a measurement with no code changed

**#2840 — throttling the MVCC vacuum cannot help.** A ceiling probe ran with
`reclaimPropVersions` **disabled entirely**, not throttled: **12 543 q/s against a base of
12 669 — −1.0 %, exactly the noise floor** — although the vacuum held **21.0 % of all Go-mutex
delay** at 1 024 connections. Deleting the work is the most generous version of any scheduling
change, and it bought **zero throughput**. **It also corrects the premise the task was written
on: mutex delay is not a cost function**, because delay counts time goroutines spent *waiting*
rather than time the workload *lost*. The campaign's ranked tables were re-read against this,
and no other row depended on the mistaken reading.

**#2867 — the reported `Snapshot.visible` contention does not exist.** It accounts for
**0.046 % / 0.027 % / 0.196 %** of `37_mvcc_write_contention`'s mutex delay across three passes
and **does not appear at all** in `36_mvcc_snapshot_topology`. None of it is the `sync.Mutex`
the report named: the children are `runtime.mapassign_fast64ptr` (93.64 %) and `makemap_small`
— the runtime heap lock *inside* the map insert, which is the **allocation** the memo causes,
not the lock guarding it. Filed as #2873.

**#2836 — removing Bolt's per-chunk allocation is not worth its risk.** The weight reproduces
at HEAD (**1.18 KB and 25.9 objects per query**, 1.42 % of allocated bytes) but GC mark CPU is
only **0.62 / 0.92 / 1.06 %** of process CPU at 64 / 256 / 1 024 connections, so the gain has a
ceiling of roughly **0.015 % of process CPU — about 70× below the 1.08 % noise floor** — on a
path guarded by the size-budget and length-bound tests.

### 6.3 Four measurement premises that were artefacts

- **The Bolt 256→1024 throughput knee** is a **measurement-window artefact**: varying only the
  window gives −14.90 % at 20 k queries, −6.89 % at 100 k and **−4.40 % at 400 k**, a fixed
  24–31 µs per-connection start-up amortised over fewer queries. **Half of the remainder was
  the laboratory's own `/dev/fd` descriptor walk**, which `os.ReadDir` lstat-ed 40×/s for
  0.62 / 2.32 / 5.78 % of CPU at 64 / 256 / 1 024. Removing it: **+4.65 %** throughput and
  **−12.76 %** p999 at 1 024, halving the apparent penalty from −6.49 % to −3.18 %. **Round 1's
  ladder carries the same bias, and says so.**
- **The second `read(2)` per query is the Go runtime's own EAGAIN retry** in `internal/poll`,
  not a protocol read: an AF_UNIX control differing only in blocking mode measures **2.0004**
  reads per logical `Read` through the poller against **1.0002** blocking. Real, 9.6 % of
  process CPU, **unreachable from module code**.
- **Round 1's "no gain is measurable above ~160 k q/s" was wrong and is corrected.** Its
  GoGraph-free control replied with *two* writes per request, so its ceiling was a two-writes
  ceiling, not the platform's. Rebuilt to reply with one, the control measures **202 252
  req/s**, against which this server's 192 649 is **95.3 %** — 4.98 % of headroom. Putting the
  control back into its two-writes shape reproduces the old 159 579 to **0.03 %**, which
  validates the instrument rather than the old conclusion.
- **Two standing backlog items were refuted on their own numbers** (#2859): #2661
  (`canonicalRelTypesKey` has **zero** occurrences at HEAD) and #2391 (`buildReadPhysical`
  **25.61 %** not 59.56 %, `ResolveLabelBitmap` **52.75 %** not 10.42 %, which inverts its own
  priority ordering).

### 6.4 Acceptance criteria retired as resting on false premises

The sprint-362 merge commit (`19138042`) records that **four** acceptance criteria were retired
this sprint and that every replacement gate was made **absolute** rather than a profile share.
Three are individually traceable to task closing summaries:

- **#2862** — "the original 15 % criterion was removed as resting on a false premise": measured
  43.35–43.67 % on `20_concurrent_reads`, because that graph is connected so the truncation
  cannot fire, and the two untouched sites are already 21.64 %.
- **#2852** — "two acceptance criteria were amended because the coordinator had written them
  impossible": one key is one shard, and the warm path takes no other lock, so `get` cannot lose
  the majority mutex share.

**The fourth is not identified in the task summaries read for this report**, and is recorded as
unattributed rather than guessed at.

## 8. What this snapshot does NOT measure

Beyond the five absences in [§0](#0-what-this-record-is-not):

- **No whole-release delta.** See §0.1. The thirteen rows are not additive.
- **No regression sweep.** Nothing establishes that code *no task touched* did not regress.
  `go.mod` and `go.sum` are byte-identical to `v0.14.2` and no file under `store/` changed,
  which bounds where a regression could have come from, but it does not measure one.
- **No cross-release binary-identity proof.** `v0.14.2`'s §0 could prove three packages
  unchanged by sha256 because its campaign compiled both trees. No such comparison was made
  here.
- **No elevated-scale coverage.** The example sweep measured **54.8 % of statements across 55 of
  99 module packages** at default scale (#2858, proven non-empty by 79 counter files merged into
  54 148 lines); the elevated pass reached **3 of 42 rows** and its coverage is unmeasured.
  `graph/io` and `store/bulkimport` are the only substantive production packages the sweep never
  reaches, and neither has a named exercising harness.
- **Nothing above ~200 k q/s on the Bolt path is measurable on this host.** The GoGraph-free
  loopback control saturates at 202 252 req/s, so the remaining 4.98 % of headroom cannot be
  explored without a remote client on separate hardware.
