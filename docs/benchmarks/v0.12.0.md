# Benchmarks — v0.12.0

Headline benchmark and load-test numbers for the GoGraph **v0.12.0** release,
measured first-hand at the release candidate.

> **What moved in v0.12.0.** Almost nothing, and one thing a great deal. This is a
> testing-and-correctness release: no engine capability was added, four `perf`
> commits landed, and 75.7 % of the changed lines are `internal/sim`. The headline
> set, the read-path sweep and the durable write ladder are all **unchanged from
> `v0.11.0` within a couple of percent**, with allocation counts identical. The one
> large movement is that **`v0.11.0`'s known-open plan-choice regression is closed**:
> `BenchmarkMinLabelScanSelective_MinLabel` goes 4,979,786 → **203,882 ns/op**
> (**−95.91 %**) and 106,293 → **1,551 allocs/op** (**−98.54 %**), so the optimised
> arm is now **16.54× faster** than the legacy control it exists to beat, where
> `v0.11.0` shipped it **1.46× slower** (§4).

> Re-measure on your own hardware before relying on any absolute number; these are
> medians from documented runs, not a guarantee.

## The confound, stated first rather than in a footnote

`v0.11.0` was measured on **go1.26.5**. This release is measured on **go1.27.0** —
the pinned `toolchain` directive was advanced in this cycle (the `go` directive stays
at `go 1.26`). Every cross-release delta in this document therefore **mixes a
compiler change with GoGraph's own**, and none is attributed to the module on the
strength of that comparison alone.

Where a figure *is* attributed, it is because a within-tree A/B measured it. That is
the case for §4 (#2431), and for the three per-change records this release produced:
[`min-label-anchor-vs-parallel-scan-2026-08-26.md`](min-label-anchor-vs-parallel-scan-2026-08-26.md),
[`range-seek-population-floor-2026-08-26.md`](range-seek-population-floor-2026-08-26.md)
and [`count-star-row-count-2026-08-27.md`](count-star-row-count-2026-08-27.md).

### Load-average discipline, and the run that proves it is not ceremony

The 2026-08-10 release-delta record established that on this host a 1-minute load
average above ~2.5 is a **systematic bias, not noise**. Every run below was gated on
it: the harness read `vm.loadavg` and refused to start until the 1-minute figure was
under 2.5, recording the figure it started at. Runs were **sequential by
construction**, one process at a time.

| Run | Gate | Waited | Wall | Result lines | Expected |
|---|---:|---:|---:|---:|---:|
| §1 headline | started at 2.44 | 60 s | 421 s | 30 | 30 ✔ |
| §2 read sweep | started at 2.30 | 90 s | 37 s | 25 | 25 ✔ |
| §4 min-label | started at 2.37 | **300 s** | 20 s | 12 | 12 ✔ |
| §3 write ladder | started at 2.41 | 0 s | 95 s | 60 | 60 ✔ |

Output was passed through the same `strip_log_noise` repair
[`scripts/bench-history.sh`](../../scripts/bench-history.sh) applies, and **the
surviving result-line count was asserted** against the expected count — the
2026-08-10 record lost 99 of 392 result lines to an interleaved log line, and a
`benchstat` that silently sees fewer samples reads exactly like "no regression".

**This release's headline set was measured twice, and the first run was discarded.**
The first was taken while a documentation-editing agent was working on the same host.
It was not compute-heavy, and the contamination was still decisive:

| Benchmark | run 1 median | run 1 spread | run 1 "Δ vs v0.11.0" | run 2 (reported) | run 2 spread |
|---|---:|---:|---:|---:|---:|
| `Dijkstra_PostWarmup` | 11.712 ms | 14.1 % | **+41.55 %** | 8.140 ms | 2.0 % |
| `Dijkstra_Large` | 11.770 ms | 18.6 % | **+40.78 %** | 8.207 ms | 2.6 % |
| `BFSDirectionOpt_PowerLaw` | 35.079 ms | 42.1 % | +17.44 % | 29.030 ms | 2.2 % |
| `Yen_K100` | 15.969 ms | 11.9 % | +10.37 % | 14.722 ms | 0.9 % |
| `Brandes_RandomGraph` | 8.499 ms | 6.6 % | +5.05 % | 8.097 ms | 1.2 % |

Run 1 would have published **five regressions of up to +41.6 % in a release that
modified no search algorithm.** The tell is the **within-run spread** — 6.6–42.1 %
against run 2's 0.9–2.6 % — which is why the spread is printed in every table below
rather than only the median. Run 1's logs are retained.

Two instrument corrections are recorded because each silently produced a wrong count:

- **A POSIX bracket expression does not honour `\t`.** The result-line counter used
  `grep -cE '…[ \t]+…'`, which matches a space, a backslash or the letter `t`, never a
  tab — so it reported **0 result lines on a log holding 30**. A zero count is exactly
  what the assertion exists to catch, and it read as a clean pass. Counting moved to
  Python.
- **`go` omits the `-N` suffix at `GOMAXPROCS=1`.** A sweep regex requiring `-(\d+)`
  silently drops all five `cpu=1` samples, and the sweep then reads as four levels
  with the uncontended baseline missing. §2 has five levels.

## 1. Headline benchmarks

The canonical regression-gate set, as defined by
[`scripts/run_headline_bench.sh`](../../scripts/run_headline_bench.sh). **Median of
6**; 30 of 30 expected result lines survived.

| Benchmark | Package | ns/op (median) | spread | Δ vs v0.11.0 | B/op | allocs/op | allocs vs v0.11.0 |
|-----------|---------|---------------:|-------:|-------------:|-----:|----------:|:-----------------:|
| `BenchmarkDijkstra_PostWarmup` | `search` | 8,140,420 (≈ 8.14 ms) | 2.0 % | −1.62 % | **0** | **0** | identical |
| `BenchmarkDijkstra_Large` | `search` | 8,207,312 (≈ 8.21 ms) | 2.6 % | −1.83 % | 1,129,255 | 4 | identical |
| `BenchmarkBFSDirectionOpt_PowerLaw` | `search` | 29,030,415 (≈ 29.03 ms) | 2.2 % | −2.81 % | **0** | **0** | identical |
| `BenchmarkYen_K100` | `search` | 14,722,044 (≈ 14.72 ms) | 0.9 % | +1.76 % | 459,524 | 1,280 | identical (median) |
| `BenchmarkBrandes_RandomGraph` | `search/centrality` | 8,096,500 (≈ 8.10 ms) | 1.2 % | +0.07 % | 62,208 | 10 | identical |

**The zero-allocation mandate holds.** `Dijkstra_PostWarmup` and
`BFSDirectionOpt_PowerLaw` allocate **zero** bytes per call in every sample, and every
allocation count matches `v0.11.0`'s (0, 4, 0, 1 280, 10). No hot-path allocation
regression landed.

**The honest reading of the time column is "unchanged".** The five deltas span
−2.81 % to +1.76 %, all within or near the runs' own 0.9–2.6 % spread. Three are
*improvements* and they are **not claimed for GoGraph**: no search algorithm changed
in this window, the compiler did, and no within-revision A/B exists. Treat all five as
unchanged.

**Two sample-level observations, reported rather than rounded away.**

- `Yen_K100`'s `allocs/op` is **not a constant**: five samples measure 1,280 and one
  measures 1,281. `v0.11.0` published 1,280. The median is 1,280; the spread is real
  and is stated rather than printed as a clean constant.
- `v0.11.0` flagged `Dijkstra_Large`'s `B/op` as **no longer deterministic**, spanning
  1,129,358 – 1,191,048 (5.5 %). Here it spans **1,129,244 – 1,144,179 (1.3 %)** and
  the median, 1,129,255, is within 0.02 % of `v0.10.0`'s published 1,129,088. The
  non-determinism `v0.11.0` reported has **largely settled**. Nothing in this release
  targeted it and the toolchain changed, so this is recorded as an observation, not as
  a fix.

## 2. Load test — read-path concurrency sweep

CLAUDE.md requires a load-test report "at multiple concurrency levels (1, 8, 64, 256,
1024 goroutines)". As in `v0.10.0` and `v0.11.0` we sweep `GOMAXPROCS` over the
`b.RunParallel` hot-key intern benchmark — the tightest shared-state contention point
in the read path, where **every goroutine interns the same key** and competes for the
same cache line. **Median of 5**; 25 of 25 expected result lines survived.

| Goroutines (`GOMAXPROCS`) | ns/op (median) | spread | Aggregate throughput | Δ vs v0.11.0 | B/op | allocs/op |
|--------------------------:|---------------:|-------:|---------------------:|-------------:|-----:|----------:|
| 1 | 9.806 | 1.0 % | 102.0 M ops/s | **+11.66 %** | 0 | 0 |
| 8 | 75.840 | 2.1 % | 13.19 M ops/s | +0.92 % | 0 | 0 |
| 64 | 87.610 | 2.1 % | 11.41 M ops/s | −1.38 % | 0 | 0 |
| 256 | 88.820 | 0.9 % | 11.26 M ops/s | +0.40 % | 0 | 0 |
| 1024 | 88.390 | 1.0 % | 11.31 M ops/s | −0.33 % | 0 | 0 |

**Read this sweep correctly.** Under `b.RunParallel`, `b.N` is the total iteration
count across all goroutines, so **`ns/op` is inverse *aggregate* throughput, not
per-goroutine latency**. The drop in aggregate throughput from 1 to 8 goroutines is
not a scaling failure of the module — it is the cost of cache-line contention existing
at all, on a benchmark deliberately built so that every goroutine fights for one key.
This is a **contention probe, not a throughput scaling test**; §3 is the throughput
scaling test.

**What it establishes.** From 8 to 1024 goroutines — a **128× over-subscription** of
10 physical cores — per-op cost stays **flat at 75.8–88.8 ns with zero allocations**,
and the 64/256/1024 levels sit within 1.4 % of `v0.11.0`. The structure degrades
predictably under massive over-subscription rather than collapsing, so the
bounded-resource and lock-contention mandates hold at the published levels.

**The +11.66 % at one goroutine is reported and attributed to nothing.** The
measurement is solid — 1.0 % spread over five samples — and it is ~1 ns absolute on a
9 ns operation. But **every change to `graph/mapper.go` in this window is a comment**:
filtering the diff for non-comment, non-blank changed lines returns empty, so not one
executable line in the interned-key hot path differs from `v0.11.0`. The candidates
are therefore the go1.26.5 → go1.27.0 change in code layout and inlining — possibly
perturbed by the new `graph/mapper_restore.go` landing in the same package (#2528) —
and ordinary cross-session drift against a figure published on a different day. No
within-revision A/B exists, so **no cause is claimed and this is not called a GoGraph
regression.**

## 3. Load test — durable write throughput at the published levels

`BenchmarkWriteScaling_StoreAPI` and `BenchmarkWriteScaling_Cypher`
(`store/txn/write_scaling_bench_test.go`) sweep exactly the published ladder —
`writerCounts = []int{1, 8, 64, 256, 1024}`. Both perform **one durable single-edge
transaction per operation** against the same WAL and engine, so a divergence between
them isolates commit-path coordination rather than the cost of the write. **Median of
6**; 60 of 60 result lines survived across the ten sub-benchmarks.

### 3.1 Through the store API (`txn.Tx.Commit`)

| Writers | Throughput | Scaling | commits/fsync | v0.11.0 | Δ |
|--------:|-----------:|--------:|--------------:|--------:|---:|
| 1 | 268.5 ops/s | 1.00× | 1.00 | 268.4 | +0.02 % |
| 8 | 1,094.5 ops/s | 4.08× | 4.11 | 1,098.5 | −0.36 % |
| 64 | 8,317.5 ops/s | 30.98× | 31.57 | 8,321.5 | −0.05 % |
| 256 | 31,801.0 ops/s | 118.46× | 120.25 | 32,234.0 | −1.34 % |
| **1024** | **112,560.0 ops/s** | **419.30×** | 426.35 | 111,483.0 | +0.97 % |

### 3.2 Through the Cypher engine (autocommit)

| Writers | Throughput | Scaling | v0.11.0 | Δ |
|--------:|-----------:|--------:|--------:|---:|
| 1 | 270.9 ops/s | 1.00× | 271.0 | −0.06 % |
| 8 | 1,054.5 ops/s | 3.89× | 1,060.0 | −0.52 % |
| 64 | 8,331.5 ops/s | 30.76× | 8,253.5 | +0.95 % |
| 256 | 31,023.0 ops/s | 114.54× | 30,804.0 | +0.71 % |
| **1024** | **116,415.5 ops/s** | **429.82×** | 115,300.5 | +0.97 % |

**Throughput is monotonic in concurrency at every step of both arms**, and the two
arms track each other within a few percent — so the Cypher layer still adds no
coordination the store API does not already have. Every level of both arms is within
**−1.34 % to +0.97 %** of `v0.11.0`: the MVCC write path this release did not touch
has not moved.

**The mechanism is re-proven arithmetically, not asserted.** On the store-API arm the
scaling factor equals `commits/fsync` at every level: 4.08 vs 4.11, 30.98 vs 31.57,
118.46 vs 120.25, 419.30 vs 426.35. The gain is **group-commit fsync amortisation**
and nothing else. The single-writer rate of 268.5 ops/s is this device's single-writer
fsync rate, unchanged from `v0.11.0`'s 268.4 — an fsync per commit is an fsync per
commit. **Nothing was traded for the scaling.**

This is the second consecutive release in which the ladder has been run, and it
independently reproduces `v0.11.0`'s figures from a different session and a different
compiler.

## 4. The v0.11.0 open regression is closed

`v0.11.0` shipped rmp **#2431** as a **CONFIRMED OPEN** defect, and its own benchmark
document called the resulting plan "the worst of the three plans the engine can
produce". The mechanism, established by sweep rather than argued:
`tryBuildColumnarFilterChain` already yields to the min-cardinality label re-anchor and
states the rule — the re-anchor reduces the number of rows **scanned**, while columnar
execution only removes a constant factor from each row — but
`tryBuildParallelScanProject` was tried immediately afterwards and was **not making the
same argument**, parallelism being a constant factor too. So the yield was **inert**:
it handed the shape straight to an operator that ignored the same rule and anchored on
`Labels[0]`. The fix (`84ab4123`) makes the parallel gate **adopt** the anchor the
serial path would choose.

`BenchmarkMinLabelScanSelective_{MinLabel,FirstLabel}` on `./bench/cypher_ldbc/`,
**median of 6**; 12 of 12 result lines survived:

| Arm | v0.11.0 ns/op | v0.12.0 ns/op | Δ | v0.11.0 allocs/op | v0.12.0 allocs/op | Δ |
|---|---:|---:|---:|---:|---:|---:|
| `_MinLabel` (the optimised plan) | 4,979,786 | **203,882** | **−95.91 %** | 106,293 | **1,551** | **−98.54 %** |
| `_FirstLabel` (the legacy control) | 3,403,230 | 3,371,589 | −0.93 % | 811 | 811 | **identical** |

`_MinLabel`'s `B/op` falls 7,119,359 → 51,280 (**−99.28 %**).

**The relationship the benchmark's name asserts is restored.** `v0.11.0` measured the
optimised arm **1.46× slower** than the control it exists to beat, with 131× more
allocations. Here it is **16.54× faster**. At 203,882 ns it is also faster than
`v0.10.0`'s 230.3 µs on the same fixture, so the anchor is better than it has ever
been rather than merely repaired.

**Why this delta *is* attributable, where §1's and §2's are not.**

- The allocation figure lands on **1,551 exactly** — the number rmp #2431 reported —
  and the time delta of −95.91 % matches its reported −96.08 % to 0.17 percentage
  points. This is an independent first-hand reproduction of a within-tree A/B, not a
  cross-release diff.
- **The control moved −0.93 % with allocations byte-identical** (811 on both sides). A
  change that moved everything would not distinguish a fix from session drift; this one
  moved the treated arm 24× and left the control alone.
- Allocation counts are compiler-invariant in a way `ns/op` is not, so −98.54 %
  allocs/op is not a go1.27.0 artefact.

**One caveat.** `_FirstLabel`'s own spread is **42.4 %** across its six samples — that
arm is noisy on this fixture. Its median is stable against `v0.11.0` (−0.93 %) and its
allocations are identical, so the ratio stands, but 3,371,589 should not be read as a
precise figure. `_MinLabel`'s spread is 1.0 %.

cited from those records, not re-measured here.

The floor suppressed the range-index seek below 1,024 nodes on a premise measurement refutes by more than an order of magnitude. | [`range-seek-population-floor-2026-08-26.md`](range-seek-population-floor-2026-08-26.md) |

| **#2624** — the social-graph build bracket | Allocation ratio **58× → 16.6×**. This is `examples/26_social_scale_bench`, which is **not part of the module**. | commit `65c278e6` |

### What got slower — measured, not minimised

Three costs land against `v0.11.0`, and every one is the price of a correctness fix
rather than a defect of its own. All three are quantified in
[`CHANGELOG.md`](../../CHANGELOG.md) and
[`release-notes/v0.12.0.md`](../../release-notes/v0.12.0.md):

- **#2603 — the anchor-swap guard costs the shape it declines 62× to 1705×.** At hub
  degree 1,601, 5.644 µs → 368.8 µs; at degree 40,000, 5.681 µs → 9.687 ms, with
  allocations 193 → 79,566. The swapped plan is flat in the hub's degree and the
  written order is linear, so **the loss grows without bound** on an ordinary spelling.
  Correctness outranks speed, so the guard ships; **#2604 is filed to recover the
  optimisation properly** and is the highest-value open performance item in the tree.
- **#2444 — the MVCC endpoint cross-checks cost Cypher `DETACH` +4–6 %** and
  relationship creation +3.9 %; direct-API bulk delete is unchanged. That is the
  attributable price of making the node the unit of write–write conflict.
- **#2593 — `flow.PushRelabel`'s discharge polling costs +3.3 % to +4.6 %** on one
  adversarial fan-out shape, p<0.05 over three interleaved rounds, with `B/op` and
  `allocs/op` identical because the counter is threaded by value.

No other regression against `v0.11.0` was measured.

## 6. What this snapshot does NOT measure

1. **Latency percentiles at the published levels.** p50/p99 at 1/8/64/256/1024 is
   **unmeasured**, for a fifth consecutive cycle. §2 and §3 report throughput and
   per-op cost, which are not a latency distribution.
2. **No certification.** The most recent production certification is
   [`docs/certification-2026-08-13.md`](../certification-2026-08-13.md), taken at the
   `v0.11.0` release commit — **192 commits behind this tag**. Nothing here discharges
   it, and no certification was run in this window.
3. **The whole-tree soak layer was not run.** `soak-artefacts/` is unchanged since
   2026-05-30 at commit `b5453b9`. The `internal/sim` soak layer *was* brought green
   and verified twice consecutively (#2620), and the DST catalogue passes under
   `SOAK_FULL=1` with 36 of 36 scenarios — neither is the whole-tree soak.
4. **Single host, single architecture** — Apple M4, 10 cores, `darwin/arm64`. No
   Linux, no NUMA, no multi-socket, and **no container was ever run**.
5. **No cross-release attribution**, per the toolchain confound stated at the top.
   Only §4's delta is attributed, and only because a within-tree A/B and an unmoved
   control support it.
6. **Memory footprint is not measured here.** The open memory findings (#2404, #2405,
   #2407) are carried forward from `v0.11.0` unchanged.

## 7. Reproduce

Every command below was executed to produce the figures above, sequentially, one
process at a time, each gated on a 1-minute load average below 2.5.

```bash
# §1 — headline / guard-band set (median of 6)
./scripts/run_headline_bench.sh

# §2 — read-path concurrency sweep (median of 5)
go test -run='^$' -bench='^BenchmarkMapper_Intern_HotKey_Parallel$' \
  -benchmem -cpu=1,8,64,256,1024 -count=5 ./graph/

# §4 — the closed regression and its control (median of 6)
go test -run='^$' -bench='^BenchmarkMinLabelScanSelective_(MinLabel|FirstLabel)$' \
  -benchmem -count=6 ./bench/cypher_ldbc/

# §3 — durable write throughput at 1/8/64/256/1024 writers (median of 6)
go test -run='^$' -bench='^BenchmarkWriteScaling' -benchmem -count=6 \
  -timeout 40m ./store/txn/
```

Pipe every invocation through `strip_log_noise` from
[`scripts/bench-history.sh`](../../scripts/bench-history.sh) **before** filtering, and
assert the number of results kept against the number expected. Two counting traps to
avoid, both of which produced a wrong count during this release's measurement: a POSIX
bracket expression does **not** honour `\t` (so `grep -E '[ \t]+'` reports zero
matches on a tab-separated benchmark log), and `go` **omits** the `-N` suffix at
`GOMAXPROCS=1` (so a sweep regex requiring it drops the uncontended baseline
silently).

Per-change (rather than per-release) tracking lives in [`history/`](history/); the
narrative ledger is [`history/LEDGER.md`](history/LEDGER.md). The prior authoritative
baseline is [v0.11.0](v0.11.0.md).
