# `v0.13.0` → `v0.14.0` — measured comparison (allocations)

**Date:** 2026-09-06 · **Machine:** Apple M4 (4P+6E, 10 cores), 32 GiB, macOS 26.5.2
(darwin 25.5.0) · **Toolchain:** go1.27.1 darwin/arm64 · **Build mode:** plain,
**NO `-race`**, `-trimpath` · **Raw data:**
[`v0130-vs-v0140-2026-09-06-raw/`](v0130-vs-v0140-2026-09-06-raw/)

**Arms.** `v0.13.0` = `b439283eb1cbf681ff61648a01b007c394e31f81` (the tag).
`v0.14.0` = `94602f465911308b9ea98b937e31ad91dfcc4bda` (`HEAD` of `release/0.14.0`) plus the
working tree's single uncommitted Go change, which is a **doc comment in `cypher/api.go`**
and nothing else; it was copied into the measurement worktree so the arm is the tree, not
the commit.

---

## The headline, stated honestly

**This release is not measurably faster, and this document does not claim it is.** It
reports one dimension only — **allocations** — and in that dimension:

- **159 of 171 compared benchmarks are unchanged.** The counting work sprint 355 added
  costs **zero allocations**.
- **8 benchmarks changed, and every one of them ALLOCATES LESS.** Nothing regressed.
- **4 benchmarks are unreliable** and are reported as such rather than averaged away.
- **No wall-clock figure is reported anywhere in this document.** Not approximately, not
  indicatively. See [Why there is no timing claim](#why-there-is-no-timing-claim).

**A timing comparison between `v0.13.0` and `v0.14.0` remains UNMEASURED.** That is not the
same as "no difference", and it must not be read as one.

---

## Why there is no timing claim

The host carried a **1-minute load average between 2.86 and 19.73** (n = 68 brackets across
both runs; median ≈ 14) on a 10-core machine, for the whole measurement.

The dominant cause was **not** the benchmark suite. With every one of the experiment's own
processes killed and verified gone, the load average was still **13.4**. The cause was
Spotlight: `mds_stores` plus four `mdworker_shared` importers at 40–74 % CPU each, indexing
**the two 1.9 GiB worktrees this experiment had just created**. The measurement contaminated
its own host.

Spotlight was left alone — disabling it is a system-wide change and not this task's to make.
The consequence is accepted instead of worked around: at that load a wall-clock figure at
these scales cannot be defended, so none is offered. `sec/op` appears nowhere below.

**Allocation counts are load-invariant**, which is why they, and only they, carry this
report.

---

## The noise floor, before any effect figure

Two independent floors were measured, both under the same load as the signal.

### Floor 1 — the same binary against itself

`B2` is a second, independent build of the **same** `v0.14.0` tree. `go build` is
deterministic here, so `B2` is **byte-identical to `B`** (sha256 in
[`binary-sha256.txt`](v0130-vs-v0140-2026-09-06-raw/binary-sha256.txt)). `B` vs `B2` is
therefore the same binary against itself, and every difference it shows is manufactured by
the host.

| Result | Count |
|---|---|
| benchmarks whose `allocs/op` agree within 0.5 % | **169 of 171** |
| benchmarks whose `allocs/op` do **not** agree | **2** |

The two that do not agree are the floor, and they are large:

| Benchmark | `B` | `B2` | apparent difference |
|---|---|---|---|
| `BenchmarkPlanCacheHit_Parameterised` | 97 | 86 | **11.34 %** |
| `BenchmarkPlanCacheMiss_InlinedLiteral` | 403 | 397 | 1.49 % |

**So on the plan-cache benchmarks this host manufactures an 11 % allocation difference from
nothing.** Any allocation claim on those shapes below that magnitude is noise. Every effect
reported below is either far outside it or explicitly withheld.

### Floor 2 — a byte-identical binary across the two versions

The `store/wal` test binary is **byte-identical between `v0.13.0` and `v0.14.0`** (sha256
match — the package's source and its whole transitive dependency set are unchanged). It is
therefore a noise floor measured *across the arms*, which Floor 1 cannot be.

All **7 of 7** `store/wal` benchmarks report identical `allocs/op` in both arms
(`CRCIncremental` ×4 = 0, `Encode` = 1, `Decode` = 3, `Reader_Replay` = 134). The method
returns "no difference" where no difference is physically possible.

### A measurement artefact worth naming

`B/op` is **not** deterministic and is not used for any verdict here. Go reports it as
`TotalAlloc / N`, and `N` differs between runs, so `B/op` wanders by a few bytes on
otherwise identical work (e.g. 271 208 vs 271 209). `allocs/op` carries the same rounding,
which is why **a difference of ±1 on a large count is treated as rounding, not as a change**,
and the classification threshold is a relative 0.5 %.

## The common benchmark set

**587 benchmark functions exist at `v0.13.0`; 597 at `v0.14.0`. 587 are common, 0 were
removed, 10 were added.** (Counted as top-level `func Benchmark…` in `*_test.go` across the
whole module, `examples/` and `bench/` included; a different counting rule gives a different
total.)

Only **4** benchmark-bearing test files differ between the trees, and every one of the four
diffs is a call-signature adaptation (one extra `nil` argument to `buildReadPhysical`) or a
plan-text assertion update. **No benchmark's workload changed.** The common set is therefore
genuinely comparable.

**Selection criterion.** Benchmarks were selected to cover every surface sprint 355 touched,
plus surfaces it did not touch as controls:

| Surface | Package | Why |
|---|---|---|
| `Expand` slot bracketing (#2761) | `cypher/exec` | added counting |
| `ShortestPath` / `AllShortestPaths` (#2763) | `cypher/exec` | added counting |
| row and columnar filters (#2764) | `cypher/exec` | added counting |
| the three parallel leaves (#2762) | `cypher` | added counting |
| plan-cache hits, estimate on the physical plan (#2765) | `cypher` | added work |
| count / label-count path (#2771) | `cypher` | changed estimator |

**Dropped, and why:** `graph/lpg` and the engine-level `ColumnarShape`, `IndexIntersectPlan`,

benchmarks do not call, plus a test-only probe field.

## Result 2 — what changed, and all of it is a reduction

Eight benchmarks moved. **Every one allocates less at `v0.14.0`.**

| Package | Benchmark | `v0.13.0` | `v0.14.0` | Δ `allocs/op` |
|---|---|---|---|---|
| `cypher` | `ZZReorderSkewed/reorder=on` | 5 925 706 | **59 968** | **−98.99 %** |
| `cypher` | `ZZReorderLiveHistory/history=quiet` | 564 429 | **25 031** | **−95.57 %** |
| `cypher` | `ZZReorderLiveHistory/history=live` | 564 428 | **25 055** | **−95.56 %** |
| `cypher` | `ReadAfterWrite_Session` | 53 | 41 | −22.64 % |
| `cypher` | `ReadAfterWrite_Sessionless` | 53 | 41 | −22.64 % |
| `cypher/exec` | `ShortestPath_Layered` | 126 | 108 | −14.29 % |
| `cypher/exec` | `ShortestPath_LayeredTyped` | 126 | 108 | −14.29 % |
| `cypher/exec` | `ShortestPath_HighDegreeFan` | 317 | 314 | −0.95 % |

`AllShortestPaths` shapes are unchanged. The reduction is not explained by this document; it
is reported because it was measured.

## Result 3 — the reorder gain, and why it is attributable

The release notes state this gain could not be measured head-to-head. **It can**, and it was.
See [The instrument was the obstacle](#the-instrument-was-the-obstacle-not-the-api).

Attribution does not rest on the numbers. **The plan itself changed**, dumped from both trees
by an identical test:

```
v0.13.0                                  v0.14.0
ColumnarProject                          ColumnarProject
└─ Apply                                 └─ Apply
   ├─ NodeByLabelScan [B]                   ├─ Filter (est. rows=3 exact)
   └─ Filter                                │  └─ NodeByLabelScan [A] (est. rows=20000 exact)
      └─ NodeByLabelScan [A]                └─ NodeByLabelScan [B] (est. rows=100 exact)
```

At `v0.13.0` the 100-row `:B` component drives and re-scans the 20 000-node `:A` label once
per row. At `v0.14.0` the property statistics estimate the filtered `:A` component at 3 rows,
so it drives instead. That is the mechanism, and it predicts the ~100× allocation drop that
was measured.

**The results are identical.** The full sorted result set from both trees hashes to the same
md5, `n = 300` rows in both. The reorder is result-preserving.

**Two controls confirm the harness is not the cause:**

- `ZZReorderSkewed/reorder=off` — the written order in *both* trees — is **unchanged**
  (5 925 706 vs 5 925 706, spread ±6 on 5.9 M, i.e. rounding).
- `ZZReorderDrainCost` is unchanged in both arms.

**Conditions, without which the figure is meaningless.** The gain requires
**`RefreshStatistics` to have run** *and* a **qualifying query shape** — a disjoint
two-component match where a label count alone cannot identify the cheaper driver but a
`(label, property)` estimate can. It is one synthetic skewed shape chosen to exhibit the
effect. **It is not a general speed-up and must never be quoted as one.**

### What the live-history arms do and do not show

Both `history=quiet` and `history=live` gain ~95.6 %. The plan dumps show why: at `v0.13.0`
the reorder **does not fire in either arm**, because both components carry a property
predicate and the count-store-only gate cannot estimate them. At `v0.14.0` it fires in both.

So the quiet-arm gain is attributable to **#2766**. The live-arm gain requires #2766 **and**
#2771 together — and because no build carrying #2766 *without* #2771 was produced, **#2771's
isolated contribution is not separated by this experiment.** What is shown is that the gain
**survives live MVCC history**, which is what #2771 exists to guarantee.

## The instrument was the obstacle, not the API

The release notes record that `BenchmarkJoinReorderStatsSkewed`,
`BenchmarkJoinReorderStatsLiveHistory` and the shortest-path benchmarks "use APIs that do not
exist at `v0.13.0`, so they cannot be compiled against the old tree."

**That was checked and it is not so.** Every API those benchmarks touch — `NewEngine`,
`NewEngineWithOptions`, `EngineOptions.DisableJoinReorder`, `RefreshStatistics`,
`Engine.Run`, `Engine.Explain`, `StaticAdjacency`, `NewShortestPath`, `NewAllShortestPaths`,
`WithTypeFilter`, `NodeLifeVersionCount`, and lpg's node/label/property writers — **exists at
`v0.13.0`.** What `v0.13.0` lacks is their **helpers** (`buildSkewGraph`,
`buildRangeSkewGraph`, `drainBenchQuery`, the five-argument `mustNode`), which the sprint
added alongside them.

The obstacle was the instrument, and an instrument can be carried across:

- `cypher/exec/shortest_path_bench_test.go` was copied **verbatim** into the `v0.13.0`
  worktree. It compiles (`go vet` exit 0) and all 7 of its benchmarks run in both arms.
- A **self-contained** reorder harness reusing no helper from either tree was written and
  placed **identically** in both worktrees (sha256 match), so the instrument is provably the
  same and only the engine differs.

Both are in the raw directory
([`zzport_reorder_bench_test.go.txt`](v0130-vs-v0140-2026-09-06-raw/zzport_reorder_bench_test.go.txt)).

**One further correction:** `BenchmarkReadPathLiveHistory`, named in the framing for this
work, **does not exist in either tree**. The 10 benchmarks actually added by `v0.14.0` are
listed in
[`benchnames-added-by-v0140.txt`](v0130-vs-v0140-2026-09-06-raw/benchnames-added-by-v0140.txt).

## What this release does not improve

Verified against the closing tree, and unchanged by this measurement:

- **The reorder gain is conditional.** No `RefreshStatistics`, no gain. Wrong query shape, no
  gain. A shape whose components a plain label count can already separate, no gain.
- **The bitmap-clone fix only pays when MVCC history is live.** A same-label bitmap clone
  still costs 38 allocations when the churn is on the counted label and the correction
  genuinely runs; #2773 removed the case where the clone was *pointless*, not the case where
  it is real.
- **`exec.OptionalExpand` is unreachable from any query** — 0 of 11 `OPTIONAL MATCH` shapes
  plan it. Unwired, not dead (#2769).
- **`exec.RenderPlan` has no caller** and renders a plan missing this release's own columns
  (#2770).
- **An MCV equality estimate is tagged `exact` with no staleness check** (#2772), and the
  most-wrong estimate is the one q-error cannot see, because columnar fusion chains carry no
  estimate at all.
- **Estimate coverage is 80 of 110 operator instances rendering `-`.**

## Limits — what this document cannot support

1. **Timing is unmeasured.** Not "unchanged", not "within noise" — **unmeasured**. Eight
   interleaved rounds were planned; the host load made the wall-clock dimension
   indefensible and the run was stopped after the data that mattered was in.
2. **Sample counts are small** — 1 to 4 per benchmark per arm, from one complete round of the
   reduced experiment plus one complete round of a larger-scope first attempt. This is
   adequate for `allocs/op`, which is deterministic for a given binary and workload, and it
   is *why* the stability check across rounds is reported rather than assumed. It would not
   be adequate for timing.
3. **Floor 1 does not capture code-layout noise.** `B` and `B2` are byte-identical, so the
   floor is pure host noise. A layout-induced difference between the two *versions* is not
   separated from a real one — though for allocation counts, layout is not a plausible
   mechanism.
4. **Only `allocs/op` is a verdict.** `B/op` is `TotalAlloc/N` with varying `N` and is
   reported nowhere as evidence.
5. **#2771's isolated contribution is not separated**, as explained above.
6. **`bench/audit352/labelcount_gate_ab_test.go`** also differs between the trees (plan-text
   assertions). It was not measured.

## Reproduction

```sh
SP=<scratch>                    # worktrees, binaries and results all live here

# 1. Two clean worktrees. Nothing is edited in the user's checkout.
git worktree add --detach $SP/wt13 v0.13.0
git worktree add --detach $SP/wt14 HEAD
cp cypher/api.go $SP/wt14/cypher/api.go          # the one uncommitted Go change

# 2. Carry the instruments across so the comparison is head-to-head.
cp $SP/wt14/cypher/exec/shortest_path_bench_test.go $SP/wt13/cypher/exec/
cp zzport_reorder_bench_test.go $SP/wt13/cypher/ ; cp zzport_reorder_bench_test.go $SP/wt14/cypher/
( cd $SP/wt13 && go vet ./cypher/ ./cypher/exec/ )   # exit 0 — the API exists at v0.13.0

# 3. Three arms. -trimpath so the worktree path is not baked in and the
#    sha256 of a binary becomes real evidence about the CODE.
for pkg in cypher/exec cypher store/wal store/txn; do
  ( cd $SP/wt13 && go test -trimpath -c -o $SP/bin/${pkg//\//_}_A.test  ./$pkg/ )
  ( cd $SP/wt14 && go test -trimpath -c -o $SP/bin/${pkg//\//_}_B.test  ./$pkg/ )
  ( cd $SP/wt14 && go test -trimpath -c -o $SP/bin/${pkg//\//_}_B2.test ./$pkg/ )
done
shasum -a 256 $SP/bin/*.test     # B == B2 ; store_wal_A == store_wal_B

# 4. Plan-and-result attribution, both trees.
( cd $SP/wt13 && go test -run TestZZDumpPlanAndResult -v -count=1 ./cypher/ )
( cd $SP/wt14 && go test -run TestZZDumpPlanAndResult -v -count=1 ./cypher/ )

# 5. Interleaved rounds. See run_ab2.sh in the raw directory.
#    stderr goes to its OWN file: 2>&1 splices the engine's construction WARN into
#    the result stream and destroyed 4 of 6 result lines during sizing.
./run_ab2.sh

# 6. Verdicts.
python3 allocs.py
```

Exit codes were appended to `exits.log` and read from there, never from a pipeline's status.
**All 33 benchmark invocations across both runs exited 0** (17 + 16). Every invocation is
bracketed by `uptime` before and after in
[`loadavg.log`](v0130-vs-v0140-2026-09-06-raw/loadavg.log).
