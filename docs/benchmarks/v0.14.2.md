# Benchmarks — v0.14.2

The per-release measured record for `v0.14.2`, taken against `v0.14.1` first-hand. Nothing
here is carried forward from the `v0.14.1` campaign and nothing is derived from a figure
taken during development: the `v0.14.1` tree was extracted and **re-measured from scratch**,
in the same rounds, on the same host, against the same noise floor.

**This record is not a release gate.** The benchmark step was removed from the release path
by decision while this campaign was running, and the campaign was stopped at that point. What
follows is a standalone measured record of what was collected, complete with the reduced
statistical power that stopping imposed. That power is stated in
[§3](#3-the-campaign-and-the-power-it-actually-has) and it governs every number below.

**Headline: the release provably changed nothing in three of the seven packages measured, and
of the 212 comparable rows in the four packages whose binary did change, exactly two move by
more than this campaign's own false-positive envelope. The one cost that is established
beyond any question of statistical power is an allocation cost, not a time cost: an absorbed
`DROP INDEX … IF EXISTS` gains 2 allocations, and a relationship `SET` gains 1 allocation per
bound relationship in storage order and 10 per two-row undirected statement.** Every
allocation figure here is a per-operation constant with every sample equal in both arms, which
is true at any sample size. The timing figures are not, and they are labelled accordingly.

## 0. What is provably unchanged — and this costs nothing to establish

`go build` is deterministic here under `-trimpath`, so a test binary's sha256 is evidence
about the **code**, not about a run. Compiling all seven packages in all three arms
([`binary-sha256.txt`](v0.14.2-raw/binary-sha256.txt)) gives this:

| Package binary | `B` == `B2` (determinism) | `A` == `B` (the two releases) |
|---|---|---|
| **`search`** | yes | **yes — byte-identical** |
| **`search/centrality`** | yes | **yes — byte-identical** |
| **`graph/index/count`** | yes | **yes — byte-identical** |
| `cypher` | yes | no — code changed |
| `cypher/exec` | yes | no — code changed |
| `bolt/server` | yes | no — code changed |
| `benchharness` (purpose-built, §8) | yes | no — links changed engine code |

**For `search`, `search/centrality` and `graph/index/count` the release changed nothing, and
that is proved rather than measured.** A hash establishes equality; a benchmark can only fail
to detect a difference. These three packages host the release gate's entire headline set
(`scripts/run_headline_bench.sh` — `Dijkstra_PostWarmup`, `Dijkstra_Large`,
`BFSDirectionOpt_PowerLaw`, `Yen_K100`, `Brandes_RandomGraph`), so **the headline benchmarks
execute byte-identical machine code at `v0.14.1` and at `v0.14.2`**. No campaign, at any
sample size, could add anything to that.

Their measured rows are therefore **not results**. They are a cross-arm noise floor — the same
binary compared against itself across the arms — and that is how §5 and §6 use them.

| Headline benchmark (round 1, `ns/op`) | `A` = v0.14.1 | `B` = v0.14.2 | `B2` = floor |
|---|---:|---:|---:|
| `Dijkstra_PostWarmup` | 8.225 ms | 8.132 ms | 8.179 ms |
| `Dijkstra_Large` | 8.182 ms | 8.302 ms | 8.206 ms |
| `BFSDirectionOpt_PowerLaw` | 28.93 ms | 28.85 ms | 28.86 ms |
| `Yen_K100` | 14.73 ms | 14.70 ms | 14.78 ms |
| `Brandes_RandomGraph` | 7.916 ms | 7.849 ms | 7.927 ms |

The spread across those fifteen numbers is host noise on identical code, and it is the honest
measure of what this host can resolve. `Dijkstra_PostWarmup` and `BFSDirectionOpt_PowerLaw`
report **0 B/op and 0 allocs/op in every arm**, which is the zero-allocation hot-path mandate
verified rather than asserted. `Dijkstra_Large` reports 1 129 264 B/op at `A`, 1 203 833 at
`B` and 1 129 358 at `B2` — a 6.6 % swing on a binary that cannot have changed, and the single
most useful reminder in this document of how to read a single sample.

## 1. The arms

| Arm | Tree | Commit | Role |
|---|---|---|---|
| `A` | `git archive` of tag `v0.14.1` | `9a6f7561` | base |
| `B` | `git archive` of `release/0.14.2` at `HEAD` | `92c47fda` | head |
| `B2` | a **second, independent compilation of the same `v0.14.2` tree** | `92c47fda` | **noise floor** |

The arms are extracted with `git archive` rather than checked out as git worktrees. The
measurement then writes nothing into the repository's git administrative area and leaves no
worktree behind. Each tree is extracted under a `.noindex` directory so Spotlight does not
index it and contaminate the host — it did exactly that during the `v0.14.1` campaign.

`B` and `B2` are byte-identical for all seven packages, so `B` vs `B2` is **the same binary
measured against itself, in the same rounds, in the same interleaving, under the same load**
as the signal it calibrates.

### What actually changed, and why the campaign is shaped the way it is

The window is one sprint (rmp 361, a bug-fixing campaign, twelve tasks). The engine delta is
**five non-test files**:

| File | Δ | What changed |
|---|---|---|
| `cypher/api.go` | +181/−21 | `dropIndexCounter` suppresses the indexes-removed count when `DROP INDEX … IF EXISTS` removed nothing, at the price of one `idxMgr.GetIndex` read before the operator; `isEntityPropertyValue` / `errEntityPropertyValue` reject node-, relationship- and path-valued properties on four write paths; one new `scalarColSnapshot` call at plan-build time; `Result.counters` dropped on a rolled-back statement; godoc |
| `cypher/exec/set.go` | +53/−3 | `relStorageDirection` normalises a relationship `SET` target from the row's traversal order to the edge's storage order |
| `cypher/exec/set_all.go` | +31/−0 | the REPLACE-form arm of the same entity-value rejection |
| `bolt/server/errors.go` | +66/−2 | three new `Neo.ClientError.*` branches in `FailureCode` |
| `bolt/server/serve.go` | +23/−4 | **godoc only** — no compiled change |

Everything else in the window is `*_test.go`, `internal/sim/` (the deterministic simulator's
oracle), or documentation.

**No benchmark in the module drives the changed write paths, and that was established from the
source before anything was measured.** Of the `cypher` package's 149 benchmarks exactly one
names a Cypher `SET` clause — `BenchmarkQueryHasWritingClause`, which classifies a query string
without executing it. Of `cypher/exec`'s 36, none does. No benchmark anywhere in the module
issues `DROP INDEX`. Two `cypher` benchmarks (`ReadPhaseForeignWriter`,
`ReadPhaseAttribution`) run a throttled background `SET n.bal = $v` while **measuring a read**,
so they price the read path, not the write, and they are excluded for that reason. The scan is
reproducible: [`benchbodies.py`](v0.14.2-raw/benchbodies.py) and
[`setscan.py`](v0.14.2-raw/setscan.py).

The campaign is therefore three things:

- **`harness`** — a purpose-built vehicle for the changed write paths ([§8](#8-the-question-a-reader-will-ask-what-did-set-and-drop-index-cost)).
- **`exec`, `cy`, `bolt`** — the three packages whose test binary changed, run as a
  whole-package **regression watch**. Since no benchmark in them reaches a changed symbol,
  what they test is whether the edit moved anything through code motion, inlining or layout.
- **`search`, `centrality`, `cnt`** — the headline set and the cross-arm floor of §0.

### Method

- **Three arms, interleaved arm-by-arm within each block** — never all of A then all of B.
  The arm order is **rotated every round** (round 1 `A B B2`, round 2 `B B2 A`), so no arm
  systematically inherits another's cache and thermal aftermath.
- **A load gate before each round**, recorded with the value it opened at, bounded at 600 s.
- **`uptime` bracketed before and after every single invocation**, and a 2 s load sampler
  running for the whole campaign so the load **during** an invocation can be sliced out.
- **Exit codes appended to `exits.log` and read from there**, never from a pipeline's status.
- **stderr to its own file per invocation** — never `2>&1`.
- **Every kept line validated** against `^Benchmark\S*\s+\d+\s+`, with the arms' benchmark
  sets asserted equal and the per-arm sample count printed before any comparison is read.
- **Nothing was mirrored into the repository while the campaign ran.** The `v0.14.1` campaign
  copied its raw files into `docs/benchmarks/` after every round and Spotlight indexed them
  mid-run, putting `mdworker_shared` at 75.7 % CPU inside round 4. Here the per-round mirror
  is a scratch directory under `.noindex` and the repository copy happened once, after the
  campaign ended. **No contamination event of that kind occurred.**

## 3. The campaign, and the power it actually has

**Read this before any number in §5 onwards.**

The campaign was designed as six rounds. It was stopped by decision after **round 1 completed
and round 2 reached the `search` block**. That is the whole evidence base; nothing was topped
up afterwards, and no benchmark was re-run to fill a gap.

| Property | Value |
|---|---|
| Window | **2026-09-15T19:11:03Z → 19:54:23Z** (43.3 min) |
| Rounds planned / completed | **6 planned, 1 complete + 1 partial** |
| Invocations | **35** |
| Invocations exiting 0 | **35 / 35** |
| `uptime` brackets | 35 before + 35 after |
| Load samples | **1 310**, one every 2 s for the whole campaign |
| Result lines kept | **A 438, B 442, B2 442** |
| Malformed lines | **0** |

| Block | Package | Benchmarks | Rounds with **all three** arms | `n` per arm used |
|---|---|---:|---:|---:|
| `harness` | `benchharness` (purpose-built) | 8 | 1, 2 | **2** |
| `exec` | `cypher/exec` (all) | 62 | 1, 2 | **2** |
| `cy` | `cypher` (60 of 149 functions) | 115 | 1, 2 | **2** |
| `bolt` | `bolt/server` (all) | 27 | 1, 2 | **2** |
| `search` | headline 4 | 4 | 1 | **1** |
| `centrality` | `Brandes_RandomGraph` | 1 | 1 | **1** |
| `cnt` | `graph/index/count` (all) | 9 | 1 | **1** |

`search` ran a second time for arms `B` and `B2` but not for `A` before the stop, so **every
block is truncated to the rounds in which all three arms ran**. No arm is ever compared
against a round its siblings never saw. Integrity table:
[`integrity.txt`](v0.14.2-raw/integrity.txt).

### What this power permits, and what it forbids

- **No p-value is computed anywhere in this document.** A Mann-Whitney U needs `n ≥ 4` per arm
  to have a usable distribution; at `n = 2` it has none. Quoting a p-value here would be worse
  than quoting nothing, so none is quoted.
- **`benchstat`'s confidence interval is equally unavailable.** It needs six samples; there are
  at most two. The comparison below is therefore stated as a median (a mean of two, at `n=2`)
  rather than as an interval, and **every individual sample is printed for every row this
  document calls a finding** ([§7](#7-the-findings)). The complete per-sample record for every
  row is in the raw `*_A.txt` / `*_B.txt` / `*_B2.txt` files.
- **The six-round adjudication bar `v0.14.1` published does not exist here and is not
  borrowed.** What replaces it is a false-positive rate measured *inside this campaign* on code
  that provably did not change ([§6](#6-the-calibration-and-the-rule-it-supports)).
- **A row that separates but does not clear that calibration is reported as *not adjudicable at
  this power* — never as unchanged.** Failing to resolve a difference is not evidence that
  there is none, and the two are not run together anywhere below.
- **Allocation counts are the exception, and they carry full weight.** `allocs/op` is normally
  a per-operation *constant*, not a statistic. Where every sample within each arm is equal and
  the two constants differ, the difference is real at any sample size — it does not depend on
  power at all. Every allocation claim in this document is of that form.

## 4. The load evidence

`uptime` brackets cannot see a spike that begins and ends inside an invocation, so one sampler
ran for the whole campaign at a 2 s cadence and every invocation recorded its own start and
end instants. Sliced per block, over all its invocations
([`loadstats.txt`](v0.14.2-raw/loadstats.txt)):

| Block | invocations | min | max | **mean** |
|---|---:|---:|---:|---:|
| `harness` | 6 | 2.04 | 2.49 | **2.26** |
| `exec` | 6 | 1.98 | 3.78 | **2.92** |
| `cy` | 6 | 2.68 | 5.13 | **3.72** |
| `bolt` | 6 | 3.68 | 6.79 | **5.19** |
| `cnt` | 3 | 5.19 | 6.37 | **5.71** |
| `centrality` | 3 | 6.02 | 6.37 | **6.14** |
| `search` | 5 | 5.14 | 13.51 | **8.17** |
| **campaign** | **35** | **1.98** | **13.51** | **4.26** |

**The load rises monotonically through a round, and it is the benchmarks' own load.** A block
that runs late in a round inherits the whole round's accumulated work. This is precisely why
all three arms of a block run adjacently: an arm is compared only against siblings that ran
under the same accumulated load.

| Round | Opened at 1-min load | Waited | Gate satisfied | Closed at |
|---|---:|---:|---|---:|
| 1 | 2.36 | 0 s | yes | **5.48** |
| 2 | 2.21 | 100 s | yes | stopped mid-round |

**Round 1 closed at load 5.48, and that matters.** The closing load is not a defect of the
method — it is the campaign's own benchmarks saturating a 10-core host — but it does mean the
blocks that ran late in a round (`bolt`, `cnt`, `centrality`, `search`) were measured under
two to three times the load of the blocks that ran early. With only one or two rounds there is
no second, differently-ordered sample to average that away, so **confidence is not uniform
across the blocks**: it is highest for `harness` (load 2.04–2.49 across all six of its
invocations, the quietest block in the campaign and the one carrying §8's result) and lowest
for `search`, `centrality` and `cnt` — which is tolerable exactly because those three are
byte-identical binaries whose rows are floor, not signal.

Residual host load was not zero and is not claimed to be: iTerm2, a persistent `osascript`,
`WindowServer` and Firefox held roughly 0.3–0.5 of one core throughout, and the per-round gate
recorded the hot-process list each time
([`loadavg.log`](v0.14.2-raw/loadavg.log), [`progress.log`](v0.14.2-raw/progress.log)).

## 5. The noise floor — measured first, before any delta was attributed

**Nothing in this document was attributed before this section's numbers existed.**

### 5.1 Floor 1 — the same binary against itself, in the same rounds

`B` vs `B2`, byte-identical binaries, the four blocks whose binary changed, `n=2` per arm.

| Metric | Comparisons | median \|Δ\| | p90 \|Δ\| | p95 \|Δ\| | max \|Δ\| |
|---|---:|---:|---:|---:|---:|
| `sec/op` | **212** | **0.55 %** | 1.83 % | 2.88 % | **16.48 %** |
| `allocs/op` | **182** | **0.00 %** | 0.00 % | 0.00 % | 4.06 % |

Stratified by the magnitude of the benchmark, because a 6 % drift means one thing at 1 ms and
another at 2 ns:

| Magnitude band | n | median \|Δ\| | p90 | p95 | max |
|---|---:|---:|---:|---:|---:|
| < 100 ns | 26 | 0.96 % | 2.20 % | 3.96 % | 7.83 % |
| 100 ns – 10 µs | 54 | 0.60 % | 2.02 % | 2.88 % | **16.48 %** |
| 10 µs – 1 ms | 63 | 0.49 % | 1.71 % | 1.83 % | 15.61 % |
| > 1 ms | 69 | 0.51 % | 1.36 % | 2.02 % | 13.72 % |

The `sec/op` maximum, **−16.48 % on `exec/BenchmarkScan_PerNode/N=4096`**, is a single wild
same-code sample: arm `B2` measured 4 609 ns in round 1 and 7 434 ns in round 2 on the
identical binary. **One same-code outlier of that size is why no bar in this document is set
from a maximum** — a bar set there would reject everything, which is not a bar but a refusal
to look.

**`allocs/op` is all but exact** — 0.00 % at the median, the p90 *and* the p95 across 182
comparisons. That is what makes §8's allocation results usable despite the power.

### 5.2 Floor 2 — an identical binary compared *across* the arms

`search`, `search/centrality` and `graph/index/count` compile to byte-identical test binaries
at both releases (§0), so `A` vs `B` on them is noise by construction — and it catches what a
within-arm floor structurally cannot, because it includes whatever differs between running arm
A's binary and arm B's.

| Metric | Comparisons | median \|Δ\| | p90 \|Δ\| | p95 \|Δ\| | max \|Δ\| |
|---|---:|---:|---:|---:|---:|
| `sec/op` | **14** | 0.99 % | 3.15 % | 4.27 % | **4.88 %** |
| `allocs/op` | 4 | **0.00 %** | 0.00 % | 0.00 % | **0.00 %** |

`n=14` is a real limitation and is not dressed up. Its value is not its size but its
*construction*: these are cross-arm comparisons of code that is provably identical, which is
exactly what §6 needs.

## 6. The calibration, and the rule it supports

At `n=2` the only non-parametric statement available is **range disjointness**: arm `A`'s
entire sample range lying outside the pooled range of `B` and `B2`, which are the same binary
and therefore supply a direct in-campaign observation of same-code spread.

That criterion needs calibrating, and this campaign calibrates it **exactly**, because Floor 2
is a set of comparisons in which the answer is known in advance to be "no difference":

> **Of the 14 cross-arm rows on byte-identical binaries, 5 — 36 % — satisfy range
> disjointness.** The worst of these false positives is `cnt/BenchmarkApply_HotParallel` at
> **+4.40 %** with a range gap of **3.15 %**.

**Range disjointness at `n=2` is therefore worth nothing on its own.** A row in a changed
package is reported here only when it exceeds *both* of those worst false-positive figures:

| Rule | Threshold | Source |
|---|---:|---|
| `|Δ|` must exceed | **4.40 %** | worst false positive on provably unchanged code |
| range gap must exceed | **3.15 %** | worst false-positive gap on provably unchanged code |

For `allocs/op` the calibration is stronger and simpler: **0 of 4 cross-arm rows and 0 of 182
within-arm rows produced a differing constant on unchanged code**, so a differing per-operation
constant is admitted directly.

For `B/op` the calibration rests on **four rows and produced two false positives (50 %)**,
which is too weak to sustain any bar at all. `B/op` is therefore used only as corroboration of
an `allocs/op` constant, never on its own. Full output:
[`adjudication.txt`](v0.14.2-raw/adjudication.txt), [`separation.txt`](v0.14.2-raw/separation.txt).

### The result of applying it

Over the **212 comparable rows in the four changed-binary blocks**:

| Outcome | Rows |
|---|---:|
| `sec/op` clears the calibration | **2** |
| `allocs/op` differing per-operation constants | **3** |

## 7. The findings

### 7.1 Timing — two rows of 212 clear the calibration

Δ is arm `A` against arm `B`. The *gap* is the distance between arm `A`'s sample range and the
pooled `B` ∪ `B2` range, which is the quantity §6 calibrates.

| Block | Benchmark | `v0.14.1` (`A`) | `v0.14.2` (`B`) | Δ | gap | every sample |
|---|---|---:|---:|---:|---:|---|
| `harness` | `H_DropIndexMissing` | 1.003 µs | 1.117 µs | **+11.42 %** | 9.47 % | A 1000, 1006 · B 1124, 1111 · B2 1150, 1101 (ns) |
| `exec` | `BuildReverse_vs_E/E=1000000` | 5.554 ms | 5.075 ms | **−8.61 %** | 6.97 % | A 5482, 5625 · B 5095, 5055 · B2 5089, 5055 (µs) |

**`H_DropIndexMissing` is the release's one established time cost, and §8 treats it in full.**
Every one of arm A's samples lies below every one of the four `B`/`B2` samples, with a 95 ns
gap between the two ranges; the arm order was rotated between the rounds, so arm A ran first in
round 1 and last in round 2 and was faster in both. In absolute terms the statement moved from
1 003 ns to 1 117 ns: **+115 ns**.

**`BuildReverse_vs_E/E=1000000` is an improvement that no changed symbol explains, and it is
reported as unexplained rather than claimed.** `B` and `B2` agree to 0.1 % while `A` sits ~8 %
above both, in both rounds and in both arm orders. Nothing in `cypher/exec/set.go` or
`set_all.go` is on the reverse-adjacency build path. The plausible reading is a code-motion or
layout effect from the package binary changing — which is exactly the risk the whole-package
regression watch exists to detect — but **attribution is not established**: no third arm was
built to isolate it, and at `n=2` this cannot be separated from a two-round coincidence.

### 7.2 Allocations — three differing per-operation constants, all in the harness

These do not depend on statistical power. Every sample within each arm is equal, in both arms.

| Benchmark | `allocs/op` | `B/op` | What it prices |
|---|---|---|---|
| `H_SetRelPropUndirected` | **251 → 261 (+10)** | 44 654 → 45 112 (**+458**) | a two-row undirected relationship `SET` (#2817) |
| `H_DropIndexMissing` | **25 → 27 (+2)** | 1 313 → 1 313 (**+0**) | an absorbed `DROP INDEX … IF EXISTS` (#2818) |
| `H_SetRelPropDirected` | **214 → 215 (+1)** | 41 434 → 41 469 (+35) | a one-row directed relationship `SET` (#2817) |

**No other benchmark in the campaign moved an allocation count** — not one of the 182
`allocs/op` comparisons outside the harness, and none in the three byte-identical packages.

`H_DropIndexMissing`'s +2 allocations with **+0 B/op** is stated exactly as measured: `B/op` is
1 313 in all six samples across all three arms while the malloc count moves 25 → 27. No
mechanism is asserted for that; it is what the runtime reported.

### 7.3 What is *not* claimed

`cy/BenchmarkCreateRelationships` shows `B/op` 5 083 988 → 5 417 322 (+6.56 %) and formally
satisfies the disjointness test. **It is rejected, and the raw samples are why:** arm A
measured 4 846 078 in round 1 and 5 321 898 in round 2 — a 9.8 % swing *within one arm*,
larger than the difference being claimed — while `B2` (5 380 173 / 5 481 152) sits alongside
`B`. The `allocs/op` figures for that row overlap in all three arms. This is a single
low-outlier in arm A's first round, not a regression, and the weak `B/op` calibration of §6 is
precisely what stops it being reported as one.

## 8. The question a reader will ask: what did `SET` and `DROP INDEX` cost?

The `SET` change adds a validation branch on a write path and the `DROP INDEX` change adds an
existence read. Both are answered here with numbers, on a vehicle built for the purpose because
the module's own benchmark corpus does not drive either path (§1).

**The vehicle.** [`harness_bench_test.go`](v0.14.2-raw/harness_bench_test.go.txt) is a purpose-built
package that existed only inside the three scratch trees, byte-identical in all three arms.
**It was never added to the module and the module never builds it** — the source is preserved in
the raw directory as evidence, and the trees that held it have been removed. It builds a 64-node
directed multigraph ring through the public Cypher API alone and issues one statement per
iteration. **Representativeness, stated
plainly:** it is in-memory, with no store, no WAL, no durability and no concurrency, so it
prices the changed code against the **least favourable denominator available** — a durable
deployment adds fsync time to the denominator and makes the same absolute cost a smaller
proportion of a statement. It is not a model of a production workload and no throughput claim is
made from it. It ran under the quietest load in the campaign (1-min load 2.04–2.49 across all
six invocations).

| Benchmark | Statement | `ns/op` A → B | `allocs/op` | verdict |
|---|---|---:|---:|---|
| `H_SetNodeProp` | `MATCH (n:N {id:$id}) SET n.v = $v` | 15.36 → 14.91 µs (−2.91 %) | **101 → 101** | **no measurable cost**; Δ inside the false-positive envelope, allocation count unchanged |
| `H_SetNodeReplaceMap` | `MATCH (n:N {id:$id}) SET n = {id:$id, v:$v, k:$id}` | 16.39 → 16.18 µs (−1.31 %) | **130 → 130** | **no measurable cost** |
| `H_SetNodePropPlanMiss` | as above, statement text varied to force a plan build | 14.68 → 14.77 µs (+0.61 %) | **102 → 102** | **no measurable cost** — the build-time `scalarColSnapshot` call does not show |
| `H_SetRelPropDirected` | `MATCH (a:N {id:$id})-[r:R]->(b:N) SET r.v = $v` | 48.21 → 49.14 µs (+1.94 %) | **214 → 215 (+1)** | **+1 allocation per bound relationship**; no resolvable time cost |
| `H_SetRelPropUndirected` | `MATCH (a:N {id:$id})-[r:R]-(b:N) SET r.v = $v` | 50.40 → 51.03 µs (+1.24 %) | **251 → 261 (+10)** | **+10 allocations per two-row statement**; no resolvable time cost |
| `H_DropIndexMissing` | `DROP INDEX bench_absent IF EXISTS` | **1.003 → 1.117 µs (+11.42 %)** | **25 → 27 (+2)** | **a real cost: +115 ns and +2 allocations per absorbed statement** |
| `H_CreateDropIndex` | `CREATE INDEX …` + `DROP INDEX …` per iteration | 19.02 → 18.77 µs (−1.28 %) | **108 → 108** | **no measurable cost** on the real-removal path |
| `H_MatchReturn` | `MATCH (n:N {id:$id}) RETURN n.v` — the harness's own control | 31.44 → 29.44 µs (−6.37 %) | **98 → 98** | control: reaches no changed symbol; its −6.37 % is a **measurement** artefact and the reason the calibration of §6 exists |

**The `SET` entity-value rejection (#2816) costs nothing this campaign can measure.** The three
node-`SET` shapes — the scalar form, the REPLACE map form and the plan-miss form that forces a
fresh plan build — hold their allocation counts exactly (101, 130, 102 in both arms) and their
timings sit inside the false-positive envelope. The per-row `isEntityPropertyValue` guard is a
type switch on a value the evaluator already has in hand, and it does not show.

**The relationship storage-order normalisation (#2817) costs allocations, and part of that cost
is the defect being fixed.** A directed bind gains 1 allocation; an undirected two-row statement
gains 10. Those do not decompose to the same per-row constant, and the reason is visible in the
change itself: at `v0.14.1` both rows of an undirected match wrote to the *same* pair — that was
the bug, one edge stamped twice and the other never — while at `v0.14.2` the reverse-hop row is
normalised and writes to the *second*, distinct edge. **So part of the +10 is `relStorageDirection`'s
by-handle probes and part of it is a property write that v0.14.1 skipped entirely.** Separating
the two would need a third arm with the normalisation disabled, which was not built:
**the split is a hypothesis consistent with the diff, not a measured attribution.** No time cost
is resolvable on either shape at this power.

**The `DROP INDEX` existence read (#2818) is the one change with an established cost.** On the
absorbed `IF EXISTS` path — the cleanest possible vehicle, since the statement changes nothing
and the added `idxMgr.GetIndex` read is essentially the whole difference — it is
**+115 ns on a 1.0 µs statement (+11.4 %) and +2 allocations**. It is the only row in the
campaign to clear the §6 calibration on both `|Δ|` and gap — by a factor of 2.6 on `|Δ|` and
3.0 on the gap.

**In proportion, this is a DDL statement's cost, not a query path's.** `DROP INDEX` executes
under the engine's exclusive DDL lock, once per statement, and on the real-removal path
(`H_CreateDropIndex`, which pays a `CREATE INDEX` in the same iteration) the added read does not
rise above the floor at all: 19.02 → 18.77 µs with allocations unchanged at 108. The 115 ns buys
a counter that stops `DROP INDEX <missing> IF EXISTS` reporting `indexesRemoved: 1` over an index
listing that is identical before and after.

## 10. What this snapshot does NOT measure

**Packages not measured, each with its reason grounded in the diff.** Every one of these has
**unchanged source** in this window *and* **no dependency path to `cypher/` or `bolt/`**, so no
changed symbol is reachable from any of their benchmarked entry points. That is a proof from
`go list -deps`, not a judgement:

| Not measured | Reason |
|---|---|
| `graph`, `graph/index`, `graph/index/btree`, `graph/index/hash` | source byte-identical to `v0.14.1`; no dependency edge to `cypher/` or `bolt/`, so no changed symbol is reachable from their benchmarked paths |
| `graph/lpg`, `graph/mvcc` | as above |
| `store/txn`, `store/checkpoint`, `store/recovery`, `store/snapshot`, `store/wal` | as above — the whole durability stack is unchanged in this window and cannot reach the changed code |
| `internal/metrics/prometheus` | as above |
| `internal/sim` | **changed** (+4 files) and it does depend on `cypher`, but it is the deterministic simulator's **oracle** — test infrastructure, not shipped engine code, and on no path a consumer runs |
| the other 89 of `cypher`'s 149 benchmarks | the `cy` selector is carried over verbatim from the `v0.14.1` campaign so the two records compare like with like. **`cypher` is sampled, not covered — 60 of 149 functions, 40 %.** |
| every concurrency ladder (`-test.cpu=1,8,64,256,1024`) | the two ladders the README publishes were in the six-round design and were **dropped with the campaign**, not by choice. **The published concurrency levels are unmeasured for this release.** |

**Not measured at all:**

1. **Rounds 2 through 6 of the design.** The campaign delivered 1 complete round and part of a
   second out of six. Everything in §3 follows from that.
2. **Latency percentiles at the published concurrency levels.** Everything here is per-op cost.
   **Ninth consecutive cycle.**
3. **The durable commit path at any concurrency.** `store/txn` was not in this campaign's block
   set, because its source did not change.
4. **On-disk footprint growth.** No benchmark reporting bytes written to disk was run.
5. **`bench/mtaudit`'s engine-under-writer ladder** — `v0.14.0` called this "the single
   highest-value measurement not made, now for two consecutive releases"; it is now four.
6. **The soak and nightly layers**, and any production certification.
7. **No `-race` figures and no profiles.** Every allocation number here is a non-race number and
   must not be compared against one taken under `-race`.
8. **Nothing here is a comparison against Neo4j, Memgraph or any other engine.**

**Three limitations specific to this campaign:**

9. **Attribution is established for nothing.** No third arm was built with the normalisation or
   the existence read disabled, so every cause named in §7 and §8 is a hypothesis consistent
   with the diff, not a measured attribution. A profile would not fix this: a profile shows
   where time goes in one arm, never why two arms differ.
10. **Confidence is not uniform across blocks.** §4 shows the load rising two- to three-fold
    through a round; with one or two rounds there is no differently-ordered sample to average
    that away. `harness` is the most trustworthy block and `search`/`centrality`/`cnt` the
    least — which is acceptable only because those three are byte-identical binaries.
11. **One host, one architecture** — Apple M4, 10 cores, `darwin/arm64`, macOS 26.6.2. The
    floors in §5 and the calibration in §6 are properties of **this host and this run**, and do
    not transfer.

## 11. Reproduce

All three arms are pre-compiled once, before any timing, and each arm runs its own binary.
Every script is in [`v0.14.2-raw/`](v0.14.2-raw/) and was used verbatim.

```bash
# 1. Three trees, extracted with `git archive` rather than `git worktree`, so the
#    measurement writes nothing into .git — and under a .noindex directory so
#    Spotlight does not index them and contaminate the host (it did exactly that
#    during the v0.14.1 campaign).
git archive --format=tar v0.14.1 | tar -x -C <scratch>/bench.noindex/A
git archive --format=tar HEAD    | tar -x -C <scratch>/bench.noindex/B
git archive --format=tar HEAD    | tar -x -C <scratch>/bench.noindex/B2

# 2. The purpose-built vehicle, byte-identical in every arm. It lives ONLY in the
#    scratch trees and is never compiled as part of the module. It ships here as
#    harness_bench_test.go.txt: a .go file under docs/ would enter `./...` and be
#    linted as module code, which is what it is not.
cp v0.14.2-raw/harness_bench_test.go.txt \
   <scratch>/bench.noindex/{A,B,B2}/benchharness/harness_bench_test.go

# 3. Build A, B and B2. -trimpath so the tree path is not baked in and a binary's
#    sha256 becomes real evidence about the CODE.
bash build.sh                          # 21 builds; every exit code in build-exits.log
shasum -a 256 <scratch>/bin/*.test > binary-sha256.txt
#   assert B == B2 for every package  -> the within-arm floor is valid
#   note which A == B                 -> those are the cross-arm floors, and the
#                                        PROOF that those packages did not change

# 4. Size the campaign from a MEASURED cost, never a guessed one.
bash size.sh                           # one invocation of every block on arm B, timed

# 5. The campaign: interleaved, arm order rotated every round, load-gated per round,
#    uptime bracketed per invocation, stderr to its own file, exits to exits.log,
#    and NOTHING mirrored into the repository while it runs.
ROUNDS=6 GATE=2.5 nohup bash campaign.sh &

# 6. Integrity FIRST, then floors, then the calibration, then effects. In that order.
python3 report.py integrity
python3 report.py floor
python3 separation.py ns/op            # range disjointness, per metric
python3 adjudicate.py                  # calibrated on the byte-identical packages
python3 loadstats.py <scratch>/raw/campaign

# 7. Which benchmarks reach the changed symbols — answered from the SOURCE.
python3 benchbodies.py <tree>/cypher '\bSET\b'
python3 setscan.py    <tree>/cypher 'DROP INDEX'
```

**Validate before you believe any comparison.** Assert that every kept line matches
`^Benchmark\S*\s+\d+\s+`; a log line landing mid-result silently removes samples and
`benchstat` will not tell you. Count the surviving result lines against the number expected,
per arm, per block.

**Read every exit status from inside the log, never from a wrapper.** A `… | tail` pipeline
reports `tail`'s status, and a real `Error 1` has been masked that way on this project before.
`exits.log` is written by the runner itself, one line per invocation.

**And do not re-use this document's bars.** The §6 calibration is the worst false positive
*this run* produced on *this host*. Re-derive it from Floor 2 every time.
