# Benchmarks — v0.7.0

Headline benchmark and load-test numbers for the GoGraph **v0.7.0**
release. v0.7.0 is a **feature release** whose headline is openCypher
completeness and correctness (eight new builtin functions, `MERGE`
whole-pattern match-or-create semantics, parallel-edge rejection) and a
broad security and denial-of-service hardening pass, alongside a
measurable win from caching the `O(V+E)` edge-type filter across
queries. Per-change performance records live in
[`history/`](history/) and [`history/LEDGER.md`](history/LEDGER.md).

The figures below were re-measured for this release with
[`scripts/run_headline_bench.sh`](../../scripts/run_headline_bench.sh)
(`-count=6`, median reported) and the read-path concurrency sweep
(`-count=5`, median reported). They are the authoritative per-release
performance picture for v0.7.0.

> Re-measure on your own hardware before relying on any absolute
> number; these are medians from documented runs, not a guarantee.

The two post-warmup traversal paths (`Dijkstra_PostWarmup`,
`BFSDirectionOpt_PowerLaw`) allocate **zero** bytes per call, confirming
the zero-allocation hot-path mandate still holds for the reusable-state
query forms.

`BenchmarkDijkstra_Large` drops from **5 → 4 allocs/op** relative to
`v0.6.0` (see the [comparison section](#v060--v070-comparison) below) —
a real, measured guard-band improvement from pre-sizing the pooled
Dijkstra heap's backing array (#1820), reclaiming a stray heap escape
that had regressed the guard band since `v0.5.0`.

## Performance impact of this release

This release's headline is correctness and security hardening, not a
broad performance-audit cycle. Two measured performance changes land in
this cycle:

1. **The `O(V+E)` edge-type filter is cached across queries** (#1871).
   Every relationship-type-filtered pattern (`-[:TYPE]->`, used by
   `Expand`, `OptionalExpand`, `VarLengthExpand`, and the predicated
   shortest-path builder) used to rebuild its filter from a full graph
   scan on every execution, regardless of selectivity. A new bounded
   LRU now caches the filter map keyed by the relationship-type set and
   a monotonic topology-generation counter bumped on every edge
   mutation. Measured on a 120k-node / ~960k-edge graph with an
   8-edge, highly selective relationship type: a repeated query against
   an unchanged graph drops from **≈190 ms / 2.16 M allocs/op to
   ≈30 ms / 336 K allocs/op** — a ~6.3× wall-clock and ~6.4× allocation
   reduction for the steady-state (post-first-query) case. This
   benchmark is new in this cycle (`bench/cypher_scale`, added
   alongside #1860) and has no `v0.6.0` baseline to diff against
   like-for-like; the number above is the commit's own before/after
   measurement, reproduced from `git log` and re-verified against the
   current `bench/cypher_scale` benchmark at this tag. It does not
   appear in the `v0.6.0 → v0.7.0` table below because the `search`/
   `search/centrality` guard-band benchmarks do not exercise
   relationship-type filtering.
2. **`Dijkstra_Large`'s stray heap escape reclaimed** (#1820), see
   above.

New functionality shipped this cycle (the eight builtin Cypher
functions, `MERGE` whole-pattern semantics, parallel-edge rejection) and
the security/DoS hardening (bounded allocations, `O_NOFOLLOW`, streamed
GraphML import) are invoked only on their respective code paths and do
not regress any guard-band benchmark, confirmed by the
[measured comparison](#v060--v070-comparison) below.

## v0.6.0 → v0.7.0 comparison

This section is a **real, measured** side-by-side benchmark of the
`v0.6.0` tag against this release's `HEAD`. Both sides were built and
run on the same machine, in the same session, with the **same
benchmark binaries' names**: the `v0.6.0` tree was checked out into a
throwaway `git worktree` (`git worktree add /tmp/gg-v060 v0.6.0`), each
benchmark set was run with `go test -bench -benchmem -count=6`
**sequentially — never concurrently with anything else** — on both
trees, and the two sample sets were compared with `benchstat` (`old` =
`v0.6.0`, `new` = `v0.7.0`). The worktree was removed afterwards.

> **Methodology note.** An initial attempt at this comparison ran the
> `v0.6.0` and `v0.7.0` headline benchmark processes concurrently on the
> same machine (an accidental artefact of background task scheduling,
> not a deliberate choice). That run showed a spurious ~70 % slowdown on
> `Dijkstra_Large`/`Dijkstra_PostWarmup` that a same-code sanity check
> immediately falsified — it was cross-process CPU and cache contention
> from two large-graph benchmark suites racing for the same 10 cores,
> not a real regression. That data was discarded and both runs were
> repeated strictly sequentially, producing the clean, mutually
> corroborating figures below. This is recorded here as a reminder that
> **benchmark isolation is a precondition for a valid measurement**, not
> an optional nicety.

All benchmarks reported here exist **identically in both tags**, so
every comparison is like-for-like. Benchmarks that were renamed, moved,
or added after `v0.6.0` are intentionally excluded — there is no honest
way to compare them across the two tags.
`BenchmarkAllNodesScan_ZeroAlloc` (present at `v0.6.0`) was renamed to
`BenchmarkAllNodesScan_PerNodeAllocCost` at some point before this
release and is excluded from the table below for the same reason.

### Method

| Property | Value |
|----------|-------|
| Old (base) | `v0.6.0` tag, built in `git worktree` |
| New | release `HEAD` (94 commits on top of `v0.6.0`) |
| Command | `go test -run='^$' -bench=<set> -benchmem -count=6` |
| Comparison | `benchstat old.txt new.txt` |
| Significance | `benchstat` two-sample test; `~` means *p* ≥ 0.05 (no significant change) |
| Environment | Apple M4 (10-core), macOS 26.5.1 (darwin/arm64), go1.26.4, GOMAXPROCS=10 |
| Isolation | Each side run to completion before the other started; no concurrent process on the machine during either run |

### Interpretation

- **Genuine, measured wins.** `Dijkstra_Large` drops **−20% allocs/op**
  (5 → 4) and **−11.84% B/op** — the pre-sized pooled-heap fix (#1820)
  restoring the guard band that had regressed during the `v0.6.0`
  cycle. `Yen_K100`'s wall-clock time improves a small but statistically
  significant **−2.78%** with unchanged allocations. The `cypher/exec`
  geomean improves a marginal **−0.95%** in time, within normal
  run-to-run variation for a set with no functional change targeting
  it.
- **No regressions.** Every other headline and `cypher/exec` benchmark
  is statistically unchanged (`~`) between `v0.6.0` and `v0.7.0`. The
  two post-warmup, reusable-state traversal paths
  (`Dijkstra_PostWarmup`, `BFSDirectionOpt_PowerLaw`) remain
  **zero-allocation** in both tags.
- **The cycle's biggest measured win — the edge-type-filter cache
  (#1871) — is not in this table** because it applies specifically to
  relationship-type-filtered `Expand`/`VarLengthExpand` traversal, which
  none of the `search`/`search/centrality`/`cypher/exec` guard-band
  benchmarks exercise. Its ~6× improvement is reported in
  [Performance impact of this release](#performance-impact-of-this-release)
  above from the dedicated `bench/cypher_scale` benchmark instead.
- **New functionality is opt-in and off the hot path.** The eight new
  Cypher builtin functions, `MERGE` whole-pattern semantics, and the
  security/DoS hardening (bounded allocations, streamed GraphML import,
  `O_NOFOLLOW`) are invoked only on their respective code paths — none
  of them execute during a `Dijkstra`/`BFS`/`Yen`/`Brandes` traversal or
  a `cypher/exec` pipeline-operator benchmark, consistent with the flat
  results above.

## Load test — read-path concurrency sweep

CLAUDE.md requires a load-test report "at multiple concurrency levels
(1, 8, 64, 256, 1024 goroutines)". As in
[v0.6.0](v0.6.0.md#load-test--read-path-concurrency-sweep), we sweep
`GOMAXPROCS` over the `b.RunParallel` hot-key intern benchmark — the
tightest shared-state contention point in the read path, where every
goroutine interns the **same** key and competes for the same cache line.
Each figure is the median of 5 samples.

| Goroutines (`GOMAXPROCS`) | ns/op (median) | B/op | allocs/op |
|--------------------------:|---------------:|-----:|----------:|
| 1 | 8.08 | 0 | 0 |
| 8 | 91.33 | 0 | 0 |
| 64 | 88.98 | 0 | 0 |
| 256 | 88.80 | 0 | 0 |
| 1024 | 87.93 | 0 | 0 |

**Reading the sweep.** From 8 to 1024 goroutines (a 128×
over-subscription of the 10 physical cores) per-op latency stays **flat
at ≈ 88–91 ns/op with zero allocations** — the structure degrades
gracefully and predictably under massive over-subscription rather than
collapsing, so the bounded-resource and lock-contention mandates hold.
The single-goroutine figure (8.08 ns/op) reflects the absence of atomic
contention at `GOMAXPROCS=1`; the jump to the ≈88–91 ns/op plateau
happens once multiple goroutines genuinely contend for the same cache
line, and the plateau itself does not grow with further
over-subscription.

## Reproduce

```
# Headline / guard-band set (median of 6)

# Read-path concurrency sweep (median of 5)

  -benchmem -cpu=1,8,64,256,1024 -count=5 ./graph/
```
