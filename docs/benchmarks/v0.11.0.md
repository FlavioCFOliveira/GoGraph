# Benchmarks — v0.11.0

Headline benchmark and load-test numbers for the GoGraph **v0.11.0** release,
measured first-hand at the release candidate.

> **What moved in v0.11.0.** Two things: **concurrency control became MVCC and
> nothing else** — the single-writer semaphore, the engine writer mutex and the
> `Graph.View` read barrier are gone — and the **planner gained six new access
> paths**. The headline consequence is on the **write** side: durable write
> throughput is now monotonic in writer count and scales **415×** from 1 to 1024
> writers, where v0.10.0 delivered the same throughput at 32 writers as at one.
> The headline **cost** is on the read side: the paths that walk a graph and read
> its properties pay a few percent for per-read version resolution, and one
> **plan-choice defect regressed a selective multi-label query 21×** in the
> default configuration (§5) — it is open, filed, and stated here rather than
> omitted.

> Re-measure on your own hardware before relying on any absolute number; these
> are medians from documented runs, not a guarantee.

## Run environment

| Property | Value |
|----------|-------|
| Date | 2026-08-13 |
| Commit | `ba436a5b` (branch `sprint-344`) |
| CPU | Apple M4 (10-core: 4 performance + 6 efficiency) |
| Memory | 32 GB |
| OS / arch | macOS (Darwin 25.5.0), `darwin/arm64` |
| Go toolchain | go1.26.5 (unchanged from `v0.10.0`; `go.mod` is byte-identical) |
| GOMAXPROCS | 10 (default) for the headline set; swept 1/8/64/256/1024 for the load tests |
| Host load at start | 1-minute load average **2.22** of 10 cores |
| Race detector | **off** for every figure here — a benchmark under `-race` measures the detector |

**Why the load average is recorded.** The 2026-08-10 release-delta record
established that on this host a 1-minute load average above ~2.5 produces a
**systematic bias, not noise**. Every run below was gated on that threshold: the
harness polled `vm.loadavg` and did not start until it was under 2.5. The
one-minute average had risen by the end of the run, which is the measurements'
own load — the sequential ordering below exists so that no two measurements
overlap.

All four runs were **sequential by construction**, one process at a time. Benchmark
output was passed through the same `strip_log_noise` repair
[`scripts/bench-history.sh`](../../scripts/bench-history.sh) applies, and **the
number of surviving result lines was asserted against the number expected** — the
2026-08-10 record lost 99 of 392 result lines to an interleaved log line, and a
`benchstat` that silently sees fewer samples reads exactly like "no regression".

## 1. Headline benchmarks

The canonical regression-gate set, as defined by
[`scripts/run_headline_bench.sh`](../../scripts/run_headline_bench.sh). Each
figure is the **median of 6 samples**.

| Benchmark | Package | ns/op (median) | Δ vs v0.10.0 | B/op | allocs/op | allocs vs v0.10.0 |
|-----------|---------|---------------:|-------------:|-----:|----------:|:-----------------:|
| `BenchmarkDijkstra_PostWarmup` | `search` | 8,274,682 (≈ 8.27 ms) | +3.83 % | 0 | 0 | identical |
| `BenchmarkDijkstra_Large` | `search` | 8,360,191 (≈ 8.36 ms) | +4.02 % | 1,174,630 | 4 | identical |
| `BenchmarkBFSDirectionOpt_PowerLaw` | `search` | 29,869,606 (≈ 29.87 ms) | +3.23 % | 0 | 0 | identical |
| `BenchmarkYen_K100` | `search` | 14,467,984 (≈ 14.47 ms) | +1.51 % | 459,332 | 1,280 | identical |
| `BenchmarkBrandes_RandomGraph` | `search/centrality` | 8,090,764 (≈ 8.09 ms) | +1.47 % | 62,208 | 10 | identical |

**The zero-allocation mandate holds.** `Dijkstra_PostWarmup` and
`BFSDirectionOpt_PowerLaw` still allocate **zero** bytes per call, and **every
allocation count is identical to `v0.10.0`** (0, 4, 0, 1 280, 10) — so no
hot-path allocation regression landed.

**The +1.5 % to +4.0 % on time is reported, not explained away.** These
algorithms' own code is unchanged in this release; what changed beneath them is
the graph read path, which now resolves a version per read. That direction is
consistent with the seven independent 7–16 % iteration regressions the
[2026-08-10 release delta](release-delta-v0.10.0-to-head-2026-08-10.md) §5
measured across unrelated packages, and with its cleanest case — `WriteCSV`,
whose B/op and allocs/op are byte-identical across revisions while its time rose
15.72 %. It is **not** proof: a cross-session comparison against figures
published on a different day cannot separate a small real regression from
session drift, and no within-revision A/B exists because the MVCC on/off switch
was deliberately removed. Treat these five as "unchanged to a few percent,
trending slightly slower".

**One honest caveat on `Dijkstra_Large`'s B/op.** Its `+4.03 %` is a median over a
sample that **spans 1 129 358 – 1 191 048 B/op**, and `v0.10.0`'s published
1 129 088 sits at the *bottom* of that spread. `v0.10.0` reported a stable value
where this run shows ~5 % variance, so the honest reading is that this
benchmark's byte count is no longer deterministic, not that it allocates 4 % more.
Its allocation **count** is 4 in every sample, as before.

## 2. Load test — read-path concurrency sweep

CLAUDE.md requires a load-test report "at multiple concurrency levels (1, 8, 64,
256, 1024 goroutines)". As in [v0.10.0](v0.10.0.md) we sweep `GOMAXPROCS` over
the `b.RunParallel` hot-key intern benchmark — the tightest shared-state
contention point in the read path, where **every goroutine interns the same key**
and competes for the same cache line. **Median of 5**; 25 of 25 expected result
lines survived.

| Goroutines (`GOMAXPROCS`) | ns/op (median) | Aggregate throughput | Δ vs v0.10.0 | B/op | allocs/op |
|--------------------------:|---------------:|---------------------:|-------------:|-----:|----------:|
| 1 | 8.782 | 113.9 M ops/s | **+14.35 %** | 0 | 0 |
| 8 | 75.150 | 13.31 M ops/s | +2.62 % | 0 | 0 |
| 64 | 88.840 | 11.26 M ops/s | −0.97 % | 0 | 0 |
| 256 | 88.470 | 11.30 M ops/s | −1.28 % | 0 | 0 |
| 1024 | 88.680 | 11.28 M ops/s | −0.63 % | 0 | 0 |

**Read this sweep correctly.** Under `b.RunParallel`, `b.N` is the total iteration
count across all goroutines, so **`ns/op` is inverse *aggregate* throughput, not
per-goroutine latency**. The drop in aggregate throughput from 1 to 8 goroutines
is therefore not a scaling failure of the module — it is the cost of cache-line
contention existing at all, on a benchmark deliberately built so that every
goroutine fights for one key. This is a **contention probe, not a throughput
scaling test**; §3 is the throughput scaling test.

**What it establishes.** From 8 to 1024 goroutines — a **128× over-subscription**
of 10 physical cores — per-op cost stays **flat at 75–89 ns with zero
allocations**, and the 64/256/1024 levels are statistically indistinguishable
from one another. The structure degrades predictably under massive
over-subscription rather than collapsing, so the bounded-resource and
lock-contention mandates hold at the published levels.

**The single-goroutine regression is real and is the honest cost.** 7.68 → 8.782
ns/op, **+14.35 %**, on the uncontended path. It independently reproduces the
`Mapper_Intern_HotKey` **+9.28 %** (8.026 → 8.771 ns) that the 2026-08-10 release
delta measured on the serial variant of the same benchmark, so it is a property
of the code rather than of this session. At 1024 goroutines the same structure is
**0.63 % faster** than at v0.10.0: this release traded a little uncontended
latency for contended-path behaviour that no longer degrades.

## 3. Load test — durable write throughput at the published levels

`BenchmarkWriteScaling_StoreAPI` and `BenchmarkWriteScaling_Cypher`
(`store/txn/write_scaling_bench_test.go`) sweep exactly the published ladder —
`writerCounts = []int{1, 8, 64, 256, 1024}`. Both perform **one durable
single-edge transaction per operation** against the same WAL and engine, so a
divergence between them isolates commit-path coordination rather than the cost of
the write. **Median of 6.**

**This sweep had never been run.** The last three production certifications each
recorded it as unrun — see
[`docs/certification-2026-08-13.md`](../certification-2026-08-13.md) §5 item 4.
Running it here discharges that envelope item.

### 3.1 Through the store API (`txn.Tx.Commit`)

| Writers | Throughput | Scaling | commits/fsync |
|--------:|-----------:|--------:|--------------:|
| 1 | 268.4 ops/s | 1.00× | 1.00 |
| 8 | 1,098.5 ops/s | 4.09× | 4.08 |
| 64 | 8,321.5 ops/s | 31.00× | 31.50 |
| 256 | 32,234.0 ops/s | 120.07× | 121.20 |
| **1024** | **111,483.0 ops/s** | **415.28×** | **422.05** |

### 3.2 Through the Cypher engine (autocommit)

| Writers | Throughput | Scaling |
|--------:|-----------:|--------:|
| 1 | 271.0 ops/s | 1.00× |
| 8 | 1,060.0 ops/s | 3.91× |
| 64 | 8,253.5 ops/s | 30.46× |
| 256 | 30,804.0 ops/s | 113.67× |
| **1024** | **115,300.5 ops/s** | **425.46×** |

**Throughput is monotonic in concurrency at every step**, and the two arms track
each other within a few percent — so the Cypher layer adds no coordination the
store API does not already have.

**The mechanism is proven arithmetically, not asserted.** The scaling factor
equals `commits/fsync` at every level: 4.09 vs 4.08, 31.00 vs 31.50, 120.07 vs
121.20, 415.28 vs 422.05. The gain is **group-commit fsync amortisation** and
nothing else. The single-writer rate of 268 ops/s is this device's
single-writer fsync rate — an fsync per commit is an fsync per commit, and the
1-writer figure is therefore **unchanged from v0.10.0's 245–248 commits/s** to
within cross-session variance. **Nothing was traded for the scaling.**

This independently reproduces
[`apply-gate-wake-2026-07-27.md`](apply-gate-wake-2026-07-27.md)'s ladder
(264 → 1 061 → 8 306 → 31 630 → 111 897 ops/s) from a different harness, and the
2026-08-10 release delta's finding that **v0.10.0 had no write concurrency at
all** — 245 commits/s at one writer and 254 at thirty-two.

## 4. What v0.10.0 → v0.11.0 does to a workload

The authoritative end-to-end comparison is
[`release-delta-v0.10.0-to-head-2026-08-10.md`](release-delta-v0.10.0-to-head-2026-08-10.md),
measured over 143 benchmarks whose workload provably could not change plus a
purpose-built two-revision harness.

**It is measured at `7a70eb3f`, which is five sprints behind this tag.** Sprints
339–343 landed after it, and they contain the largest memory and CPU wins of the
release — the 2.74× cut in memory per relationship, the byte-stream property bag,
the 6.03× Bolt CPU reduction, and the bulk-delete fix. Its **read and write**
figures are therefore a floor rather than a ceiling for this tag; its
**regression** figures are the ones to treat as still-current, and §1, §2 and §5
above re-measure the three that matter most at the real tag.

Headlines from that record, unchanged by this run:

| Axis | v0.10.0 → HEAD |
|---|---|
| Durable write scaling, 1 → 32 writers | 1.04× → **16.53×** |
| Parameterised point lookup on an indexed property | **50–65×** faster (up to 267× at 20 000 nodes) |
| LDBC Interactive Complex, 15 queries | geomean 25.70 → 18.44 µs (**−28.24 %**) |
| Graph iteration and bulk write, 7 independent benchmarks | **+7–16 % slower** |
| WAL recovery, 15 000 ops | 5.680 → 8.561 ms (**1.51× slower**) |
| On-disk bytes per node | 278 → 286 (**+2.9 %**) — the commit timestamp |
| Steady-state heap, 20 000 nodes / 60 000 edges | +1.3 % heap in use, **−10.6 % mallocs** |

The single most important item in it is not a ratio: **the flagship read suite was
structurally blind to the largest read win of the cycle**, because every benchmark
in `bench/cypher_ldbc` passes literal keys in the query text, and literals already
seeked at v0.10.0. The 50–65× gain applies to the parameterised form that every
Bolt client, prepared statement and plan-cache hit actually sends. Any future
read-path gate must carry a parameterised arm.

## 5. One regression that is a defect, not a trade-off — CONFIRMED OPEN

`BenchmarkMinLabelScanSelective_MinLabel`, **median of 6**:

| Arm | ns/op | B/op | allocs/op |
|---|---:|---:|---:|
| `_MinLabel` (the optimised plan) | **4,979,786** (≈ 4.98 ms) | 7,119,359 | 106,293 |
| `_FirstLabel` (the legacy control it exists to beat) | 3,403,230 (≈ 3.40 ms) | 117,021 | 811 |

v0.10.0 measured `_MinLabel` at **230.3 µs** on the same fixture, so this is a
**≈21.6× regression** — and the optimised arm is now **slower than its own
control**, with **131× more allocations**. The relationship the benchmark's name
asserts does not hold.

Attributed at this tag by sweeping `cypher.EngineOptions` on the same fixture
(100 000 `:Common` nodes of which 1 000 also carry `:Rare`), **asserting 1 000
rows in every arm**, best of 30 repetitions:

| Configuration | best | Chosen plan |
|---|---:|---|
| **default** | **4.087 ms** | `Project / ParallelScanProject` |
| `DisableParallelScan` | **0.194 ms** | `ColumnarProject / Filter / NodeByLabelScan [Rare]` |
| `DisableBitmapIntersection` | 4.078 ms | `Project / ParallelScanProject` (unchanged) |
| `DisableParallelScan` + `DisableBitmapIntersection` | 0.195 ms | `NodeByLabelScan [Rare]` |
| `DisableParallelScan` + `DisableMinLabelScan` | 3.122 ms | `NodeByLabelScan [Common]` |
| `DisableMinLabelScan` (legacy) | 3.308 ms | `NodeByLabelScan [Common]` |

The conclusion is precise, and every clause is measured:

- **The min-cardinality label anchor still works** — 0.194 ms, which is *faster*
  than v0.10.0's 230 µs on the same fixture. It is simply **never chosen**.
- **The parallel-scan tier is admitted ahead of it and is 21.1× slower** on this
  shape. It is also slower than the **legacy** plan (3.308 ms) that the anchor was
  built to replace, so on this shape it is the worst of the three plans the engine
  can produce.
- **The bitmap intersection is not implicated**: disabling it changes neither the
  plan nor the time.
- **The regression is in the default configuration**, which is what every user
  gets.

This is not a trade-off; it is **a gate admitting a plan it should reject**, on a
plan the same engine still knows how to produce. It was first recorded in the
2026-08-10 release delta at 24.4× and **was never filed as a task**; it is now
**rmp #2431**, and it survives three further sprints unchanged.

## 6. What this snapshot does NOT measure

- **Latency percentiles.** §2 and §3 report throughput and per-op cost at the
  published levels; they do not report p50/p99 at each level. The one percentile
  evidence carried into this release is inherited: `DIMACS_SF1_SSSP` moves further
  at the tail than at the mean — p50 281.7 → 331.5 µs, **p95 338.9 → 442.6 µs
  (+30.58 %)**.
- **The whole-tree soak layer**, unrun for a fourth consecutive cycle. The
  artefacts in `soak-artefacts/` are from 2026-05-30 at commit `b5453b9`.
- **Bolt at concurrency.** [`bolt-concurrency-pooled-vs-churn-2026-08-10.md`](bolt-concurrency-pooled-vs-churn-2026-08-10.md)
  is the instrument; it was not re-run at this tag.
- **Any platform but this one.** Single host, single architecture: Apple M4,
  10 cores, `darwin/arm64`. No Linux, no NUMA, no multi-socket, no container.
- **The open memory findings** — rmp #2404, #2405, #2407 — and **rmp #2425**, the
  3–10 % cost of the deferred `UNIQUE` release on constrained writes.

## 7. Reproduce

Every command below was executed to produce the figures above, sequentially, on a
host gated at a 1-minute load average below 2.5.

```bash
# §1 — headline / guard-band set (median of 6)
./scripts/run_headline_bench.sh

# §2 — read-path concurrency sweep (median of 5)
go test -run='^$' -bench='^BenchmarkMapper_Intern_HotKey_Parallel$' \
  -benchmem -cpu=1,8,64,256,1024 -count=5 ./graph/

# §3 — durable write throughput at 1/8/64/256/1024 writers (median of 6)
go test -run='^$' -bench='^BenchmarkWriteScaling' -benchmem -count=6 \
  -timeout 40m ./store/txn/

# §5 — the regression, and its control
go test -run='^$' -bench='^BenchmarkMinLabelScanSelective_(MinLabel|FirstLabel)$' \
  -benchmem -count=6 ./bench/cypher_ldbc/
```

Pipe every invocation through `strip_log_noise` from
[`scripts/bench-history.sh`](../../scripts/bench-history.sh) **before** filtering,
and assert the number of results kept against the number expected — otherwise a
library log line splits a benchmark's name from its result and the sample is
dropped in silence.

The §5 attribution needs a short harness in package `cypher_ldbc_test` that
reuses `buildMinLabelScanBenchGraph` and `minLabelScanBenchQuery`, constructs one
`cypher.Engine` per `EngineOptions` arm with `MaxResultRows:
cypher.MaxResultRowsUnlimited`, prints `Engine.Explain` beside the timing, and
**asserts 1 000 rows in every arm** so a configuration that returns fewer rows
cannot read as faster.

Per-change (rather than per-release) tracking lives in [`history/`](history/); the
narrative ledger is [`history/LEDGER.md`](history/LEDGER.md). The prior
authoritative baseline is [v0.10.0](v0.10.0.md).
